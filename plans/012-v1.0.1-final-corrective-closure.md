# Phase 12: final version 1.0.1 corrective closure

## Objective

Close the defects that remain after the first Phase 11 implementation attempt and produce a release candidate that can legitimately satisfy the version-1 contract on Linux and macOS.

This is a narrowly scoped correctness, lifecycle, packaging, and evidence pass. It must not redesign the three-crate architecture, add new metrics, or expand Gregg into a general monitoring platform.

The implementation baseline for this plan is commit:

```text
9fb34cdcd5b2e4f08c63097839027911b2513be4
```

Phase 11 corrected several important defects, including the Darwin swap ABI field layout, pre-binding the daemon listener, wiring snapshot staleness, explicit-port parsing, streaming response bodies, immediate startup polling, batch membership after task panic, and initial CI expansion. Those items should be preserved. This plan addresses only the defects and evidence gaps that remain.

## Required outcome

At the end of this phase:

- all remaining release-blocking defects are corrected;
- native Linux and macOS behavior is demonstrated on the supported architecture classes;
- service lifecycle and installer behavior are exercised, not merely unit-tested;
- clean package and install verification exists for all three crates;
- resource and soak evidence contains actual measurements;
- the `1.0.1` source, annotated tag, crates.io packages, and evidence all identify the same release candidate;
- Phase 11 and Phase 12 statuses accurately describe what was and was not completed.

## Non-goals

Do not add:

- TLS, authentication, or public-internet deployment support;
- historical storage, alerting, or service discovery;
- per-process metrics;
- remote execution or administration;
- plugin systems;
- new protocol fields or a schema-version change;
- a replacement HTTP stack, terminal framework, or service-management abstraction;
- broad refactors unrelated to the defects listed below.

## Workstream A: finish macOS FFI correctness

### A1. Use the canonical host-self interface

The current implementation calls the legacy `host_self()` compatibility symbol. Replace it with the canonical `mach_host_self()` declaration unless a documented linker constraint requires retaining the compatibility symbol.

Required behavior:

- declare `mach_host_self() -> mach_port_t` in the isolated FFI module;
- obtain a valid host send right before Mach host queries;
- reject `MACH_PORT_NULL` defensively even if the API is expected not to return it;
- keep raw ports private to `collector/macos/ffi.rs`;
- preserve the safe owned-value interface exposed to the collector.

Suggested shape:

```rust
struct HostPort {
    port: mach_port_t,
}

impl HostPort {
    fn current() -> Result<Self, CollectError> {
        let port = unsafe { mach_host_self() };
        if port == MACH_PORT_NULL {
            return Err(CollectError::new(
                CollectErrorKind::SourceUnavailable,
                "mach_host_self returned MACH_PORT_NULL",
            ));
        }
        Ok(Self { port })
    }

    fn raw(&self) -> mach_port_t {
        self.port
    }
}
```

Do not claim that a Mach trap “cannot fail” as the safety justification. Validate the returned port and convert failure into a normal collector error.

### A2. Correct Mach send-right deallocation

The current `Drop` implementation passes `MACH_PORT_NULL` as the task argument to `mach_port_deallocate`. That is not the current task IPC space.

Required correction:

- declare or otherwise obtain `mach_task_self()`;
- call `mach_port_deallocate(mach_task_self(), host_port)`;
- never pass `MACH_PORT_NULL` as the task argument;
- contain all ownership handling inside the FFI module;
- document whether `mach_host_self()` returns a send right that this process must release;
- in `Drop`, failure cannot be returned, but it must not be described as impossible;
- where practical, add a test-only query counter or repeated native smoke test capable of exposing unbounded right leakage.

A suitable implementation is:

```rust
impl Drop for HostPort {
    fn drop(&mut self) {
        if self.port == MACH_PORT_NULL {
            return;
        }

        let task = unsafe { mach_task_self() };
        if task == MACH_PORT_NULL {
            return;
        }

        let _ = unsafe { mach_port_deallocate(task, self.port) };
        self.port = MACH_PORT_NULL;
    }
}
```

If the selected API returns a non-owned special port that must not be deallocated, document that with an authoritative platform reference and remove the RAII deallocation instead. Do not leave ambiguous ownership semantics.

### A3. Strengthen native macOS tests

The existing tests prove individual native query functions return plausible data. Add a complete collector smoke test that exercises the production `FfiNativeQueries` path through the collector abstraction.

Required native test sequence:

1. Construct the production macOS collector.
2. Read identity and assert nonempty host, architecture, kernel release, and nonzero logical core/memory values.
3. Perform the CPU warm-up sample.
4. Wait only the minimum deterministic interval required for cumulative counters to advance.
5. Perform a second sample.
6. Validate the complete protocol snapshot.
7. Assert `cpu_iowait == false` and `iowait_pct == None`.
8. Assert memory total and page size are nonzero.
9. Assert swap used is not greater than swap total.
10. Repeat the complete sample path enough times to catch ownership or state-reset defects.

Do not replace this with another mock test.

### A4. Restore actual Intel and Apple Silicon CI coverage

Use explicit GitHub Actions runner labels so the architecture is unambiguous.

Required matrix intent:

```yaml
- os: macos-15-intel
  expected_arch: x86_64
- os: macos-15
  expected_arch: arm64
```

Add a diagnostic step:

```sh
uname -m
rustc -vV
```

Fail the job if the observed architecture does not match the expected architecture. Do not assume two differently named macOS labels imply two architectures.

### A acceptance criteria

1. The FFI declares and calls the canonical host-self interface or documents a validated reason not to.
2. `MACH_PORT_NULL` is rejected before host-statistics calls.
3. Host-port ownership is correct and no deallocation call uses a null task port.
4. A complete production collector smoke test passes on Intel macOS.
5. The same smoke test passes on Apple Silicon.
6. Repeated sampling does not show monotonic Mach-port right growth attributable to Gregg.

## Workstream B: close client configuration correctness

### B1. Store the resolved port, not the parser placeholder

The current `cmd_add` computes the resolved port from `config.default_port` but stores `ep.port`, which remains `11310` for portless input.

Correct the construction so the stored endpoint uses the resolved value:

```rust
let resolved_port = if spec.port_was_explicit {
    spec.port
} else {
    config.default_port
};

let entry = SystemEntry {
    id: Uuid::new_v4().to_string(),
    host: spec.host,
    port: resolved_port,
    port_was_explicit: spec.port_was_explicit,
    name: name.map(str::to_owned),
};
```

Alternatively, add an `EndpointSpec::into_endpoint_with_port(resolved_port)` method. Do not compute one port for duplicate checking and store another.

Required regression tests:

- set `default_port = 12000`, then `add host`; stored port is `12000`;
- set `default_port = 12000`, then `add host:11310`; stored port is `11310` and explicit;
- duplicate detection uses the resolved stored address;
- `--replace` replaces the correct resolved address;
- list output displays the resolved address.

The previous test that leaves `default_port` at `11310` is insufficient and should remain only as a baseline case.

### B2. Integrate a real cross-process lock into mutation paths

The current `AdvisoryLock` can retain a file handle, but `ConfigStore::mutate` and `mutate_with_result` never acquire it. The process-local `Mutex` does not prevent two CLI processes from losing updates.

Required design:

- derive a stable lock path adjacent to the config, for example `config.toml.lock`;
- acquire the OS file lock before loading the config;
- hold it through mutation, validation, atomic write, directory sync, and final reload if performed;
- release it only after the complete critical section;
- keep the in-process mutex if useful for thread serialization, but do not treat it as the cross-process mechanism;
- avoid truncating the lock file before lock acquisition;
- use blocking lock acquisition with a bounded timeout, or retry nonblocking acquisition with bounded backoff;
- return a distinct, actionable lock timeout error;
- preserve the locked file handle in a guard object whose `Drop` releases the lock.

Suggested abstraction:

```rust
struct FileLockGuard {
    file: File,
}

impl FileLockGuard {
    fn acquire(path: &Path, timeout: Duration) -> Result<Self, ConfigError>;
}
```

The guard should be local to the mutation call. Avoid a global `AtomicBool`; the kernel lock state and retained file descriptor are the source of truth.

Required tests:

1. Two independent processes concurrently add different endpoints at least 100 times; no update is lost.
2. A process killed while holding or after releasing the lock does not permanently block future mutations.
3. Lock timeout produces a deterministic nonzero exit and does not modify the config.
4. A failed validation releases the lock.
5. A failed atomic write releases the lock.
6. The lock file may remain as an inode, but it must not imply a stale lock after the descriptor closes.

Use subprocess tests rather than two threads in the same process for the primary concurrency proof.

### B3. Keep serialization compatibility deliberate

`port_was_explicit` is persisted in `SystemEntry`. Confirm whether this is actually required after resolving the port.

Preferred rule:

- parsing input needs to distinguish omitted from explicit port;
- stored entries need only the resolved host and port unless public JSON/TOML behavior depends on preserving original syntax.

If the field remains persisted:

- document it in the configuration format;
- confirm old configurations deserialize with the intended default;
- confirm list/remove semantics depend only on the new command input, not historical persistence of the flag.

If it is not needed, remove it from `SystemEntry` while retaining it in `EndpointSpec`.

### B acceptance criteria

1. A non-default configured port is stored and polled correctly for portless additions.
2. Explicit `:11310` remains distinguishable from omitted port during command parsing.
3. Host-only and exact-port removal remain correct.
4. Duplicate and replacement behavior uses the same resolved port that is persisted.
5. Independent processes cannot lose valid concurrent mutations.
6. Lock failures are bounded, actionable, and leave configuration intact.

## Workstream C: repair polling scheduler control flow

### C1. Ensure one trigger produces one generation

The current refresh branch performs a generation inside `select!` and then falls through to the unconditional periodic generation. A single Ctrl-R therefore causes two polls.

Refactor the loop around an explicit trigger enum:

```rust
enum Trigger {
    Periodic,
    Manual,
    Cancel,
}
```

Each loop iteration should:

1. wait for exactly one trigger;
2. break on cancellation;
3. run exactly one generation for periodic or manual triggers;
4. send exactly one batch;
5. return to waiting.

A simpler acceptable structure is:

```rust
loop {
    tokio::select! {
        _ = cancel.cancelled() => break,
        msg = refresh_rx.recv(), if refresh_open => {
            match msg {
                Some(()) => run_one_generation().await,
                None => refresh_open = false,
            }
        }
        _ = interval.tick() => run_one_generation().await,
    }
}
```

Use `tokio::time::interval` with an explicit missed-tick policy, or document why a recreated sleep is preferred. Preserve the no-overlap invariant.

### C2. Handle refresh channel closure without a busy loop

When `refresh_rx.recv()` returns `None`, disable that select branch permanently. Do not repeatedly poll a closed receiver.

Required test:

- drop the refresh sender while leaving the scheduler active;
- observe only periodic generations at the configured interval;
- assert CPU/task activity does not become a tight loop;
- cancel and confirm prompt shutdown.

### C3. Specify timer semantics after manual refresh

Choose and document one behavior:

- fixed cadence: manual refresh does not reset the periodic schedule; or
- reset cadence: the next periodic generation occurs one full interval after manual refresh.

The current documentation says manual refresh does not reset the timer. Retain that behavior unless a deliberate contract change is documented. Tests must prove it.

### C4. Preserve complete batch membership

Keep the synthetic result for a panicked task, but distinguish task panic from cancellation if useful. At minimum:

- every configured endpoint appears exactly once;
- order is deterministic or explicitly normalized by state reduction;
- task panic does not panic the scheduler;
- cancellation during a generation has documented behavior;
- no generation overlaps another.

### C acceptance criteria

1. Startup produces one immediate generation.
2. One Ctrl-R signal produces exactly one additional generation.
3. Ten rapid Ctrl-R signals cannot exceed the documented coalescing or queue behavior.
4. Closing the refresh channel does not create a busy loop.
5. Periodic cadence after manual refresh matches documentation.
6. Every completed batch contains one result per configured endpoint.

## Workstream D: make the response cap strictly bounded

### D1. Check before allocation and append

The current client appends a response chunk before checking cumulative size. Change the order:

```rust
let next_len = body
    .len()
    .checked_add(chunk.len())
    .ok_or(PollOutcome::BodyTooLarge)?;

if next_len > MAX_RESPONSE_BYTES {
    return BodyTooLarge;
}

body.extend_from_slice(&chunk);
```

Also preallocate conservatively:

- if `Content-Length` is present and within the cap, reserve at most that value;
- never reserve based on an untrusted length greater than the cap;
- retain rejection before reading when declared length exceeds the cap.

### D2. Add hostile-body tests

Required cases:

- one chunk exactly at the cap succeeds if valid;
- one chunk one byte above the cap is rejected before append;
- many small chunks crossing the cap are rejected;
- no `Content-Length` with an unbounded stream is rejected at the cap;
- declared length below the cap but actual body above it is rejected;
- declared length above the cap is rejected without consuming the body;
- integer-overflow behavior is impossible through checked addition.

Where feasible, expose a small pure helper for bounded accumulation so allocation behavior can be tested deterministically.

### D acceptance criteria

1. The client never extends its accumulation buffer beyond `MAX_RESPONSE_BYTES`.
2. Oversized declared bodies are rejected before body consumption.
3. Oversized chunked bodies are rejected before the overflowing append.
4. Tests cover exact boundary, one-byte overflow, misleading length, and chunked overflow.

## Workstream E: finish daemon task supervision

### E1. Treat unexpected clean task exit as a failure

The daemon currently treats `Ok(())` from the server or sampler task as a clean daemon outcome even when no shutdown was requested.

Required rule:

- before shutdown has been initiated, any critical task exit is unexpected and must make `greggd run` return a nonzero runtime error;
- after shutdown has been initiated, normal task completion is expected;
- task panic and task-returned error are both propagated;
- a bind conflict remains a fail-fast error before task spawn.

Introduce explicit shutdown state rather than inferring from branch order.

### E2. Join all critical tasks during shutdown

After receiving a signal or detecting a critical failure:

1. broadcast shutdown exactly once;
2. wait for the server task with a bounded grace period;
3. wait for the sampler task with a bounded grace period;
4. abort only after the grace period expires;
5. report which task failed to stop;
6. return nonzero if shutdown followed a task failure or timed out.

Do not return while critical tasks remain detached.

### E3. Remove detached state-update tasks

The sampler callback currently spawns a new Tokio task for every state synchronization. This can reorder readiness transitions.

Use one of these designs:

- make the sampler callback async and await state synchronization; or
- send state updates through a bounded channel to one ordered consumer task.

Required invariant:

- if sample N transitions to failed and sample N+1 transitions to ready, state application order matches sampler order;
- shutdown drains or deliberately discards queued updates according to documented behavior;
- no unbounded task creation occurs at sample frequency.

### E4. Add end-to-end runtime tests

Required tests:

- bind conflict returns nonzero promptly;
- synthetic server task error stops sampler and returns nonzero;
- synthetic sampler task panic/error stops server and returns nonzero;
- unexpected `Ok(())` from either critical task is treated as failure before shutdown;
- signal-driven shutdown joins both tasks;
- stale snapshot transitions to `503` and a later valid sample restores `200`;
- ordered state update test proves no stale transition can overwrite a newer ready state.

### E acceptance criteria

1. No critical daemon task can terminate unnoticed.
2. Unexpected clean exit is a runtime failure.
3. Shutdown joins or explicitly times out every critical task.
4. Sampler state transitions are applied in order without detached per-sample tasks.
5. Bind, task failure, stale transition, recovery, and signal shutdown tests pass.

## Workstream F: correct native service lifecycle and installers

### F1. Redesign launchd semantics around loaded and running states

Separate these concepts:

- installed: plist exists;
- loaded: launchd knows the service;
- running: a process instance is active.

Required command behavior:

#### `start`

- if installed but unloaded, run `launchctl bootstrap system <plist-path>`;
- if loaded but stopped, run `launchctl kickstart system/<label>`;
- if already running, succeed idempotently or return a clearly documented no-op;
- do not require the user to bootstrap manually after `greggd stop`.

#### `stop`

Choose one consistent public meaning:

- stop process but keep service loaded, using an appropriate launchctl operation; or
- unload service with `bootout`, in which case `start` must bootstrap it again.

The simplest acceptable version-1 contract is unload-on-stop plus bootstrap-on-start.

#### `restart`

- loaded/running: kickstart with replacement;
- loaded/stopped: kickstart;
- installed/unloaded: bootstrap;
- missing plist: fail with an actionable path error.

#### `croncheck`

- active service: succeed with no action;
- loaded but not running: kickstart;
- installed but unloaded: bootstrap;
- missing plist or binary: return nonzero with diagnostics;
- repeated failures must remain bounded by existing restart-loop protection.

Correct `bootstrap` syntax to use `system` as the domain and the plist as the service path. Use `system/<label>` only as a service target where required.

### F2. Make service-state probing authoritative

Avoid parsing broad `launchctl list` output if a target-specific probe is available. Prefer `launchctl print system/<label>` and interpret exit status.

Required tests should use an injectable command runner and cover:

- loaded/running;
- loaded/stopped;
- unloaded/installed;
- missing plist;
- command permission failure;
- malformed or unexpected command output.

Native manual evidence must still exercise real launchd.

### F3. Correct installer repository-root resolution

Both installer scripts currently walk two levels above `packaging/`, resulting in the parent of the repository.

Use one level:

```sh
REPO_ROOT="$(cd "$(dirname "$0")/.." && pwd)"
BINARY_PATH="${REPO_ROOT}/target/release/greggd"
```

Required installer properties:

- work when invoked from any current directory;
- accept an explicit binary path override;
- validate the selected binary architecture;
- preserve existing config unless explicit replacement is requested;
- install the unit/plist from the repository root reliably;
- state exactly whether the service is started automatically;
- leave no partially installed service if a later step fails where rollback is practical.

Add shell syntax checks and isolated-prefix tests where root/service-manager access is unavailable.

### F4. Run systemd under a non-root identity

Implement a dedicated service account or `DynamicUser=yes`.

Choose based on config placement:

- `DynamicUser=yes` is acceptable if the daemon requires no persistent writable state and only reads the config;
- a static `greggd` system user is acceptable if packaging needs stable ownership.

The unit should not grant `/etc/gregg` write access during steady-state operation unless daemon behavior requires it. Configuration mutation commands can run separately with administrative privileges.

Required checks:

- daemon process UID is nonzero;
- `/proc`, `/sys`, and the config remain readable;
- no unnecessary capabilities are present;
- port 11310 binds successfully;
- restart and stop work under systemd;
- hardening directives do not block required metric collection.

### F5. Native lifecycle evidence

Record real command transcripts for:

- Linux systemd install, enable/start, status, restart, stop, start, uninstall or cleanup;
- macOS launchd install, bootstrap/start, print/status, restart, stop/unload, start/bootstrap, croncheck, cleanup;
- failure when binary or config is missing;
- behavior after host reboot where practical.

Do not substitute mocked command-runner tests for this evidence.

### F acceptance criteria

1. `greggd start` works from an installed but unloaded launchd state.
2. `stop`, `restart`, and `croncheck` match documented loaded/running semantics.
3. Launchctl commands use correct domains and service targets.
4. Both installers resolve the repository root correctly from any working directory.
5. Installer documentation matches actual auto-start behavior.
6. systemd runs `greggd` under a non-root identity.
7. Native systemd and launchd lifecycle evidence is recorded.

## Handoff rule

An implementing agent must leave any criterion open when required native hardware, service-manager privileges, crates.io access, or soak duration is unavailable. It must record the exact blocker and the command or environment needed to close it.
