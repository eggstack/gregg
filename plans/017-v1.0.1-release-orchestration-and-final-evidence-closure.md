# Phase 17: version 1.0.1 release orchestration and final evidence closure

## Objective

Close the remaining release-orchestration defects after the Phase 16 implementation pass, bind every qualifying native and protected-host execution to verified package artifacts, aggregate immutable evidence across separate workflow dispatches, and complete an auditable `1.0.1` release of:

- `gregg-protocol`;
- `greggd`;
- `gregg`.

The implementation baseline for this plan is:

```text
041a067fa9be222618c03c6d52c9a7a47e39031d
```

Phase 16 established the required release-integrity foundations and those changes must be preserved:

- full-SHA pre-tag candidate validation;
- annotated-tag validation for `v1.0.1`;
- canonical candidate metadata and validation;
- machine-readable mandatory stage requirements;
- actual `.crate` artifact upload for protocol and binary packages;
- package archive and installed-binary provenance helpers;
- locked binary installation from unpacked packages;
- package-derived protected operational and lifecycle jobs;
- explicit smoke and qualifying resource/soak modes;
- deterministic fleet fixtures;
- production `PollScheduler` and `AppState` mixed-fleet integration coverage;
- postpublication checkout and exact crates.io installation;
- aligned normal and development `gregg-protocol = 1.0.1` requirements;
- a conservative evidence ledger that does not claim release completion.

This phase is intentionally narrower than Phase 16. It must not redesign the application, daemon API, client state engine, collectors, service commands, TUI, or protocol. It closes the remaining release-control chain from verified source through package-derived execution, cross-run evidence, tag, publication, and registry verification.

## Current disposition

At the baseline commit:

- the Phase 16 implementation pass is committed;
- no final source SHA has been frozen for publication;
- no annotated `v1.0.1` tag exists;
- crates.io contains only unyanked `1.0.0` releases;
- no qualifying workflow run IDs, attempt IDs, GitHub artifact IDs, or artifact archive digests are recorded;
- per-dispatch aggregation exists, but final cross-run retrieval and aggregation are not wired into CI;
- candidate metadata uses semantic artifact labels rather than actual GitHub artifact identities;
- package provenance is generated independently for `greggd` and `gregg`, while no three-crate merged provenance document exists;
- the protocol package stage does not emit the same provenance record shape as the binary packages;
- protected-host package installation generates a new lockfile instead of consuming the exact lockfile tested during binary prepublication;
- native platform jobs still execute source-built workspace binaries rather than package-installed binaries;
- the mixed-fleet gate covers functional transitions but is not a sustained client/state-engine soak;
- systemd and launchd jobs lack guaranteed cleanup after an intermediate failure;
- annotated-tag timestamps are not normalized to the evidence validator's canonical UTC form;
- native and lifecycle artifacts remain incomplete relative to the Phase 16 evidence contract;
- the evidence ledger still describes the Phase 16 implementation as uncommitted.

Phase 17 is complete only when these defects are corrected, one immutable candidate completes all required stages, and `1.0.1` is tagged, published, registry-installed, and reconciled with immutable evidence.

## Governing invariants

1. **One immutable source:** every qualifying stage names the same full lowercase 40-character candidate SHA.
2. **One package chain:** every qualifying executable is installed from a `.crate` archive whose checksum and size are recorded in the merged package provenance manifest.
3. **One dependency graph per package gate:** protected and native package installations consume the exact verification lockfile generated and tested during binary prepublication.
4. **Actual artifact identity:** final evidence records GitHub workflow run ID, attempt, artifact ID, artifact name, artifact size, artifact creation time, and downloaded artifact archive checksum.
5. **No semantic-label substitution:** labels such as `package-archive` may describe artifact contents but may not be presented as GitHub artifact IDs.
6. **Cross-run completeness:** final aggregation downloads the selected immutable artifacts from every required workflow dispatch and rejects missing, duplicate, mixed-SHA, or conflicting evidence.
7. **Native source evidence is distinct from package-native evidence:** workspace builds may prove collector/source behavior, but package qualification must run package-installed binaries.
8. **Protected hosts are repeatable:** stale services, binaries, processes, ports, and temporary roots are detected or cleaned before execution and always cleaned after execution.
9. **A soak is not a functional smoke:** qualifying sustained gates enforce minimum duration, repeated transitions, sample completeness, and bounded resource behavior.
10. **No post-tag source mutation:** source, manifests, workflows, scripts, tests, and packaging are immutable after the annotated release tag is created.
11. **Publication is ordered and irreversible:** partial publication is recorded honestly; a source defect after publication requires a new patch version.
12. **Documentation follows evidence:** the plan registry and ledger are marked complete only after immutable release evidence exists.

## Workstream A: implement protected cross-run evidence retrieval

### A1. Add a dedicated final aggregation workflow

Add a workflow such as:

```text
.github/workflows/release-finalize.yml
```

It must be manually dispatched through a protected GitHub environment and accept:

- exact candidate SHA;
- release version, fixed to `1.0.1`;
- selected workflow run ID and attempt for each release stage group;
- optional explicit artifact IDs where a run contains ambiguous matching artifacts;
- rerun-selection file or equivalent structured input;
- tag name for final mode;
- a mode distinguishing pre-tag review from final postpublication aggregation.

Do not encode a large unreviewable free-form JSON document directly in a workflow input when a checked-in selection file or uploaded reviewed manifest can be used instead.

Recommended checked-in template:

```text
plans/evidence/v1.0.1-run-selection.example.json
```

Example logical shape:

```json
{
  "candidate_sha": "0123456789abcdef0123456789abcdef01234567",
  "release_version": "1.0.1",
  "runs": {
    "protocol-prepublish": {"run_id": "1001", "attempt": "1"},
    "protocol-index-check": {"run_id": "1002", "attempt": "1"},
    "binary-prepublish": {"run_id": "1003", "attempt": "2"},
    "native-source": {"run_id": "1004", "attempt": "1"},
    "native-package": {"run_id": "1005", "attempt": "1"},
    "mixed-fleet-client": {"run_id": "1006", "attempt": "1"},
    "operational-evidence": {"run_id": "1007", "attempt": "1"},
    "postpublish-verify": {"run_id": "1008", "attempt": "1"}
  }
}
```

### A2. Retrieve workflow run metadata

For every selected run, query the GitHub Actions API and preserve normalized run metadata:

- repository;
- workflow ID and workflow name;
- run ID;
- run attempt;
- event type;
- status and conclusion;
- creation, start, update, and completion timestamps where available;
- actor login or stable non-secret identifier;
- run URL;
- source branch metadata, clearly labelled as workflow dispatch context rather than candidate identity;
- selected artifact IDs.

Require:

- completed status;
- successful conclusion;
- exact selected attempt;
- repository equality;
- workflow identity matching the expected release workflow;
- no expired selected artifact.

Do not rely on the workflow run's `head_sha` as the release candidate identity for `workflow_dispatch`. Candidate identity must come from validated artifact metadata generated after detached checkout.

### A3. Resolve actual GitHub artifact records

For each selected run and attempt:

1. list workflow artifacts through the GitHub API;
2. filter by exact expected artifact names and selected run attempt;
3. require exactly one matching artifact unless an explicit reviewed selection resolves an approved rerun;
4. reject expired artifacts;
5. record:
   - numeric GitHub artifact ID;
   - artifact name;
   - artifact byte size;
   - creation and expiration timestamps;
   - workflow run ID;
   - workflow run attempt;
   - archive download URL only in transient execution logs, not as a durable credential-bearing URL;
6. download the artifact ZIP;
7. calculate SHA-256 and byte size of the downloaded ZIP;
8. extract into a run-and-artifact-specific directory;
9. validate contained candidate metadata before consuming any other file.

A final manifest must use numeric GitHub artifact IDs, not semantic labels from `candidate.json`.

### A4. Preserve semantic content roles separately

Keep candidate metadata's artifact entries, but rename or reinterpret the field so it cannot be confused with GitHub artifact identity.

Preferred shape:

```json
{
  "name": "greggd-1.0.1.crate",
  "role": "package-archive",
  "sha256": "...",
  "size_bytes": 12345
}
```

At final aggregation, attach those content records beneath the actual GitHub artifact record:

```json
{
  "github_artifact_id": 123456789,
  "github_artifact_name": "binary-greggd-1.0.1-deadbeef-1",
  "archive_sha256": "...",
  "archive_size_bytes": 45678,
  "contents": [
    {"name": "greggd-1.0.1.crate", "role": "package-archive", "sha256": "..."}
  ]
}
```

### A5. Token and permission constraints

The finalizer must use the minimum permissions required:

```yaml
permissions:
  contents: read
  actions: read
```

Use a protected environment for final aggregation and publication reconciliation. Do not print tokens, authenticated URLs, or full runner environment dumps.

### A acceptance criteria

1. A dedicated protected final aggregation workflow exists.
2. It accepts reviewed immutable run and attempt selections.
3. It queries actual workflow-run and artifact records through the GitHub API.
4. It rejects failed, incomplete, expired, missing, or ambiguous artifacts.
5. It downloads selected artifact ZIPs and records their SHA-256 and size.
6. It records numeric GitHub artifact IDs and exact names.
7. Candidate identity is derived from validated artifact metadata, not mutable workflow context.
8. Semantic content roles are not represented as GitHub artifact IDs.
9. Retrieval tests use deterministic mocked API responses or recorded fixtures.

Update the candidate schema and validator so every declared evidence content item can carry:

- `name`;
- `role`;
- `sha256`;
- `size_bytes`;

For qualifying success metadata, require checksum and size for files that materially support the gate, including:

- package archives;
- lockfiles;
- normalized manifests;
- package provenance;
- native transcripts;
- lifecycle transcripts;
- resource CSV and summary;
- soak CSV and summary;
- registry summary;
- tag identity;
- installed binary checksum records.

Pure descriptive notes may remain unhashed only when they are also represented inside a hashed containing artifact ZIP.

### B2. Record accurate start and completion times

Many current jobs set `started_at` and `completed_at` to the same value after execution. Correct each qualifying job to capture:

```bash
started_at="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
# run gate
completed_at="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
```

For long-running jobs, also record monotonic duration in the domain summary.

### B3. Record result from actual job outcome

Do not write `result = success` before all gate commands and metadata validation complete.

Recommended structure:

1. initialize evidence directory and start timestamp;
2. run gate under strict failure handling;
3. capture completion timestamp;
4. calculate file checksums and sizes;
5. write success candidate metadata;
6. validate metadata;
7. upload evidence.

For failures, an `if: always()` step may write separate non-qualifying diagnostic metadata with `result = failure`; the final aggregate must reject it for release qualification.

### B4. Include source identity mode

Candidate metadata must record whether the stage ran in:

- `pre-tag-full-sha` mode; or
- `annotated-tag` mode.

For final tagged stages, include:

- ref input `v1.0.1`;
- tag-object SHA;
- peeled commit SHA;
- normalized tagger identity and timestamp;
- tag object content digest.

### B acceptance criteria

1. Material evidence files include checksum and size records.
2. Candidate timestamps span actual execution rather than metadata creation only.
3. Success metadata is written only after the gate succeeds.
4. Failure metadata cannot qualify for final aggregation.
5. Source identity mode is explicit.
6. Final tagged evidence includes complete tag identity.

## Workstream D: reuse the verified lockfile on every qualifying install

### D1. Bind lockfile identity into provenance

For each binary package, add to provenance:

```json
{
  "verification_lockfile": "greggd-Cargo.lock",
  "verification_lockfile_sha256": "...",
  "verification_lockfile_size_bytes": 12345
}
```

The lockfile must be generated in the unpacked package before stable build/test/install and then retained unchanged.

### D2. Update protected package installer

Change `install-verified-package.sh` to require:

```text
--lockfile PATH
```

For binary crates it must:

1. verify the supplied lockfile checksum and size against provenance;
2. unpack the selected `.crate` archive;
3. reject an unexpected existing `Cargo.lock` unless it is byte-identical;
4. copy the verified lockfile into the unpacked package root;
5. verify the copied lockfile checksum again;
6. run `cargo install --path ... --locked`;
7. retain the install transcript outside the temporary directory;
8. output a machine-readable installation record containing archive, lockfile, and binary identities.

It must not silently generate a new lockfile in a qualifying mode.

A separate explicitly named local-smoke mode may generate a lockfile, but that mode cannot satisfy release qualification.

### D3. Update native and protected workflows

Every package-installed daemon/client execution must download and provide:

- `.crate` archive;
- package provenance file;
- exact verification lockfile;
- expected candidate SHA and version.

This applies to:

- native package runtime jobs;
- systemd lifecycle;
- launchd lifecycle;
- Linux resources;
- macOS resources;
- Linux soak;
- macOS soak;
- any package-installed mixed-fleet client run.

### D4. Test dependency-graph drift rejection

Add deterministic tests proving:

- modified lockfile checksum fails;
- missing lockfile fails;
- a freshly generated but different lockfile fails;
- copied lockfile checksum is revalidated;
- `cargo install --locked` is present;
- qualifying mode never invokes `cargo generate-lockfile`.

### D acceptance criteria

1. Binary provenance records lockfile checksum and size.
2. Protected/native installers require the verified lockfile.
3. Qualifying installs never generate a replacement lockfile.
4. Lockfile mutation or omission fails before compilation.
5. Installation records connect archive, lockfile, and binary identities.
6. Stable, MSRV, native, lifecycle, resource, and soak package gates share the recorded dependency graph.

## Workstream F: add sustained mixed-fleet client/state-engine evidence

### F1. Preserve the deterministic functional test

Keep the existing two-generation mixed-fleet integration test as the fast functional gate. Extend it to cover a healthy-to-failure transition in addition to failure-to-recovery.

Required functional transitions:

- healthy remains healthy;
- slow remains independently tracked;
- timeout fails without blocking the full fleet indefinitely;
- malformed payload becomes an endpoint-local failure;
- HTTP failure remains endpoint-local;
- stale payload semantics are asserted explicitly;
- recovery moves from failed to online;
- a previously healthy endpoint moves to failed;
- refused connection remains endpoint-local;
- refresh generations remain monotonic.

### F2. Add a sustained nonvisual state-engine harness

Add either:

- a dedicated integration-test harness; or
- a supported hidden/internal nonvisual test command;

that drives the production poller, scheduler, reducer, and cancellation behavior for a bounded sustained duration.

Qualifying defaults should be defined by the release contract. A practical minimum for this release-control gate is 30 minutes unless an earlier plan explicitly requires longer.

The sustained gate must include repeated fixture transitions on a deterministic schedule, for example:

- healthy → error → healthy;
- recover endpoint alternating failure and success;
- slow endpoint latency variation below and above timeout;
- malformed → valid;
- stale timestamp → current timestamp;
- endpoint process restart;
- connection refusal and recovery on a newly bound port.

### F3. Measure bounded behavior

Record over the sustained run:

- generation count;
- expected and observed refresh count;
- per-endpoint outcome counts;
- maximum batch duration;
- request timeout compliance;
- active task count or a supported proxy;
- process RSS and CPU;
- file descriptor count where supported;
- channel depth or backpressure indicators available from the implementation;
- cancellation completion time;
- fixture process count;
- panic/error count.

Define pass/fail criteria before observing final results. At minimum:

- no panic;
- no unbounded generation lag;
- no monotonic RSS/task/descriptor growth beyond documented tolerance;
- all expected transitions observed;
- scheduler cancels within a bounded interval;
- a slow endpoint does not cause full-fleet duration to exceed the concurrency/timeout contract.

### F4. Package-bind the client soak

The sustained qualifying run must execute the client code from the verified `gregg-1.0.1.crate` package artifact, not only from the workspace.

Acceptable approaches:

- install the package and invoke a supported nonvisual evidence command compiled into the release binary; or
- unpack the exact package archive, apply the verified lockfile, and run a package-contained integration harness whose source and dependency graph are provenance-bound.

Do not add a public user-facing command solely for evidence unless it is clearly hidden and harmless.

### F5. Retain evidence

Upload:

- transition schedule;
- expected transition manifest;
- observed transition JSONL/CSV;
- resource samples;
- summary JSON;
- fixture logs;
- package provenance;
- lockfile identity;
- candidate metadata.

### F acceptance criteria

1. Functional coverage includes healthy-to-failure and failure-to-recovery.
2. A sustained production state-engine gate exists.
3. The sustained gate uses package-bound client code.
4. Repeated deterministic transitions are observed.
5. Generation, cancellation, resource, and task/descriptor behavior are measured.
6. Predeclared thresholds determine pass/fail.
7. Raw and summarized evidence is uploaded.

## Workstream G: harden protected-host preflight and cleanup

### G1. Add explicit preflight steps

Before systemd or launchd installation, require a preflight transcript that checks:

- expected OS and architecture;
- runner label/host class;
- current service state;
- existing installed binary path and checksum;
- existing service definition/plist/unit checksum;
- port `11310` availability;
- stale `greggd` processes;
- stale release-specific temporary roots;
- available disk space;
- required commands and privilege capability;
- no conflicting test run marker.

The workflow may clean a known stale state only through a documented cleanup function. Unexpected state must fail with diagnostics rather than being overwritten silently.

### G2. Add a run-scoped marker and lock

Protected hosts should use a release-run lock or marker containing:

- repository;
- workflow run ID;
- attempt;
- candidate SHA;
- start timestamp.

Acquire atomically. Refuse concurrent qualifying runs. Remove it during guaranteed cleanup.

### G3. Move cleanup to `if: always()` steps

Systemd and launchd workflows must contain dedicated cleanup steps with:

```yaml
if: always()
```

Cleanup must attempt, in order:

- stop/bootout the service;
- disable or unload the release test service;
- terminate remaining candidate processes;
- remove installed candidate binary only where the test contract permits;
- restore or remove unit/plist files created by the test;
- remove temporary roots and run marker;
- verify port release;
- record final service state;
- record cleanup result.

Cleanup failures must be visible and prevent a qualifying pass. Preserve the original gate failure and cleanup failure separately.

### G4. Capture diagnostics on failure

On systemd failure, upload:

- `systemctl status`;
- relevant `journalctl` excerpt bounded to the current run;
- unit file and checksum;
- process listing filtered to Gregg;
- port ownership.

On launchd failure, upload:

- `launchctl print` output;
- plist and checksum;
- process listing filtered to Gregg;
- relevant bounded unified-log excerpt where available and safe;
- port ownership.

Do not upload secrets or broad host logs.

### G5. Prove repeatability

Add a protected smoke procedure that runs lifecycle setup and cleanup twice against the same candidate package and requires both passes to succeed without manual intervention.

The qualifying full lifecycle run may incorporate this by exercising repeated stop/start and then verifying the host returns to the documented clean baseline.

### G acceptance criteria

1. Protected jobs detect stale service, process, binary, port, and marker state.
2. Concurrent qualifying runs are prevented.
3. Cleanup runs with `if: always()`.
4. Cleanup failure is release-blocking.
5. Failure diagnostics are retained.
6. The same host can rerun the candidate without manual cleanup.
7. Final host state matches the documented baseline.
