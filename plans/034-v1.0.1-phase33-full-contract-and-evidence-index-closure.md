## Governing invariants

1. **A registry lockfile checksum is mandatory.** Boundary-2 cannot pass with a null or omitted protocol checksum in any mode.
2. **Qualification uses registry semantics, not directory-source semantics.** The local fixture must produce the same lockfile fields used for crates.io verification: package name, exact version, registry source, and checksum.
3. **Observed checksum equality is unconditional.** The parsed lockfile checksum must equal the validated registry-record checksum before build or publication authorization succeeds.
4. **Every declared evidence file exists.** Candidate generation may not advertise a path that is absent, outside the artifact root, empty where prohibited, or inconsistent with its recorded digest and size.
5. **Evidence indices are material objects.** A named index must be created, validated, uploaded, and independently replayable.
6. **Qualification requirements come from the production contract.** The harness must load the checked-in requirements file and may not substitute reduced ad hoc stage lists.
7. **Synthetic evidence proves orchestration, not platform behavior.** Synthetic candidates may stand in for native/lifecycle/soak results, but every required logical stage and identity relationship must be represented.
8. **One stage binds to one exact GitHub artifact.** Artifact topology may group stages only where the dispatch contract and production workflow do so; ambiguity and duplicate containment fail.
9. **Singleton role materialization precedes aggregation.** Final aggregation consumes files resolved through the production role contract, not direct test-only paths.
10. **Qualification validation is independent.** The output validator owns a mandatory contract and cannot trust the driver's omissions.
11. **The summary is not the contract.** The driver reports what happened; a separately checked-in contract defines what must have happened.
12. **Exact-SHA qualification remains mandatory.** Any executable, workflow, script, schema, requirements, or fixture change invalidates prior hosted qualification.
13. **Documentation-only evidence recording is explicit.** The qualified implementation SHA and later evidence-recording commit are distinct fields.
14. **No publication occurs in Phase 34.** No tag is created and no crates.io state is mutated.
15. **Validation fails closed.** Null checksums, missing indices, missing stages, direct-path singleton bypasses, stale evidence, and ambiguous topology all exit nonzero.

## Workstream A: require genuine registry checksum semantics in Boundary 2

### A1. Remove missing-checksum success paths

Delete or prohibit all logic equivalent to:

```python
allow_missing_checksum=True
if lock_checksum is not None:
    compare_checksums()
```

`parse_lockfile_protocol()` must always require a lowercase 64-character checksum for `gregg-protocol 1.0.1`, regardless of whether the source is crates.io or a qualification-only local sparse registry.

`registry-reverify.py` must reject before build authorization when:

- the checksum field is missing;
- the checksum is null;
- the checksum is malformed;
- the checksum differs from the validated registry record;
- more than one matching package record exists;
- the matching record uses a path, git, or directory source;
- the source is not the explicitly supplied expected registry source.

The final result schema must require:

```json
{
  "protocol_registry_checksum": "<64 lowercase hex>",
  "lockfile_protocol_checksum": "<same 64 lowercase hex>",
  "checksum_match": true
}
```

`verification: pass` is invalid unless all three values exist and agree.

### A2. Implement a real local sparse-registry fixture

Replace directory source replacement with a loopback sparse registry that causes Cargo to write a registry source and checksum into the generated lockfile.

The fixture must provide at least:

- `config.json` with a loopback download URL;
- the correct sparse index path for `gregg-protocol`;
- one index record for `gregg-protocol 1.0.1`;
- the exact packaged protocol `.crate` bytes;
- the crate SHA-256 in the sparse index record;
- deterministic startup and shutdown;
- bounded request handling;
- no external network access;
- no credentials;
- no crates.io mutation.

Configure Cargo through an isolated temporary `CARGO_HOME`. Preferred shape:

```toml
[source.crates-io]
replace-with = "phase34-local-registry"

[source.phase34-local-registry]
registry = "sparse+http://127.0.0.1:<port>/"
```

The qualification invocation must supply the exact expected local sparse source. Production release jobs must continue to require the approved crates.io source. Fixture source acceptance must be unreachable unless an explicit qualification-only flag is present.

Do not use a directory source, path patch, vendored source, or prewritten lockfile as the positive checksum proof.

### A3. Preserve production source policy

`registry-reverify.py` should distinguish:

```text
production mode:
  expected source is approved crates.io sparse/index source

qualification mode:
  expected source is one exact loopback sparse URL supplied by the harness
```

Qualification mode must require all of:

- loopback host;
- `http` or `https` URL with no userinfo;
- explicit `--qualification-local-registry` flag;
- no path/directory source;
- no environment-provided arbitrary source;
- checksum-bearing lockfile record.

The production workflow validator must reject qualification-only flags in `.github/workflows/release-candidate.yml` and `.github/workflows/release-finalize.yml`.

### A4. Verify exact archive identity before and after

Continue to verify the Boundary-1 archive SHA-256 and size before unpacking and after every Cargo command. The command-evidence summary must record both identities and `unchanged: true`.

The selected archive must not be regenerated, repacked, normalized, or substituted during Boundary 2.

## Stop conditions

- Cargo cannot produce a checksum-bearing lockfile from the loopback sparse registry;
- checksum equality requires accepting a directory/path source;
- a required production stage cannot be represented without changing the release requirements;

- final aggregation succeeds only when bypassing role materialization;
- the independent validator cannot distinguish an omitted required output;
