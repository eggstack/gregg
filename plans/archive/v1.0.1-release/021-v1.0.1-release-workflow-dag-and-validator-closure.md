# Phase 21: `v1.0.1` release-workflow DAG and validator closure

## Objective

Make every advertised release dispatch stage executable and add deterministic validation that proves stage-to-job reachability rather than only checking that strings appear in the workflow.

## Baseline defect

At baseline `eab5fe2e1d8f4635bb09aaf4ba69e18375ff5671`:

- `.github/workflows/release-candidate.yml` exposes `mixed-fleet-sustained` in `workflow_dispatch.inputs.stage.options`;
- the `mixed-fleet-sustained` job declares `needs: [resolve, source-ci]`;
- the job requires `needs.source-ci.result == 'success'`;
- `source-ci.if` does not include `inputs.stage == 'mixed-fleet-sustained'`.

Therefore the sustained dispatch skips `source-ci`, and the sustained job cannot satisfy its own condition.

The existing workflow validator did not catch this because it validates textual presence and selected contracts, not the logical relationship among dispatch values, job conditions, and `needs` dependencies.

## Scope

### In scope

- `.github/workflows/release-candidate.yml`;
- the existing release-workflow validation script and its tests;
- any checked-in release stage requirements file located by:

```bash
rg -n 'mixed-fleet-sustained|protocol-prepublish' .github scripts plans -g '*.yml' -g '*.yaml' -g '*.json' -g '*.py'
```

- small documentation updates required to describe the corrected dispatch contract.

### Out of scope

- changing release stage names;
- removing required stages;
- changing evidence schemas;
- changing artifact names;
- implementing the actual sustained harness, which belongs to Phase 22;
- tagging or publishing.

## Required design

Use one explicit source of truth for the set of dispatch stages and their expected jobs. The validator may parse the YAML directly or use a checked-in machine-readable stage contract, but it must prove all of the following:

1. every dispatch option is known;
2. every required logical stage has a producer job;
3. the producer job can be selected by the corresponding dispatch value;
4. every required `needs` dependency can also run for that dispatch value, or is intentionally unconditional;
5. a skipped dependency cannot be required to report `success`;
6. no required stage is orphaned by mutually exclusive conditions;
7. no unknown dispatch option silently bypasses all release work.

Do not implement this as another collection of substring checks.

## Implementation steps

### Step 1: locate the current validator and requirements contract

Run:

```bash
rg -n 'release-candidate.yml|workflow_dispatch|mixed-fleet-sustained|source-ci' scripts .github plans
```

Record the exact validator path in the implementation notes. Reuse its test framework rather than creating a second independent validator.

### Step 2: add a failing regression fixture or mutation test

Add a test that represents the baseline broken condition:

```text
stage = mixed-fleet-sustained
source-ci.if excludes mixed-fleet-sustained
mixed-fleet-sustained.needs includes source-ci
mixed-fleet-sustained.if requires needs.source-ci.result == success
```

The validator must reject this graph with a diagnostic that names:

- dispatch stage `mixed-fleet-sustained`;
- dependent job `mixed-fleet-sustained`;
- blocking dependency `source-ci`;
- the incompatible condition.

A generic “workflow invalid” message is insufficient.

### Step 3: repair the workflow reachability defect

Preferred narrow fix:

```yaml
source-ci:
  if: ${{
    inputs.stage == 'protocol-prepublish' ||
    inputs.stage == 'binary-prepublish' ||
    inputs.stage == 'native-evidence' ||
    inputs.stage == 'mixed-fleet-client' ||
    inputs.stage == 'mixed-fleet-sustained'
  }}
```

Equivalent formatting is acceptable.

Do not remove `source-ci` from the sustained job merely to make it run unless the implementation demonstrates that the sustained stage intentionally does not require the standard source gate. The current release policy expects the source gate, so adding the missing dispatch condition is the default correction.

### Step 4: define a stage/job truth table

The validator test must include a table equivalent to:

| Dispatch value | Required selected jobs |
| --- | --- |
| `protocol-prepublish` | `resolve`, `source-ci`, protocol package jobs, aggregation appropriate to the stage |
| `protocol-index-check` | `resolve`, protocol index verification jobs |
| `binary-prepublish` | `resolve`, `source-ci`, binary package jobs, package evidence jobs |
| `native-evidence` | `resolve`, `source-ci`, native source/package jobs required by the workflow contract |
| `mixed-fleet-client` | `resolve`, `source-ci`, `mixed-fleet-client` |
| `mixed-fleet-sustained` | `resolve`, `source-ci`, `mixed-fleet-sustained` |
| `operational-evidence` | `resolve`, protected operational jobs when required package inputs are supplied |
| `postpublish-verify` | `resolve`, postpublication verification jobs |

Use the repository’s actual job names. Do not copy this table blindly if names differ.

### Step 5: validate dependency closure

For each required job selected by a stage:

1. recursively follow `needs`;
2. evaluate whether each dependency is unconditional or selected by the same dispatch value;
3. reject cycles;
4. reject references to nonexistent jobs;
5. reject a job that tests `needs.<job>.result == 'success'` when `<job>` is not reachable for the same dispatch.

The validator does not need to implement the full GitHub Actions expression language. It only needs a deliberately constrained parser for the expression patterns used by this repository. Unsupported patterns must fail closed with a diagnostic rather than being treated as reachable.

### Step 6: validate stage contract consistency

Compare the workflow dispatch options with the checked-in release requirements contract:

- missing required option: fail;
- extra undocumented option: fail;
- required logical stage with no job: fail;
- job emits a candidate stage not present in the release requirements: fail unless explicitly marked auxiliary;
- duplicate logical stage producers for the same dispatch path: fail unless the contract requires an architecture matrix and aggregation handles it explicitly.

### Step 7: add positive and negative tests

Minimum negative cases:

1. baseline sustained dependency defect;
2. missing `needs` job;
3. mutually exclusive dependency condition;
4. unknown dispatch option;
5. required stage removed from the workflow;
6. malformed or unsupported `if` expression;
7. dependency cycle;
8. job requiring success from a skipped dependency.

Minimum positive cases:

1. current corrected workflow;
2. unconditional dependency;
3. a matrix job where the logical stage intentionally has several native artifacts;
4. protected stage whose package input is a separate dispatch input rather than a same-run dependency.

## Smaller-model guardrails

- Change only the workflow, its validator, tests, and directly associated release documentation.
- Do not rename jobs or artifacts unless a test proves the current name is internally inconsistent.
- Do not weaken a job condition to `always()`.
- Do not use `continue-on-error` to bypass reachability failures.
- Do not claim the stage works from YAML inspection alone; run the validator tests.
- Keep the parser narrow and explicit. A 100-line constrained evaluator is preferable to an incomplete general expression evaluator.

## Validation commands

Run the exact existing validator command used by CI. Also run:

```bash
python3 -m unittest discover -s scripts -p 'test*.py'
cargo fmt --all -- --check
cargo test --workspace --all-targets --all-features
```

If the workflow validator has a dedicated command, include its complete output in the handoff notes.

A repository-owned nonpublishing dispatch may be run after the static tests pass. Use a nonrelease candidate SHA and stage `mixed-fleet-sustained`; confirm that `resolve`, `source-ci`, and `mixed-fleet-sustained` are selected. The Phase 22 harness may still fail until implemented, but the job must be reachable.

## Acceptance criteria

Phase 21 is complete only when all criteria are demonstrated:

1. `source-ci` is selected for `mixed-fleet-sustained`.
2. The sustained job’s `needs.source-ci.result == 'success'` condition can be satisfied.
3. Every dispatch option is represented in a tested stage/job truth table.
4. The validator recursively checks dependency closure.
5. The validator rejects a required-success dependency that is skipped for the same dispatch value.
6. The baseline broken workflow is covered by a regression test that fails before the fix and passes after it.
7. Missing jobs, dependency cycles, unknown stages, and unsupported conditions fail closed.
8. The validator compares the workflow with the release requirements contract.
9. The corrected checked-in workflow passes the validator.
10. No required release stage or native architecture lane is removed.
11. No release gate is weakened with `always()`, `continue-on-error`, or broad error masking.
12. The Python release-tooling test suite passes.
13. The workspace test suite passes.
14. A nonpublishing dispatch, when infrastructure is available, visibly selects `resolve`, `source-ci`, and `mixed-fleet-sustained` for the sustained stage.
