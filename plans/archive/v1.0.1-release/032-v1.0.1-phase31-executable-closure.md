# Phase 32: `v1.0.1` Phase-31 executable closure

## Objective

Close the remaining deterministic defects in the Phase 31 release-control implementation and prove that the corrected orchestration path is executable before Phase 30 freezes a release candidate.

This phase is intentionally narrow. It does not reopen the product and platform work owned by Phases 23 through 29. It repairs the concrete failures found after commit:

```text
c3260a024704186466917ffc65d2f148ccb9f099
```

At that baseline, Phase 31 has substantial implementation landed but is not complete. The sustained runner cannot complete its success path, postpublication candidate generation uses an invalid artifact schema, the `1.0.0` disposition describes `1.0.1`, dependent-package “re-verification” is only a checksum operation, final run selection is incorrectly required to exist inside the frozen candidate checkout, standalone manifest validation permits missing GitHub artifact identity, provenance file association still contains first-match fallbacks, and scheduler shutdown is inferred from channel closure rather than a joined task result.

Phase 32 supersedes Phase 31 only for these remaining closure defects. Preserve all correct Phase 31 behavior.

## Current defects to close

1. `scripts/run-mixed-fleet-sustained.py` reads `requested_secs` before assignment on the successful summary path.
2. Sustained validation is mostly inline, allowing unit tests to duplicate expressions instead of exercising production validation code.
3. `postpublish-verify` writes artifact entries with `artifact_id` but no required `role`, so candidate generation fails.
4. `1.0.0-disposition.json` is populated from crates.io `1.0.1` API responses.
5. Disposition validation checks only top-level crate keys and does not prove that every record describes version `1.0.0`.
6. Boundary-2 archive “re-verification” only recalculates the archive checksum and never resolves or builds against the published `gregg-protocol 1.0.1`.
7. The finalizer requires a selection file inside the immutable candidate checkout even though final postpublication run IDs cannot be known when that candidate is frozen.
8. `validate-manifest` treats `github_artifact` as optional, so a stored cross-run manifest can lose immutable artifact identity and still validate.
9. Provenance indexing falls back to the first `Cargo.lock` or first `.crate` under an artifact.
10. Sustained scheduler shutdown is inferred from receiver closure; the scheduler task is not joined and a panic can be misclassified as clean shutdown.
11. The synthetic final-mode test reproduces the incorrect `1.0.0` disposition and does not exercise the actual finalizer input materialization contract.
12. No immutable nonpublishing workflow run proves the corrected paths in GitHub Actions.

## Governing invariants

1. **Successful paths must be executed, not inferred.** A test suite that covers only rejection branches cannot qualify a release runner.
2. **One schema per candidate artifact.** Every candidate artifact entry has a nonempty `name` and `role`; optional identity fields may supplement but never replace `role`.
3. **Version labels are semantic.** A file named `1.0.0-disposition.json` must contain only verified `1.0.0` records.
4. **Boundary 2 proves registry compatibility.** Recomputing an archive checksum is not dependency re-verification.
5. **The frozen candidate contains tooling, not future run data.** Selection data created after candidate freeze must be supplied as immutable external workflow input and recorded by digest.
6. **Cross-run manifests always carry immutable GitHub artifact identity.** Numeric artifact ID, exact artifact name, downloaded ZIP SHA-256, and downloaded ZIP size are mandatory for every selected stage.
7. **Current-run summaries are not release manifests.** They may exist before artifact upload IDs are assigned, but they cannot be accepted as cross-run release evidence.
8. **Provenance association is declarative.** Archive and lockfile ownership comes from package-specific provenance metadata, never traversal order.
9. **Clean shutdown is joined shutdown.** Channel closure alone is insufficient.
10. **No archive replacement across publication boundaries.** The exact Boundary-1 `.crate` bytes must be re-used at Boundary 2 and publication.
11. **Validation fails closed.** Ambiguity, missing evidence, unsupported schema, invalid version, stale input, task panic, and partial verification all exit nonzero.
12. **Phase completion requires GitHub-hosted evidence.** Local tests are necessary but not sufficient.

### A1. Correct initialization order

In `scripts/run-mixed-fleet-sustained.py`, derive all normalized runtime values before any summary validation:


### A2. Extract production validation functions

Create callable functions used by the runner and tests, for example:

```python

    summary: object,
    *,
    requested_secs: float,
    configured_endpoint_count: int,
```

Raise one typed exception, such as `SustainedEvidenceError`, and let `main()` convert it to one `FATAL:` message and exit status 1.

Tests must call these functions or invoke the actual runner subprocess. Tests that independently reimplement the same comparisons do not count.

### A3. Enforce the complete summary contract

Require all of the following:

- summary is an object;
- `requested_duration_secs` is numeric and equals configured duration;
- `observed_duration_secs` is numeric and at least requested duration;
- externally measured monotonic duration is at least requested duration;
- `endpoint_count` equals the configured endpoint count and is at least 3;
- `completed_generations >= 2`;
- `first_generation > 0`;
- `last_generation >= first_generation`;
- `completed_generations == last_generation - first_generation + 1`;
- `configured_max_concurrent_polls` equals the runner/workload contract value;
- `observed_max_concurrent_polls > 0`;
- `observed_max_concurrent_polls <= configured_max_concurrent_polls`;
- `online_results > 0`;
- `offline_results > 0`;
- `observed_transitions` is a nonempty array of nonempty strings;
- `clean_shutdown is true`;
- `panic_or_join_failure is null`;
- no boolean is accepted where an integer is required;
- NaN, infinity, negative values, and numeric strings are rejected.

### A4. Enforce the complete resource-sample contract

Require:

- at least the configured minimum sample count;
- every record is an object;
- sequential `sample_index` values starting at zero;
- one exact child PID across all samples;
- strictly increasing monotonic timestamps;
- positive RSS, virtual size, and thread count;
- `process_alive is true` for every retained sample;
- first sample occurs after process launch;
- last sample covers the documented minimum fraction of requested runtime;
- no sample occurs after the recorded workload completion timestamp;
- malformed JSONL fails rather than being skipped.

### A5. Execute the actual happy path

Add a test that launches the real compiled sustained workload through `run-mixed-fleet-sustained.py` with a bounded smoke duration. The test must reach successful summary and sample validation and return zero.

The smoke test may use a short duration such as 2–5 seconds, but it must still produce:

- at least two generations;
- online and offline results;
- at least one transition;
- positive observed concurrency;

Keep the full release duration controlled by the workflow input or release contract; the smoke test does not replace release evidence.

## Workstream B: positively join scheduler shutdown

### B1. Expose a narrow observed scheduler handle

Add a test-only or crate-private API that returns both the batch receiver and the scheduler task handle. Preferred shape:

```rust
pub(crate) struct SchedulerRunHandle {
    pub batches: mpsc::Receiver<PollBatch>,
    pub task: tokio::task::JoinHandle<Result<(), SchedulerRunError>>,
}
```

The existing production API may remain unchanged by wrapping the new internal primitive and discarding the handle only in production call sites that do not need it. Do not expand the public crate API without necessity.

The scheduler task should return a meaningful result rather than relying exclusively on sender drop.

### B2. Define clean shutdown precisely

The sustained workload must:

1. cancel the token;
2. prevent the scheduler from blocking forever on a full receiver channel;
3. await the scheduler `JoinHandle` under a bounded timeout;
4. set `clean_shutdown: true` only for `Ok(Ok(()))`;
5. record a diagnostic for scheduler error, join panic/cancellation, or timeout;
6. abort and await the task after timeout so no task leaks remain;
7. return a failing test result when shutdown is not clean.

Channel closure may be used as an additional assertion but not as the authoritative shutdown signal.

### B3. Required scheduler-shutdown tests

Add deterministic tests for:

- normal cancellation and joined success;
- scheduler returns an explicit error;
- scheduler task panics;
- scheduler does not stop before the timeout;
- receiver is dropped while a send is pending;
- no active poll observer guards remain after joined shutdown;
- no fixture child process remains alive after the workload test.

### Workstream B acceptance criteria

- [ ] The sustained workload receives a real scheduler task handle.
- [ ] `clean_shutdown` derives from the joined task result.
- [ ] A closed batch channel cannot by itself produce `clean_shutdown: true`.
- [ ] Panic, cancellation error, explicit scheduler error, and timeout are distinguishable diagnostics.
- [ ] Timeout cleanup aborts and awaits the task.
- [ ] All B3 tests pass under Tokio’s current-thread test runtime.
- [ ] Normal production scheduler behavior and public interfaces remain compatible.
