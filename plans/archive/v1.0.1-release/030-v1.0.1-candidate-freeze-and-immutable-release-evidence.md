# Phase 30: `v1.0.1` candidate freeze and immutable release evidence

## Objective

Freeze one corrected commit SHA, execute every required source, native, package-native, sustained, lifecycle, resource, soak, publication, and postpublication gate against that exact candidate, then reconcile the final evidence ledger using immutable GitHub and crates.io identities.

This is an execution plan, not an implementation phase. Do not change product code after candidate freeze. Any required source change invalidates the candidate and restarts this phase from the beginning with a new SHA.

## Dependencies

Phases 21 through 29 must be complete with their acceptance evidence before this phase starts.

At minimum, confirm:

- release stage DAG and semantic validator are correct;
- sustained workload evidence is live and nonempty;
- macOS counter conversion is correct on Intel and ARM64;
- readiness and freshness semantics are correct;
- endpoint/config validation is canonical;
- macOS package runs as an unprivileged service identity;
- ordinary and MSRV CI cover all four native architectures;
- bounded scheduler optimization has preserved semantics;
- daemon response caching and runtime-latency decision are complete.

## Governing release invariants

1. **One full candidate SHA:** every run, job, candidate record, package provenance record, and final manifest identifies the same lowercase 40-character commit SHA.
2. **No mutable references:** use the full candidate SHA or the final annotated tag where explicitly required. Do not qualify `main`, a short SHA, or a moving branch.
3. **One version:** workspace and all three crates identify version `1.0.1` before freeze.
4. **Clean tree:** the frozen candidate has no uncommitted or generated source changes.
5. **Run identity:** record GitHub workflow run ID and attempt separately.
6. **Artifact identity:** record numeric GitHub artifact ID, exact artifact name, ZIP SHA-256, and ZIP size separately.
7. **Native execution:** architecture claims require native runner execution.
8. **Package execution:** package-native claims require installation from the verified `.crate` artifact and its recorded lockfile/provenance, not a source build.
9. **Cleanup fails closed:** protected-host cleanup failure invalidates the qualifying job.
10. **Tag immutability:** create one annotated `v1.0.1` tag; never move or replace it after publication.
11. **Ordered publication:** publish the protocol crate first, verify index availability, then publish dependent binaries in the documented order.
12. **Registry verification:** final claims use fresh installations from crates.io, not local package archives.
13. **Evidence completeness:** no prose statement substitutes for a required run, artifact, checksum, native lifecycle record, or registry result.
14. **Retry transparency:** every rerun records a new attempt and the final selection identifies the chosen attempt explicitly.

## Scope

### In scope

- final local and CI qualification;
- immutable candidate selection;
- release workflow dispatches;
- protected host lifecycle/resource/soak jobs;
- pre-tag aggregation;
- annotated tag creation and verification;
- ordered crates.io publication;
- postpublication installation and verification;
- final aggregation;
- `plans/v1.0.1-final-evidence.md` reconciliation;
- plan registry status updates and release notes.

### Out of scope

- product code changes after freeze;
- adding new release stages;
- changing evidence requirements to fit available results;
- moving the version to `1.0.2` without a separate decision;
- retrospective recreation of missing artifact IDs from filenames;
- yanking or replacing `1.0.0` unless separately justified.

## Step 1: pre-freeze repository qualification

Run the complete local gate on the proposed candidate:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-targets --all-features
cargo doc --workspace --no-deps
python3 -m unittest discover -s scripts -p 'test*.py'
for script in scripts/*.sh packaging/*.sh; do bash -n "$script"; done
shellcheck scripts/*.sh packaging/*.sh
```

Run all existing release workflow validators and package checks, including:

```bash
cargo package -p gregg-protocol --allow-dirty
cargo package -p greggd --allow-dirty
cargo package -p gregg --allow-dirty
```

Use the repository’s stricter checked-in commands where they exist. `--allow-dirty` is shown only for local package inspection; the frozen candidate itself must be clean.

Confirm:

- `Cargo.lock` is present and committed;
- package manifests use exact intended `1.0.1` dependency versions;
- README, changelog, architecture docs, and install paths describe the corrected behavior;
- `plans/README.md` marks Phase 20 active and phases 21–29 complete only where evidence exists;
- no `TODO`, ignored failure, or temporary duration override weakens a release gate.

## Step 2: qualify ordinary CI on the proposed candidate

Push the proposed candidate and require one ordinary CI run in which all jobs use the same SHA.

Required stable jobs:

- Linux x86-64;
- Linux ARM64;
- macOS Intel x86-64;
- macOS Apple Silicon ARM64.

Required MSRV jobs:

- Rust 1.75 Linux x86-64;
- Rust 1.75 Linux ARM64;
- Rust 1.75 macOS Intel;
- Rust 1.75 macOS ARM64.

Record:

- workflow name;
- run ID;
- attempt;
- candidate SHA;
- every job name and conclusion;
- runner OS/architecture evidence.

A green run against an earlier commit does not qualify.

## Step 3: freeze the candidate

After local and ordinary CI qualification:

```bash
git rev-parse HEAD
git status --porcelain
git show -s --format='%H%n%ct%n%s' HEAD
```

Record the full SHA in:

- the release selection input;
- the evidence ledger’s candidate field;
- operator notes.

From this point:

- do not amend the commit;
- do not merge additional changes into the candidate;
- do not use a branch name as a release input;
- do not tag yet.

If any subsequent pre-tag gate exposes a source defect, abandon this candidate, implement the correction in a new commit, rerun Steps 1–3, and use the new SHA everywhere.

## Step 4: execute prepublication stages

Dispatch release stages in the repository-defined order. The expected high-level sequence is:

1. `protocol-prepublish`;
2. `protocol-index-check` where the workflow uses a pre-existing published protocol dependency or dry-run index contract;
3. `binary-prepublish`;
4. `native-evidence`;
5. `mixed-fleet-client`;
6. `mixed-fleet-sustained`;
7. `operational-evidence`.

Follow the actual corrected workflow contract from Phase 21. Do not invent same-run dependencies where selected prior run IDs are required.

For every dispatch, record immediately:

- candidate ref supplied;
- stage supplied;
- package run ID/attempt inputs, if any;
- workflow run ID;
- run attempt;
- job conclusions;
- artifact names;
- numeric artifact IDs;
- artifact creation and expiration timestamps.

## Step 5: validate source and package provenance

For every produced package artifact:

- download the artifact through the checked-in retrieval tooling;
- record GitHub-reported size;
- record downloaded ZIP size;
- calculate ZIP SHA-256;
- safely extract it;
- validate every `candidate.json`;
- validate package provenance;
- validate the package-specific lockfile;
- validate `.crate` archive SHA-256 and size;
- verify package name/version/candidate SHA;
- ensure `gregg-protocol`, `greggd`, and `gregg` records remain distinct.

Do not use `find -print -quit` or another filesystem heuristic to choose among ambiguous package files. The selected artifact contract must identify deterministic paths.

## Step 6: validate all native evidence

Required source-native and package-native architecture evidence:

| Target | Source-native | Package-native |
| --- | --- | --- |
| Linux x86-64 | required | required |
| Linux ARM64 | required | required |
| macOS Intel x86-64 | required | required |
| macOS Apple Silicon ARM64 | required | required |

Each native record must include:

- candidate SHA;
- release version;
- workflow run ID and attempt;
- job name;
- runner OS and observed architecture;
- source or package identity mode;
- binary/package checksum where applicable;
- test command and conclusion;
- start and completion timestamps.

macOS evidence must include the corrected unsigned Mach counter smoke and recovery behavior. Linux ARM64 must be native, not cross-compiled.

## Step 7: validate sustained mixed-fleet evidence

The selected `mixed-fleet-sustained` artifact must contain and validate:

- requested duration;
- observed live workload duration;
- completed generations;
- endpoint count;
- online and offline/error outcomes;
- observed transition count;
- maximum active poll count;
- nonempty resource sample count;
- monotonic sample timestamps;
- target PID identity;
- clean shutdown result.

Reject the artifact if:

- compilation time is included in the measured interval;
- no target process was sampled;
- the resource file is empty;
- the last sample occurs before the required fraction of runtime;
- any generation omits an endpoint;
- evidence records only configured duration and not observed duration.

## Step 8: execute protected operational evidence

Use the selected verified package artifacts on protected hosts.

Required operational categories:

- package installation verification;
- daemon start/readiness/status;
- restart and stop;
- systemd lifecycle on Linux;
- launchd lifecycle on macOS;
- effective service identity;
- listener address;
- resource budget;
- qualifying soak duration;
- cleanup and post-cleanup verification.

Protected jobs must:

- run only after preflight passes;
- identify the package run ID/attempt consumed;
- record package and binary provenance;
- use bounded startup, readiness, shutdown, and cleanup deadlines;
- execute cleanup under `if: always()` or equivalent;
- fail the job when cleanup fails;
- preserve both original and cleanup diagnostics when both fail.

macOS evidence must prove the daemon effective UID is the dedicated nonroot account. Linux evidence must prove the systemd service uses the dedicated `greggd` account and hardening unit.

## Step 9: perform pre-tag aggregation

Run the finalizer in **pre-tag mode** against a reviewed run-selection file.

Pre-tag aggregation must require all prepublication evidence and must not require:

- annotated tag identity;
- crates.io publication disposition;
- postpublication artifacts;
- final registry installation results.

The generated pre-tag manifest must include:

- candidate SHA/version/tooling SHA;
- selected workflow run IDs and attempts;
- numeric artifact IDs;
- artifact names and ZIP digests;
- every required logical stage exactly once or according to matrix cardinality;
- package provenance and lockfile identities;
- native architecture evidence;
- sustained/lifecycle/resource/soak evidence;
- no unresolved placeholders.

Run negative validation by removing one mandatory stage from a copy of the selection. The finalizer must reject it deterministically.

Do not create the tag until the valid pre-tag manifest is archived and reviewed.

## Step 10: create and verify the annotated tag

Create exactly one annotated tag:

```bash
git tag -a v1.0.1 <candidate-sha> -m 'gregg v1.0.1'
git cat-file -t v1.0.1
git rev-parse 'v1.0.1^{tag}'
git rev-parse 'v1.0.1^{commit}'
```

Verify:

- object type is `tag`;
- peeled commit equals the frozen candidate SHA;
- tagger timestamp and message are captured;
- tag-object SHA is distinct from the peeled commit SHA;
- repository state remains unchanged.

Push the tag once. Never force-update it.

If tag verification fails before publication, stop and correct the release procedure. Do not reuse a malformed tag name without an explicit recovery decision.

## Step 11: publish in dependency order

Publish using verified candidate package contents and the repository’s release scripts.

Required order:

1. `gregg-protocol 1.0.1`;
2. wait for and verify crates.io index/API availability;
3. `greggd 1.0.1`;
4. `gregg 1.0.1`.

Before each publish:

- compare packaged archive checksum with pre-tag provenance;
- verify candidate and tag identity;
- verify the crate/version is not already published unexpectedly;
- verify dependencies resolve to the intended `1.0.1` protocol version;
- record command start/completion and disposition.

After each publish:

- record crates.io package/version identity;
- record API/index observation timestamp;
- record checksum where exposed by the verification tooling;
- do not republish or overwrite.

A partial publication must be recorded honestly. Do not mark the release complete until all required crates and postpublication gates succeed.

## Step 12: execute postpublication verification

Dispatch `postpublish-verify` against the annotated tag/candidate according to the corrected workflow.

Use clean temporary roots and registry installations:

```text
cargo install greggd --version 1.0.1 --locked --root <clean-root>
cargo install gregg --version 1.0.1 --locked --root <clean-root>
```

Use the project’s verified install scripts when stricter provenance checking is available.

Verify:

- binaries report version `1.0.1`;
- installed package source is crates.io;
- lockfile behavior matches release policy;
- `greggd` starts and serves valid schema data;
- `gregg` can poll the installed daemon;
- native architecture and package identity are recorded;
- no local source path or target directory is used.

Required registry-native coverage must follow the release requirements contract. At minimum include supported Linux and macOS package behavior where the workflow provides native runners.

## Step 13: final aggregation

Run the finalizer in **final mode** with:

- the reviewed prepublication run selection;
- annotated tag identity;
- publication disposition records;
- postpublication workflow run/artifacts;
- registry-install verification;
- immutable finalizer tooling SHA.

Final aggregation must reject:

- missing postpublication stage;
- mismatched candidate/tag commit;
- short SHA;
- missing tag-object SHA;
- missing package provenance;
- missing numeric artifact ID;
- artifact ZIP digest mismatch;
- mixed run attempts not selected explicitly;
- stale or expired artifact without downloaded digest evidence;
- missing native architecture;
- missing sustained/resource/soak evidence;
- root-run macOS lifecycle evidence;
- crates.io version mismatch;
- mutable tooling identity.

The final manifest must validate independently after being copied to a clean directory with only its declared evidence inputs.

## Step 14: reconcile the evidence ledger

Update `plans/v1.0.1-final-evidence.md` only after final aggregation succeeds.

Replace placeholders with precise fields:

- frozen candidate SHA;
- ordinary CI run ID and attempt;
- release run IDs and attempts by stage;
- selected job names/conclusions;
- numeric artifact IDs and exact names;
- ZIP SHA-256 values and sizes;
- native target evidence;
- package-native evidence;
- protected lifecycle/resource/soak evidence;
- pre-tag manifest checksum;
- annotated tag-object SHA;
- peeled commit SHA;
- crates.io publication identities and timestamps;
- postpublication run/artifacts;
- final manifest path/checksum/tooling SHA.

Do not place a commit abbreviation in a workflow-run field. Do not place an artifact filename in an artifact-ID field.

Update `plans/README.md` statuses:

- Phase 20 roadmap: complete;
- Phases 21–29: complete only with linked evidence;
- Phase 30: complete;
- `v1.0.1`: released and verified.

## Step 15: final independent verification

A second operator or review agent must verify:

1. candidate SHA consistency across all manifests;
2. tag-object and peeled-commit identity;
3. crates.io versions are publicly retrievable;
4. final artifact IDs resolve to the recorded runs;
5. ZIP digests match downloaded artifacts;
6. all four native architecture categories exist;
7. package-native evidence is distinct from source-native evidence;
8. sustained evidence contains live nonempty samples;
9. protected cleanup succeeded;
10. final manifest validator passes from clean inputs;
11. ledger fields use the correct identifier types;
12. no release plan is marked complete solely by source inspection.

Record reviewer identity/date and disposition.

## Smaller-model execution protocol

This phase is long. Assign one bounded subtask at a time:

1. pre-freeze local/CI qualification;
2. candidate freeze record;
3. one workflow stage dispatch and artifact capture;
4. native matrix review;
5. sustained artifact review;
6. protected operational review;
7. pre-tag aggregation;
8. tag creation/verification;
9. one crate publication step;
10. postpublication verification;
11. final aggregation;
12. ledger reconciliation;
13. independent review.

Each subtask must return a structured handoff containing inputs, immutable identifiers, results, and blockers. The coordinating agent must not infer missing IDs from prose.

## Stop conditions

Stop the release immediately when:

- candidate SHA differs anywhere;
- a required job is skipped;
- a required artifact is absent or ambiguous;
- candidate metadata inside an artifact mismatches;
- a native runner reports the wrong architecture;
- resource/sustained evidence is empty;
- package-native installation uses a source build;
- protected cleanup fails;
- the tag does not peel to the candidate;
- publication order is violated;
- crates.io returns a conflicting existing version;
- finalizer tooling is mutable or unidentified;
- the final manifest validator fails.

Do not weaken validation or edit evidence to continue. Correct the underlying problem and restart from the earliest invalidated step.

## Acceptance criteria

Phase 30 is complete only when all criteria are demonstrated:

1. One full immutable candidate SHA is selected after complete local and four-architecture CI qualification.
2. No source change occurs after freeze.
3. Every required release dispatch stage runs and succeeds for that SHA.
4. Every selected run records its run ID and attempt.
5. Every selected artifact records its numeric ID, exact name, ZIP SHA-256, and size.
6. Every contained candidate record validates against the same SHA/version.
7. Source-native and package-native evidence exists for all four advertised architectures.
8. The sustained stage proves live duration, complete generations, transitions, and nonempty resource samples.
9. Protected Linux and macOS lifecycle/resource/soak gates pass and clean up fully.
10. macOS package evidence proves nonroot service execution.
11. Pre-tag aggregation succeeds and rejects a deliberately incomplete selection.
12. `v1.0.1` is an annotated tag whose peeled commit equals the candidate SHA.
13. Protocol and binary crates are published in the required order.
14. crates.io reports all three `1.0.1` packages.
15. Fresh registry installations pass version, daemon, protocol, and client checks.
16. Postpublication workflow evidence is complete.
17. Final aggregation succeeds with immutable tooling identity.
18. Final manifest validates independently from clean declared inputs.
19. The final evidence ledger contains correct immutable identifiers in correctly named fields.
20. The plans index accurately marks completed phases and release status.
21. An independent reviewer verifies the final evidence and records approval.
22. No required criterion is satisfied only by source inspection, short SHA, semantic artifact label, or prose assertion.
