# Phase 15: version 1.0.1 release-gate corrective execution

## Objective

Correct the remaining defects in the Phase 14 release machinery, execute every outstanding native and operational gate against one immutable candidate commit, and complete a traceable `1.0.1` release of `gregg-protocol`, `greggd`, and `gregg`.

The implementation baseline for this plan is:

```text
a1d2688ed906d18e78a4a8e6c3fb6be2a62e474b
```

Phases 11 through 14 have already corrected the substantive application defects discovered after `1.0.0`, including:

- Darwin ABI layout and Mach-port ownership;
- daemon pre-bind, stale policy, ordered sampler updates, and abnormal-exit cleanup;
- client endpoint persistence, cross-process locking, and transactional editing;
- scheduler generation and cadence behavior;
- strict response-size enforcement;
- installer path resolution and non-root systemd identity;
- launchd domain/service-target construction and state-aware stop behavior;
- bounded native macOS retry behavior;
- secure client config mode intent;
- immutable candidate-ref resolution foundations;
- a first installed-daemon verification script.

Preserve those changes. This phase is a narrowly scoped release-gate corrective pass, not another application redesign.

## Current release disposition

At the baseline commit:

- workspace source is versioned `1.0.1`;
- no `v1.0.1` tag resolves;
- crates.io contains only unyanked `1.0.0` releases of all three crates;
- the installed-daemon verifier writes a TOML schema that `greggd` rejects;
- the verifier does not itself install the package and does not check the child process exit status after SIGTERM;
- client config permission changes ignore permission-setting failures and write the edit copy before enforcing mode `0600`;
- launchd stop implementation is state-aware, but the added tests do not execute the state machine through an injectable command runner;
- binary package verification still follows protocol package construction rather than actual publication and crates.io indexing of `gregg-protocol 1.0.1`;
- binary MSRV jobs have the same unpublished-registry dependency problem;
- Linux ARM64, native systemd, native launchd, resource, macOS soak, and mixed-fleet soak gates are absent or unexecuted;
- release jobs do not upload durable artifacts;
- no postpublication registry-install verification exists;
- the evidence document contains prospective or contradictory claims and no frozen SHA, run IDs, artifact IDs, tag SHA, or `1.0.1` registry records.

`1.0.1` remains an unfrozen source candidate. Phase 15 must not mark completion until release execution and evidence are complete.

## Scope

### P0 correctness

- Make the installed-daemon verifier use the real `greggd` configuration contract.
- Verify daemon termination through the child exit status.
- Make client configuration permission enforcement fail closed.
- Create sensitive temporary files with secure permissions before writing content.
- Add executable launchd state-machine tests through an injectable command runner.

### P0 release workflow

- Separate protocol prepublication verification from protocol publication/indexing.
- Block binary and binary-MSRV verification until registry `gregg-protocol 1.0.1` is proven available.
- Add durable artifacts and an aggregate candidate manifest.
- Add Linux ARM64 and explicit operational-evidence paths.
- Add postpublication registry-install verification.

### P0 release execution

- Freeze one exact source SHA.
- Run all stable, MSRV, package, native, lifecycle, resource, soak, and dependency gates against that SHA.
- Decide the disposition of `1.0.0`.
- Create and verify an annotated `v1.0.1` tag.
- Publish crates in dependency order.
- Verify registry packages, checksums, installs, and runtime behavior.
- Reconcile evidence and registry status without altering tagged release source.

### Non-goals

Do not add:

- new metrics, wire fields, HTTP endpoints, or CLI commands;
- TLS, authentication, discovery, history, alerting, or public-internet serving;
- Windows support;
- a new configuration or service-management framework;
- general deployment automation beyond the three existing crates;
- unrelated dependency upgrades or cosmetic refactors;
- bypasses such as `--allow-dirty`, `--no-verify`, `|| true`, cross-compilation presented as native evidence, or source inspection presented as runtime evidence.

## Workstream A: repair installed-daemon verification

### A1. Generate a valid daemon configuration

`scripts/verify-installed-daemon.sh` must write the flat `greggd` configuration schema actually accepted by `crates/greggd/src/config.rs`.

Use a configuration equivalent to:

```toml
name = "loopback-test"
host = "127.0.0.1"
port = 43123
sample_interval_ms = 1000
stale_after_ms = 10000
```

Do not write:

```toml
[server]
port = 43123
refresh_ms = 1000

[[systems]]
name = "loopback-test"
```

Required properties:

- all field names match the daemon `Config` struct exactly;
- unknown sections and client-only `systems` entries are absent;
- the selected host is loopback-only;
- sample and stale intervals satisfy validation;
- the script prints the effective config on failure, while avoiding unrelated sensitive content.

### A2. Make the package-install boundary explicit

The verification script should verify a supplied binary. The workflow must be responsible for installing that binary from the unpacked `.crate` source into a clean root.

Required binary-package flow:

1. unpack `target/package/greggd-1.0.1.crate` into an empty directory;
2. install from that unpacked package into an empty `--root`;
3. pass exactly `<root>/bin/greggd` to `verify-installed-daemon.sh`;
4. record the installed binary SHA-256 and size;
5. avoid falling back to `target/release/greggd` in package-verification jobs.

The native source jobs may also run the verifier against a release build, but that is separate evidence and must be labelled accordingly.

### A3. Verify clean child termination

After sending SIGTERM:

- wait for the process with the shell `wait` builtin;
- capture its exit status;
- require the expected successful status;
- report stdout/stderr if the process exits nonzero;
- fail if shutdown exceeds the deadline;
- after forced SIGKILL, reap the child before exiting;
- ensure the EXIT trap does not mask the original failure.

Acceptable pattern:

```bash
kill -TERM "$GREGGD_PID"
if ! wait_for_exit "$GREGGD_PID" "$MAX_WAIT"; then
    kill -KILL "$GREGGD_PID" || true
    wait "$GREGGD_PID" || true
    die "greggd did not terminate within deadline"
fi

set +e
wait "$GREGGD_PID"
status=$?
set -e
[ "$status" -eq 0 ] || die "greggd exited with status $status"
GREGGD_PID=""
```

Adjust for shell semantics so the process is not reaped twice.

### A4. Validate HTTP behavior robustly

The verifier must:

- check required tools (`curl`, `jq`, and either `python3` or a documented port allocator);
- choose an isolated port with bounded collision handling;
- wait for readiness with a monotonic bounded deadline;
- distinguish connection failure, warming response, and malformed response;
- require `/healthz` to return the documented success status;
- query `/v1/status` and validate schema version and required fields;
- verify `system.architecture`, `system.hostname`, and positive logical core count;
- verify finite, bounded percentage values where the protocol requires them;
- print daemon logs on all failure paths;
- clean temporary files and processes on success and failure.

### A5. Add tests for the verifier

Add a lightweight shell or integration test suite covering:

- generated config parses through `greggd`;
- invalid binary path fails;
- child exits during startup and logs are shown;
- health timeout fails;
- malformed status JSON fails;
- nonzero shutdown exit fails;
- successful real-daemon path passes;
- shellcheck passes.

Where practical, use a tiny fake HTTP child to exercise failure paths deterministically, while retaining one real `greggd` test.

### A acceptance criteria

1. The verifier-generated TOML parses and validates as `greggd::config::Config`.
2. An installed package binary reaches `/healthz` and `/v1/status` successfully.
3. A daemon exiting nonzero after SIGTERM fails the verifier.
4. Startup and shutdown are both bounded.
5. No `|| true` masks a release-gate failure.
6. Failure output includes the daemon log and actionable context.
7. The workflow distinguishes package-installed and source-built verifier runs.

## Workstream B: make config permissions fail closed

### B1. Create the atomic replacement securely before writing

On Unix, create the atomic replacement using explicit mode `0600` before any configuration bytes are written.

Preferred implementation:

```rust
use std::os::unix::fs::OpenOptionsExt;

let mut file = OpenOptions::new()
    .write(true)
    .create_new(true)
    .mode(0o600)
    .open(&temp_path)?;
```

Requirements:

- do not use `fs::write` for sensitive atomic temporary files on Unix;
- do not rely only on the process umask;
- write, flush, and `sync_all` after secure creation;
- rename within the same directory;
- sync the parent directory;
- preserve the existing cleanup behavior on error.

### B2. Make permission errors fatal

Remove ignored results such as:

```rust
let _ = file.set_permissions(...);
let _ = fs::set_permissions(path, ...);
```

Every required permission operation must map to `ConfigError::AtomicWrite` or a dedicated permission error and abort the write.

If the replacement is created with `0600`, an additional post-rename chmod may be retained as defense in depth, but its failure must be returned rather than ignored.

### B3. Secure the editor copy before content is written

`edit_transaction()` must create its editor-visible temporary file securely before serializing the current configuration into it.

Required order:

1. acquire in-process and cross-process locks;
2. create the editor temp file with `0600` atomically;
3. write current config bytes;
4. flush and close as needed for the editor;
5. invoke editor;
6. parse and validate edited content;
7. commit through the fail-closed atomic writer;
8. remove the editor temp file on all paths.

Do not write through `fs::write` and chmod afterward.

### B4. Permission tests

Add Unix tests proving:

- new config is `0600` under a permissive umask;
- atomic rewrites remain `0600`;
- `add`, `remove`, `refresh`, and `edit` preserve `0600`;
- editor temp mode is already `0600` when the editor callback begins;
- invalid edit preserves original bytes and mode;
- editor failure preserves original bytes and mode;
- injected permission-setting failure is returned;
- a successful write cannot be reported when the final secure mode was not established.

Use an injectable file-operations layer or narrowly scoped test hook for deterministic chmod failure; do not make the production API broadly abstract.

### B acceptance criteria

1. Sensitive temporary files are never created with broader permissions before content is written.
2. Required chmod or secure-open failures propagate.
3. Successful client writes always leave mode `0600` on Unix.
4. Invalid and failed edits preserve both bytes and mode.
5. Cross-process locking and atomic durability remain intact.

## Workstream C: make launchd state behavior executable in tests

The production `stop()` logic is now state-aware, but current unit tests mostly inspect argument builders and comments rather than executing state transitions.

### C1. Introduce a narrow command-runner seam

Define a private or crate-private runner abstraction that can execute `launchctl` and return captured status/stdout/stderr.

Example shape:

```rust
trait LaunchctlRunner {
    fn output(&self, args: &[&str]) -> io::Result<Output>;
}
```

Production uses `std::process::Command`; tests use a scripted fake runner.

Keep the public `ServiceManager` surface unchanged.

### C2. Test actual state transitions

With the fake runner, prove:

- `NotLoaded` stop performs one `print`, zero `bootout`, and succeeds;
- `Loaded` stop performs one `print`, one `bootout`, and succeeds;
- `Running` stop performs one `print`, one `bootout`, and succeeds;
- state-query permission error propagates without `bootout`;
- bootout error propagates;
- two consecutive stops succeed and the second performs no `bootout`;
- start after stop performs `print` then `bootstrap system <plist>`;
- restart from running performs `print`, `bootout`, then `bootstrap`;
- command arrays remain exact and paths with spaces remain one argument.

### C3. Preserve native validation requirement

These tests close deterministic source behavior only. A real macOS launchd lifecycle transcript remains mandatory before release.

### C acceptance criteria

1. Unit tests execute the service state machine rather than merely inspect helper arrays.
2. Idempotency and error propagation are proven deterministically.
3. Production command invocation remains argument-array based.
4. Native launchd validation remains an explicit release gate.

## Workstream D: split the release workflow around real registry state

### D1. Replace pseudo-staging with explicit stages

The workflow must not run binary package or binary MSRV jobs merely because protocol packaging succeeded locally.

Use either separate workflows or a required `stage` input with at least:

- `protocol-prepublish`
- `protocol-index-check`
- `binary-prepublish`
- `native-evidence`
- `operational-evidence`
- `postpublish-verify`

A monolithic `full` stage is allowed only after all registry prerequisites are already satisfied. It must fail clearly when they are not.

### D2. Protocol prepublication stage

Against the frozen candidate SHA:

1. verify candidate metadata and clean checkout;
2. run source CI;
3. package `gregg-protocol 1.0.1` without bypass flags;
4. locate `target/package/gregg-protocol-1.0.1.crate`;
5. calculate SHA-256;
6. unpack and inspect normalized manifest;
7. build and test unpacked source under stable;
8. build unpacked source under Rust 1.75;
9. build a clean external consumer against the package or a local registry representation;
10. upload all artifacts.

This stage must not attempt `greggd` or `gregg` package verification.

### D3. Human-authorized protocol publication

After all prepublication and required native gates that policy places before publication:

- publish `gregg-protocol 1.0.1` from the frozen source;
- record command, actor, timestamp, and output;
- wait for crates.io index availability;
- record registry checksum and published timestamp;
- verify the version is not yanked;
- build a clean consumer that resolves the crates.io copy.

Publication credentials must not be exposed in artifacts or logs.

### D4. Protocol index gate

Create a job or script that fails unless registry `gregg-protocol 1.0.1` is resolvable.

It must record:

- registry/index source queried;
- version;
- checksum;
- publication timestamp where available;
- yank state;
- clean consumer resolution output.

Binary jobs must depend on this gate, not on the protocol package job.

### D5. Binary prepublication stage

Only after the index gate passes, package `greggd` and `gregg`.

For each crate:

1. run `cargo package --list`;
2. run verified `cargo package`;
3. locate exact archive under `target/package`;
4. calculate SHA-256;
5. unpack into an empty directory;
6. inspect normalized manifest and included files;
7. prove `gregg-protocol 1.0.1` resolves from crates.io rather than the workspace path;
8. build and test unpacked source under stable;
9. build unpacked source under Rust 1.75;
10. install into an empty root;
11. run `--help` and `--version` where supported;
12. run installed-daemon and installed-client functional smokes;
13. upload artifacts.

### D6. Correct MSRV sequencing

Split MSRV jobs similarly:

- protocol package MSRV may run before publication;
- binary package MSRV must wait for the indexed protocol dependency;
- record the resolved dependency graph and lockfile behavior;
- do not silently omit `--locked` or silently generate a different graph without recording it;
- where packaged source lacks a usable lockfile, document the deterministic resolution method and archive its generated lockfile.

### D acceptance criteria

1. Binary package jobs cannot start before indexed protocol `1.0.1` is proven.
2. Binary MSRV jobs use the same registry prerequisite.
3. Protocol prepublication can pass independently.
4. Every package is verified from unpacked source.
5. Installed binary tests use clean package-install roots.
6. Registry dependency resolution is demonstrated explicitly.
7. No release job depends on an unpublished workspace path dependency.
