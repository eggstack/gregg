# Phase 29: `v1.0.1` daemon hot-path and runtime-isolation closure

## Objective

Remove avoidable per-request serialization work from `greggd`, measure the synchronous native collector’s effect on the current-thread Tokio runtime, and apply a bounded isolation correction only where measurements show the reactor can be blocked materially.

This phase is deliberately measurement driven. Cached response serialization is mandatory because snapshots are immutable between samples. Collector isolation is mandatory only when the defined responsiveness thresholds are exceeded, but the measurements and decision record are always required.

## Dependencies

Complete Phases 23, 24, 26, and 27 first. This phase must measure the corrected collectors, readiness model, service packaging, and four-architecture implementation.

## Baseline behavior

At baseline `eab5fe2e1d8f4635bb09aaf4ba69e18375ff5671`:

- `ServerState` stores an `Arc<StatusSnapshot>`;
- every `GET /` and `GET /v1/status` calls `serde_json::to_vec()` for the unchanged snapshot;
- concurrent readers therefore repeat identical serialization and allocation work;
- `greggd` uses a current-thread Tokio runtime;
- the sampler calls synchronous procfs/Mach/sysctl collection inline in the sampler task;
- a slow filesystem or native call can occupy the only runtime thread and delay HTTP handling.

The normal collectors are expected to be fast, so do not add complex threading without evidence. The server serialization change, however, is low-risk and should land unconditionally.

## Scope

### In scope

- `crates/greggd/src/server/mod.rs` and server tests;
- `crates/greggd/src/sampler.rs` and `run.rs` only if isolation thresholds require a correction;
- a deterministic latency test using a scripted slow collector;
- lightweight native collection-duration measurements;
- response-allocation and throughput measurements;
- documentation of the resulting runtime model.

### Out of scope

- switching to a multi-thread Tokio runtime without evidence;
- changing the HTTP schema;
- adding compression, HTTP/2, TLS, or caching headers;
- changing sample cadence limits;
- collector algorithm redesign;
- a generalized benchmark framework;
- unbounded worker pools.

## Workstream A: pre-serialize immutable status responses

### Required state representation

When a fresh snapshot is published, serialize it exactly once and store both:

1. the typed `Arc<StatusSnapshot>` needed for freshness checks and tests;
2. immutable compact JSON bytes used by the status handlers.

Acceptable byte types:

```rust
Arc<[u8]>
bytes::Bytes
Arc<Vec<u8>>
```

Prefer an existing dependency type. Do not add a dependency solely for this storage if `Arc<[u8]>` is sufficient.

Suggested internal record:

```rust
struct PublishedSnapshot {
    snapshot: Arc<StatusSnapshot>,
    json: Arc<[u8]>,
}
```

`ServerState` may store one `Arc<PublishedSnapshot>` behind the existing lock.

### Publication semantics

`publish_fresh_snapshot()` must:

1. validate or assume the already validated protocol snapshot according to existing architecture;
2. serialize compact JSON once;
3. create one immutable published record;
4. replace the old record atomically under the state lock;
5. update current collector/health state according to Phase 24;
6. expose the same bytes to every reader until the next fresh sample.

A serialization failure is an internal invariant failure because `StatusSnapshot` is serializable. Handle it consistently with project policy; do not publish a partially updated state.

### Handler semantics

`status_handler()` must:

- clone the stored immutable byte reference;
- evaluate freshness using the typed snapshot timestamp;
- return the cached bytes without calling `serde_json::to_vec()`;
- preserve the exact `application/json` content type and status codes;
- continue returning retained last-valid bytes during a permitted warming/failed freshness window;
- return `503` once stale according to Phase 24.

Health response serialization may remain per request because it changes with readiness and failure diagnostics. It may also be cached if implemented narrowly and tested, but that is not required.

### Required tests

1. published cached bytes decode to the original snapshot;
2. bytes match compact `serde_json::to_vec()` output exactly;
3. repeated status requests do not trigger additional snapshot serialization;
4. replacing a snapshot replaces both typed and byte representations atomically;
5. concurrent requests never observe typed metadata from one snapshot and bytes from another;
6. retained snapshot bytes preserve the original timestamp;
7. stale behavior remains unchanged;
8. no public JSON field or ordering contract relied upon by fixtures changes unexpectedly.

Use a test-only serialization counter or injectable serializer if needed. Do not infer serialization count only from timing.

## Workstream B: measure collector and reactor latency

### Measurement harness

Add a deterministic test or helper that runs:

- the actual current-thread runtime topology;
- HTTP server and sampler concurrently;
- a scripted collector that can block synchronously for a configured duration;
- repeated HTTP requests during collection;
- monotonic latency measurements.

Record:

- configured sample interval;
- injected collection delay;
- request count;
- median request latency;
- p95 and p99 request latency;
- maximum request latency;
- sample completion count;
- missed or delayed sampling intervals;
- runtime topology.

Use a deterministic local listener and bounded test duration.

### Native collector measurements

On all four native targets, record at least 100 collection cycles after warm-up where practical. Capture:

- minimum;
- median;
- p95;
- p99;
- maximum collection duration;
- configured sample interval;
- host architecture and OS;
- whether any collection returned warming/reset/failure.

Do not claim production latency from debug compilation alone. Use the same profile selected by release operational evidence, or report both debug and release while basing the decision on release measurements.

### Isolation thresholds

A collector isolation correction is required when either condition is demonstrated on a qualifying native target:

1. native collector p99 duration exceeds 25% of the configured minimum supported sampling interval (`250 ms`), meaning p99 exceeds `62.5 ms`; or
2. an inline collection delay of `50 ms` causes HTTP p99 latency to increase by more than `40 ms` relative to the idle baseline in the deterministic current-thread test.

The second threshold is expected to reveal reactor blocking by design. If the implementation retains inline collection, the decision record must explain why the production native measurements make the risk acceptable and must still add a regression budget for native collection duration.

A simpler and safer outcome is to isolate synchronous collection if the change remains narrow and preserves state ownership.

## Workstream C: bounded collector isolation when required

### Preferred design

Keep a single stateful collector instance and at most one in-flight collection operation.

Acceptable patterns:

1. a dedicated sampler worker thread owning the collector, with a bounded request/result channel of capacity one;
2. `spawn_blocking` that moves the collector into the blocking closure and returns both the collector and cycle result before the next sample.

Conceptual `spawn_blocking` shape:

```rust
let collector = self.collector.take().expect("collector present");
let joined = tokio::task::spawn_blocking(move || {
    let cycle = collect_one_cycle(&collector);
    (collector, cycle)
}).await;
self.collector = Some(returned_collector);
```

The actual design must account for `sample()`, `identity()`, and `capabilities()` consistently. Avoid making multiple concurrent calls on one collector.

### Required isolation invariants

- exactly one collector instance owns its counter baseline;
- no overlapping collection cycles;
- no unbounded queue of delayed samples;
- a missed cadence skips or delays according to documented sampler behavior rather than accumulating work;
- join panic becomes a controlled sampler failure;
- collector ownership is recovered after a successful blocking task;
- shutdown remains bounded and does not leak a worker thread or detached collection task;
- readiness and retained-snapshot semantics from Phase 24 remain unchanged;
- the HTTP reactor remains responsive during a scripted slow collection.

### Shutdown policy

A blocking native call cannot always be force-cancelled safely. Document the policy explicitly:

- stop scheduling new cycles after shutdown;
- wait for the current cycle only up to the existing daemon cleanup policy where possible;
- do not detach repeated workers;
- record a diagnostic when the blocking cycle exceeds the shutdown deadline;
- ensure process termination by supervision remains deterministic.

Do not claim that aborting a `spawn_blocking` handle cancels an already running closure.

## Workstream D: measurements and regression budgets

Add a checked-in evidence template or benchmark note under `plans/` or `architecture/` containing:

- baseline commit;
- corrected commit;
- commands;
- build profile;
- target matrix;
- response serialization count per snapshot and per request;
- request latency summary;
- native collector duration summary;
- isolation decision;
- any known measurement limitations.

### Required improvements

For a fixed snapshot and repeated local requests:

- snapshot serialization count must change from O(request count) to O(fresh snapshot count);
- response bytes must remain identical;
- median local request throughput must not regress by more than 5%;
- allocations attributable to snapshot serialization should decrease materially when measurable.

If isolation lands:

- scripted `50 ms` collection must not add more than `15 ms` to HTTP p99 latency over idle baseline on the same host;
- no more than one collection operation may be active;
- sampling generation count must remain correct.

## Smaller-model implementation sequence

1. Read Phase 24’s final state representation and all server tests.
2. Add a serialization-count regression test.
3. Introduce `PublishedSnapshot` or equivalent.
4. route status handlers through cached bytes.
5. run server and workspace tests.
6. add the scripted slow-collector latency harness.
7. collect native duration measurements on available targets.
8. compare measurements to the thresholds.
9. if required, implement one bounded isolation design only.
10. add shutdown, panic, and no-overlap tests for the isolation path.
11. run four-architecture CI.
12. write the measurement/decision record.

## Guardrails

- Do not cache stale timestamps as fresh.
- Do not serialize once per request under a different helper name.
- Do not remove the typed snapshot needed for freshness policy.
- Do not add an unbounded channel or worker pool.
- Do not allow overlapping collection cycles.
- Do not switch runtime flavor as the first response to blocking.
- Do not claim `spawn_blocking` cancellation that Tokio does not provide.
- Do not change status JSON or response codes.
- Do not implement collector isolation without tests for stateful baseline preservation.
- Do not skip the measurement record when no isolation code is added.

## Acceptance criteria

Phase 29 is complete only when all criteria are demonstrated:

1. A fresh status snapshot is serialized exactly once when published.
2. Repeated status requests reuse immutable cached bytes.
3. Cached bytes decode to the same `StatusSnapshot` and match existing compact JSON.
4. Typed snapshot metadata and cached bytes are replaced atomically.
5. Phase 24 readiness, retention, and stale-response semantics remain unchanged.
6. A deterministic current-thread slow-collector latency test exists.
7. Native collector duration statistics are recorded for all four advertised architectures.
8. The isolation decision is compared explicitly with the documented thresholds.
9. When thresholds require isolation, only one collector operation can be active and HTTP responsiveness meets the latency budget.
10. When isolation is not implemented, the decision record demonstrates native p99 below the production threshold and retains a regression test/budget.
11. Collector panic/join failure becomes a controlled failed state rather than a daemon hang.
12. Shutdown remains bounded and leaves no worker or process behind.
13. Snapshot serialization changes from O(requests) to O(fresh snapshots).
14. Median local request throughput does not regress by more than 5%.
15. All targeted tests, the complete workspace gate, and four-architecture CI pass.
