# Phase 22: `v1.0.1` sustained workload and resource evidence

## Objective

Replace the nominal `mixed-fleet-sustained` release job with a real bounded long-running workload that exercises Gregg’s production polling and state-reduction path, measures only the live workload interval, samples resources while the target process is alive, and fails closed when evidence is missing.

## Dependency

Phase 21 must be complete so the `mixed-fleet-sustained` dispatch can actually reach this job.

## Baseline defect

At baseline `eab5fe2e1d8f4635bb09aaf4ba69e18375ff5671`, the sustained job:

1. starts its timer before several `cargo test` commands;
2. includes compilation and test setup in the observed duration;
3. runs the test commands sequentially rather than maintaining a live workload;
4. invokes `ps` only after those commands have exited;
5. permits `ps` to fail with `|| true`;
6. creates `resource-samples.txt` even when no Gregg process was sampled;
7. fails if fast tests finish before 30 seconds instead of keeping a workload alive for 30 seconds.

This does not prove sustained behavior.

## Scope

### In scope

- `.github/workflows/release-candidate.yml`;
- a repository-owned sustained runner script, recommended path:

```text
scripts/run-mixed-fleet-sustained.py
```

- a dedicated Rust integration test or nonvisual driver using production `PollScheduler`, `HttpClient`, endpoint state reduction, and deterministic fixture servers;
- release evidence metadata and tests for the sustained stage;
- resource sample parsing and validation.

### Out of scope

- interactive TUI rendering under a pseudo-terminal;
- replacing the existing short functional mixed-fleet test;
- long protected-host soak duration policy changes;
- generalized benchmarking infrastructure;
- performance optimization unrelated to keeping the workload stable.

## Required workload model

Use a two-layer design:

1. **Rust workload driver:** exercises the production client polling and state engine for a configured monotonic duration.
2. **External runner:** builds first, launches the workload binary/test, samples its process resources while it is alive, enforces time and sample requirements, and writes evidence files.

The runner must not count compilation or dependency download time as sustained runtime.

### Preferred Rust driver

Add an ignored integration test or purpose-built test binary under `crates/gregg/tests/` that:

- starts deterministic local fixture endpoints;
- includes at least one healthy endpoint;
- includes at least one unreachable or connection-refused endpoint;
- includes at least one endpoint that changes state during the run;
- constructs the production `HttpClient` and `PollScheduler`;
- runs repeated generations for `GREGG_SUSTAINED_SECONDS`;
- feeds every completed `PollBatch` through the production state reducer;
- checks that every generation contains exactly one result per configured endpoint;
- checks generation numbers are strictly increasing;
- checks the online/offline transition is observed;
- checks task count and in-flight request count remain bounded;
- writes a machine-readable summary when the duration completes.

The driver must be noninteractive and deterministic. It may reuse existing fixture helpers, but must not replace the production scheduler with a test-only loop.

### Suggested invocation

The exact test name may differ, but the contract should be equivalent to:

```bash
GREGG_SUSTAINED_SECONDS=30 \
GREGG_SUSTAINED_SUMMARY="$PWD/evidence/sustained-summary.json" \
./target/debug/deps/mixed_fleet_sustained-<hash> --ignored --nocapture
```

A dedicated helper binary is also acceptable when it keeps release-only code out of the shipped binary packages.

## External runner requirements

The script should expose explicit options such as:

```text
--duration-seconds 30
--sample-interval-seconds 5
--evidence-dir evidence
--profile debug|release
```

### Execution sequence

The runner must perform these steps in order:

1. validate arguments;
2. create a clean evidence directory;
3. build the workload target with `cargo test --no-run` or `cargo build`;
4. locate the exact executable deterministically;
5. record build completion;
6. record `workload_started_monotonic_ns` immediately before process launch;
7. launch the workload as a child process;
8. confirm the child remains alive after startup;
9. sample resources repeatedly while the child is alive;
10. wait for the child to exit;
11. record `workload_completed_monotonic_ns`;
12. validate the workload summary;
13. validate duration and resource sample requirements;
14. write the candidate artifact metadata;
15. exit nonzero on any missing or inconsistent evidence.

### Resource sample schema

Write JSON Lines or a JSON array. Each sample must include at least:

```json
{
  "sample_index": 1,
  "monotonic_ns": 123456789,
  "pid": 4242,
  "rss_bytes": 12345678,
  "virtual_bytes": 87654321,
  "thread_count": 7,
  "process_alive": true
}
```

Linux may use `/proc/<pid>/status` and `/proc/<pid>/stat`. The CI job currently runs on Linux, so a Linux implementation is sufficient for this release stage. Avoid parsing locale-dependent human-readable `ps` output when `/proc` provides structured values.

### Minimum sample policy

For a 30-second CI qualification with a 5-second sample interval:

- require at least 5 valid samples;
- require all samples to identify the same target PID unless an intentional supervised restart is part of the test;
- require `process_alive: true` at sampling time;
- require positive RSS and thread-count values;
- require strictly increasing monotonic timestamps;
- require the last sample to occur after at least 80% of the requested duration.

Do not weaken the requirement because a file exists.

## Duration semantics

Use a monotonic clock.

Compute:

```text
observed_duration = workload_completed_monotonic_ns - workload_started_monotonic_ns
```

The run qualifies only when:

```text
observed_duration >= requested_duration
```

A small upper tolerance may be documented for scheduling and cleanup. Do not require exact equality.

Compilation, fixture build, dependency download, and artifact upload must occur outside the measured interval.

## Functional summary requirements

The Rust driver must write a summary containing at least:

- requested duration;
- observed duration;
- endpoint count;
- completed generation count;
- first and last generation numbers;
- maximum concurrently active polls;
- count of online results;
- count of offline/error results;
- observed state transitions;
- clean shutdown status;
- any panic or task-join failure.

The external runner must reject a missing or malformed summary.

## Workflow changes

Replace the current sequential test block in `mixed-fleet-sustained` with:

1. checkout and toolchain setup;
2. build/setup outside the timer;
3. run the sustained runner;
4. validate the generated summary and resources;
5. run the existing short scheduler/state/poller unit tests separately if still useful, but do not count them as sustained time;
6. create `candidate.json` only after the sustained evidence validator passes;
7. upload all required evidence with `if-no-files-found: error`.

The candidate notes must record actual values, not only configured values:

```text
requested_duration_secs=30
observed_duration_secs=<actual>
resource_sample_count=<actual>
completed_generations=<actual>
```

## Required evidence files

At minimum:

```text
evidence/sustained-summary.json
evidence/resource-samples.jsonl
evidence/workload-stdout.txt
evidence/workload-stderr.txt
evidence/artifacts.json
evidence/candidate.json
```

Optional diagnostic files may be added, but the required set must be validated before upload.

## Negative tests

Add deterministic tests for:

1. workload exits before requested duration;
2. workload process fails to start;
3. workload panics;
4. summary is missing;
5. summary reports insufficient generations;
6. resource sample file is empty;
7. resource sample has zero RSS;
8. samples have nonmonotonic timestamps;
9. samples refer to a dead or wrong PID;
10. last sample occurs too early;
11. endpoint transition never occurs;
12. a generation omits an endpoint;
13. runner receives an invalid duration or sample interval;
14. child does not exit within a bounded cleanup deadline.

## Positive tests

Add deterministic short-duration tests, separate from the qualifying workflow duration:

- 2-second workload with 200-millisecond sampling;
- multiple generations complete;
- online and offline outcomes occur;
- at least three samples are written;
- the runner exits zero;
- evidence parses and validates.

Do not use the 30-second qualifying duration in every unit test.

## Smaller-model guardrails

- Do not time `cargo test` compilation.
- Do not sleep merely to satisfy duration while no production-path work occurs.
- Do not sample only the parent shell or Cargo process.
- Do not keep `|| true` on mandatory sampling or evidence validation.
- Do not accept an empty file as resource evidence.
- Do not reuse the short functional test as the sustained stage without a repeated production polling loop.
- Do not alter the required 30-second CI qualification merely to make the test faster.
- Keep all cleanup bounded and fail closed.

## Validation commands

Run:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-targets --all-features
python3 -m unittest discover -s scripts/tests -p 'test*.py'
```

Run the local short qualification, for example:

```bash
python3 scripts/run-mixed-fleet-sustained.py \
  --duration-seconds 2 \
  --sample-interval-seconds 0.2 \
  --evidence-dir target/sustained-smoke
```

Then inspect:

```bash
python3 -m json.tool target/sustained-smoke/sustained-summary.json
wc -l target/sustained-smoke/resource-samples.jsonl
```

Finally run a nonpublishing GitHub Actions dispatch with the full 30-second duration.

## Acceptance criteria

Phase 22 is complete only when all criteria are demonstrated:

1. The sustained dispatch reaches the sustained job.
2. Build and setup complete before the workload timer starts.
3. A live production-path polling and state-reduction workload runs for at least the configured duration.
4. The workload completes multiple generations and every generation contains one result per endpoint.
5. At least one online and one offline/error path are exercised.
6. At least one endpoint state transition is observed.
7. Resource samples are collected while the target workload process is alive.
8. The qualifying 30-second run produces at least five valid samples.
9. Resource evidence is nonempty, monotonic, and tied to the target PID.
10. Missing or empty resource evidence fails the job.
11. Early process exit fails the job.
12. Compilation time cannot satisfy the duration requirement.
13. The workload summary records actual duration, generations, concurrency, and transitions.
14. Candidate metadata records actual observed duration and sample count.
15. Required evidence files are uploaded with `if-no-files-found: error`.
16. Short deterministic positive and negative tests pass locally.
17. The full workspace and release-tooling tests pass.
18. A nonpublishing workflow run produces a valid `mixed-fleet-sustained` artifact with immutable run and artifact identity.

## Handoff record

The implementing agent must report:

- Rust workload driver path and test name;
- runner script path;
- target process selection method;
- requested and observed duration;
- sample interval and sample count;
- completed generations and observed transitions;
- local smoke command result;
- nonpublishing workflow run ID, attempt, artifact ID, and artifact name when available.
