# Phase 18: narrow `v1.0.1` release-orchestration correction

## Objective

Correct the executable orchestration defects remaining after the Phase 17 implementation pass without reopening Gregg application behavior, protocol design, collectors, daemon semantics, client state reduction, TUI behavior, or service-manager architecture.

The implementation baseline for this plan is:

```text
19b8e134afbc3001f70f66a082a197dee2aefb13
```

Phase 17 introduced the correct release-control concepts, but several of those components are not connected in a runnable end-to-end chain. Phase 18 must make the existing release workflow executable and internally consistent so one frozen candidate can proceed through:

1. prepublication source and package gates;
2. source-native and package-native gates;
3. sustained mixed-fleet evidence;
4. protected lifecycle, resource, and soak gates;
5. pre-tag cross-run aggregation;
6. annotated-tag verification;
7. ordered crates.io publication;
8. postpublication verification;
9. final cross-run aggregation with actual GitHub artifact identities.

This is a narrow release-orchestration correction. It must not add product features or redesign release policy.

## Current disposition

At the baseline commit:

- ordinary source CI is reported green after the macOS mixed-fleet fixture race was corrected;
- no frozen release candidate exists;
- no annotated `v1.0.1` tag exists;
- crates.io contains only the unyanked `1.0.0` releases;
- no qualifying release workflow run IDs, attempts, numeric artifact IDs, or artifact ZIP digests are recorded;
- `.github/workflows/release-finalize.yml` exists, but its artifact retrieval command cannot parse the supplied artifact-name arguments;
- `scripts/github-artifact-retrieval.py` defines artifact downloading and extraction but does not invoke it from `main()`;
- the retrieval manifest is not consumed by final aggregation, so actual GitHub artifact IDs never enter the final release manifest;
- advertised `pre-tag` finalization always executes the `--final` path and requires postpublication evidence;
- package-native jobs are guarded by mutually exclusive stage conditions and cannot run;
- package-native artifact names do not match binary package artifact names;
- the package-native job attempts to use one package provenance document and one lockfile for both binaries;
- `mixed-fleet-sustained` is mandatory but no job emits that stage;
- protected cleanup failures are masked with `|| true`;
- the finalizer checks out mutable default-branch tooling rather than explicitly identifying the immutable finalizer toolchain;
- the release ledger uses a commit abbreviation where a workflow run ID is required and identifies the Phase 17 registry commit rather than the substantive implementation commit.

Phase 18 is complete only when those orchestration defects are corrected and demonstrated through deterministic end-to-end tests. Actual protected-host execution, tagging, publication, and final immutable evidence remain required for release completion, but they must not begin until the corrected orchestration passes a dry-run qualification.

## Governing invariants

1. **No product scope:** only release workflows, release scripts, evidence schemas, release tests, and release documentation may change unless a release-blocking application defect is discovered.
2. **One candidate SHA:** every selected run and every extracted `candidate.json` must name the same full lowercase 40-character SHA.
3. **Actual artifact identity:** numeric GitHub artifact IDs and downloaded ZIP digests must enter the final manifest; semantic content labels are not artifact IDs.
4. **Download before consume:** provenance, candidate metadata, registry summaries, and dispositions may be consumed only from downloaded and validated artifacts.
5. **Per-run artifact contracts:** every selected workflow run declares the exact artifact names expected from that run. No global artifact list is applied to every run.
6. **Mode separation:** pre-tag aggregation must not require tag, registry, disposition, publication, or postpublication evidence. Final aggregation must require all of them.
7. **Package-native independence:** native package jobs consume already-produced binary package artifacts from a selected binary-prepublish run; they do not require the binary-prepublish job to run in the same dispatch.
8. **Per-package provenance:** `greggd` and `gregg` use their own archive, provenance document, lockfile, and install record.
9. **Sustained means sustained:** `mixed-fleet-sustained` must be a distinct bounded long-run gate, not an alias for the two-generation functional test.
10. **Cleanup fails closed:** cleanup failure invalidates a qualifying protected-host job unless the original gate already failed and cleanup failure is retained as an additional diagnostic.
11. **Immutable tooling identity:** the final manifest records the exact commit containing the finalizer and validation tooling used to produce it.
12. **Evidence claims use correct identifiers:** commit SHAs, workflow run IDs, run attempts, job IDs, artifact IDs, and tag-object SHAs are recorded in separate correctly named fields.

## Scope

### P0 implementation work

- Repair the finalizer CLI contract and run-selection schema.
- Make artifact retrieval download, checksum, extract, and validate every selected artifact.
- Feed retrieved numeric artifact identities into aggregation.
- Split pre-tag and final aggregation behavior.
- Repair package-native workflow dispatch and artifact naming.
- Use package-specific provenance and lockfiles.
- Add a real sustained mixed-fleet stage.
- Make protected cleanup fail closed and preserve dual-failure diagnostics.
- Pin and record finalizer tooling identity.
- Replace shallow static tests with end-to-end mocked retrieval/finalization tests.
- Correct the evidence ledger and plan registry after implementation.

### P0 pre-release qualification

- Run the complete local gate.
- Execute a synthetic or repository-owned dry-run finalizer against deterministic mocked GitHub API/artifact fixtures.
- Execute a real nonpublishing release workflow sequence against a disposable candidate SHA where infrastructure is available.
- Do not freeze, tag, or publish until the corrected orchestration is proven runnable.

### Non-goals

Do not:

- change metrics, endpoint schemas, polling semantics, service commands, config formats, or TUI behavior;
- add Windows support;
- reduce the native matrix;
- reduce resource or soak durations;
- treat source-native evidence as package-native evidence;
- create a generalized multi-repository release framework;
- introduce new signing or attestation infrastructure unless required to fix an identified correctness defect;
- publish `1.0.1` merely because the corrected workflow definitions land;
- mask workflow failures with `continue-on-error`, broad `|| true`, or unconditional success metadata.

## Workstream A: define a correct run-selection and artifact contract

### A1. Make artifact expectations per selected run

Replace the current global `--expected-artifact-names` contract with a selection-file contract in which every selected run declares the exact artifacts it must contain.

Recommended shape:

```json
{
  "candidate_sha": "0123456789abcdef0123456789abcdef01234567",
  "release_version": "1.0.1",
  "tooling_sha": "89abcdef0123456789abcdef0123456789abcdef",
  "runs": {
    "source-ci": {
      "run_id": 1001,
      "attempt": 1,
      "workflow_name": "release-candidate",
      "artifacts": [
        {"name": "source-ci-deadbeef-1"}
      ]
    },
    "binary-prepublish-greggd": {
      "run_id": 1004,
      "attempt": 1,
      "workflow_name": "release-candidate",
      "artifacts": [
        {"name": "binary-greggd-deadbeef-1"}
      ]
    }
  }
}
```

Allow an optional numeric artifact ID only to resolve an explicitly reviewed ambiguity:

```json
{"name": "binary-greggd-deadbeef-1", "artifact_id": 123456789}
```

The normal case must select by exact artifact name and require exactly one unexpired match.

### A2. Validate selection semantics before network access

Add a selection validator that rejects:

- short or malformed candidate SHA;
- release version other than `1.0.1`;
- malformed tooling SHA;
- empty run set;
- nonnumeric run ID or attempt;
- duplicate logical stage names;
- duplicate selected artifact names within a run;
- missing expected artifact list;
- empty artifact names;
- artifact IDs that are not positive integers;
- unsupported workflow names;
- final-mode selection missing mandatory stage groups;
- pre-tag selection containing postpublish-only stages unless explicitly allowed as surplus nonqualifying evidence.

### A3. Separate logical stages from workflow runs

One workflow run may contain several required logical stages. The selection schema must not require a separate run ID for every job when several jobs came from one dispatch.

Preferred model:

```json
"runs": {
  "binary-prepublish": {
    "run_id": 1004,
    "attempt": 1,
    "artifacts": [
      {"name": "binary-greggd-deadbeef-1"},
      {"name": "binary-gregg-deadbeef-1"},
      {"name": "msrv-greggd-deadbeef-1"},
      {"name": "msrv-gregg-deadbeef-1"}
    ]
  }
}
```

The extracted `candidate.json` files determine logical stage identity. Final aggregation still requires each mandatory logical stage exactly once.

### A acceptance criteria

1. Artifact expectations are declared per selected run.
2. The finalizer no longer passes a global list that applies to every run.
3. Selection validation occurs before GitHub API requests.
4. Malformed run IDs, attempts, artifact names, and artifact IDs fail deterministically.
5. One run can supply several logical stages without duplicating run records.
6. The checked-in example selection matches the actual workflow artifact naming contract.
7. A JSON schema or equivalent validator covers the selection format.

## Workstream B: make artifact retrieval genuinely end to end

### B1. Invoke artifact downloading from `main()`

After `resolve_artifacts()` returns selected artifact records, call `download_artifact()` for every selected artifact.

Each returned record must include:

- numeric GitHub artifact ID;
- exact artifact name;
- workflow run ID;
- workflow run attempt;
- GitHub-reported artifact size;
- downloaded ZIP size;
- downloaded ZIP SHA-256;
- creation and expiration timestamps;
- local ZIP path;
- extraction path;
- selected candidate metadata path(s);
- candidate metadata SHA-256 values;
- logical stages discovered inside the artifact.

### B2. Validate every `candidate.json`, not only the first

Artifacts may contain more than one candidate record. For each downloaded artifact:

1. recursively enumerate every `candidate.json`;
2. require at least one;
3. validate every candidate against the expected SHA and release version;
4. reject mixed stage records where the artifact contract permits only one stage;
5. reject duplicate candidate records for the same stage unless byte-identical and explicitly documented;
6. record all candidate paths and hashes.

Never select only `candidate_files[0]` and ignore the rest.

### B3. Prevent unsafe ZIP extraction

Do not use unrestricted `ZipFile.extractall()` on untrusted artifact paths.

Before extraction, reject entries that:

- are absolute paths;
- contain `..` path traversal;
- resolve outside the intended extraction root;
- represent symlinks or special files when unsupported;
- collide after normalization;
- exceed a documented extracted-size or entry-count bound.

Add a deterministic malicious-ZIP test.

### B4. Preserve retrieval output as an input manifest

`retrieved-manifest.json` must contain all run and artifact identity records and must be consumed by the release aggregator.

It must not merely be uploaded as an unused side artifact.

### B5. Normalize artifact size fields

Keep separate fields for:

- `github_reported_size_bytes`;
- `downloaded_zip_size_bytes`;
- optional extracted content size.

Do not overwrite the GitHub-reported size with the downloaded size under the same field.

### B acceptance criteria

1. Every selected artifact is actually downloaded.
2. Every ZIP is hashed and sized.
3. Every ZIP is safely extracted.
4. Every contained candidate record is validated.
5. Mixed candidate SHAs or versions fail retrieval.
6. The retrieval manifest records numeric artifact IDs and ZIP digests.
7. The retrieval manifest is consumed by final aggregation.
8. Malicious path traversal ZIPs are rejected.
9. Empty, corrupt, expired, missing, and ambiguous artifacts are tested.

## Workstream D: split pre-tag and final aggregation modes correctly

### D1. Pre-tag mode requirements

Pre-tag mode must require only the approved prepublication set:

- source CI;
- protocol prepublication;
- binary prepublication and MSRV where possible under the approved protocol staging model;
- source-native evidence;
- package-native evidence;
- mixed-fleet functional and sustained evidence;
- lifecycle evidence;
- resource evidence;
- qualifying soaks;
- merged three-crate package provenance.

Pre-tag mode must not require:

- annotated tag identity;
- protocol registry index record unless the release process deliberately publishes protocol before the final tag and documents that policy;
- binary registry records;
- `postpublish-verify`;
- final registry summary;
- `1.0.0` disposition file unless policy requires that decision before pre-tag approval.

Resolve the protocol publication/tag ordering explicitly. The workflow and plan must agree on one sequence.

### D2. Final mode requirements

Final mode must require:

- all pre-tag mandatory stages;
- exact annotated `v1.0.1` identity;
- tag object and peeled candidate equality;
- protocol registry index evidence;
- binary publication and registry records;
- exact postpublication installs and runtime verification;
- `1.0.0` disposition for all three crates;
- complete registry summary;
- merged package provenance.

### D3. Separate machine-readable stage sets

Update `release-requirements.json` to define separate arrays:

```json
{
  "release_version": "1.0.1",
  "pre_tag_required_stages": [],
  "final_required_stages": []
}
```

The final set may extend the pre-tag set. Validators must reject accidental mismatch between workflow mode and selected requirement set.

### D4. Finalizer command construction

Only append:

- tag arguments;
- registry summary;
- disposition;
- `--final`;

when `mode == final`.

Pre-tag mode must produce a valid pre-tag manifest with `tag: null` and no final-only records.

### D acceptance criteria

1. Pre-tag mode runs without an annotated tag.
2. Pre-tag mode runs without postpublication evidence.
3. Final mode rejects missing tag, registry, disposition, or postpublish evidence.
4. Machine-readable pre-tag and final stage sets exist.
5. The selected release ordering is internally consistent and documented.
6. Tests accept a complete synthetic pre-tag set and reject it under final mode.
7. Tests accept a complete synthetic final set.

## Workstream E: repair package-native dispatch and artifact contracts

### E1. Remove impossible same-dispatch dependencies

`native-package-evidence` must not require `binary-prepublish` to succeed in the same `native-evidence` dispatch.

Use one of these explicit designs:

#### Preferred design: external selected package run

- `native-evidence` accepts required `package_run_id` and `package_run_attempt`;
- package-native jobs download binary artifacts from that selected successful binary-prepublish run;
- a preflight step validates the selected run and artifact names;
- no `needs: binary-prepublish` dependency exists.

#### Acceptable design: combined dispatch

Add a distinct stage such as `binary-and-native-evidence` in which package and native jobs intentionally run together. Do not rely on mutually exclusive stage conditions.

The preferred external-run design better preserves staged protocol publication and rerun selection.

### E2. Establish one canonical artifact naming function

Binary package producers and every consumer must use the same exact artifact name.

Recommended producer names:

```text
binary-greggd-<short-sha>-<run-attempt>
binary-gregg-<short-sha>-<run-attempt>
```

or:

```text
binary-greggd-<version>-<short-sha>-<run-attempt>
binary-gregg-<version>-<short-sha>-<run-attempt>
```

Choose one and update:

- binary upload steps;
- native package download steps;
- protected operational downloads;
- lifecycle downloads;
- run-selection examples;
- workflow static validation;
- finalizer expected artifact contracts.

Do not mix candidate version and run attempt in the same position across producer and consumer names.

### E3. Keep downloaded artifacts separated

Download daemon and client package artifacts into separate roots:

```text
package-artifacts/greggd/
package-artifacts/gregg/
```

Do not merge both downloads into one directory where duplicate filenames such as `candidate.json`, `package-provenance.json`, or `Cargo.lock` become ambiguous.

### E4. Use package-specific records

For `greggd`, use only:

- `greggd-1.0.1.crate`;
- daemon package provenance;
- daemon verification lockfile.

For `gregg`, use only:

- `gregg-1.0.1.crate`;
- client package provenance;
- client verification lockfile.

Do not use the daemon provenance or daemon lockfile to install the client.

### E5. Validate selected package run before matrix fan-out

Add a lightweight prerequisite job that:

- validates run ID and attempt;
- confirms both expected binary artifacts exist and are unexpired;
- records their numeric artifact IDs;
- confirms both candidate metadata records match the requested SHA;
- exposes validated artifact names/IDs as job outputs or a small downloaded manifest.

### E acceptance criteria

1. Package-native jobs are no longer permanently skipped.
2. Producer and consumer artifact names match exactly.
3. Daemon and client artifacts are downloaded into separate roots.
4. Each package uses its own provenance and lockfile.
5. Missing or mixed package artifacts fail before native matrix execution.
6. All four package-native platforms can start from one selected binary-prepublish run.
7. Static tests evaluate actual job conditions, not only substring presence.

## Workstream G: make protected cleanup fail closed

### G1. Preserve the primary job outcome

Protected jobs must distinguish:

- gate success;
- gate failure;
- cleanup success;
- cleanup failure.

A cleanup step must always run, but cleanup failure must not be hidden.

### G2. Use explicit cleanup outcome propagation

One acceptable pattern:

1. run gate step with an explicit step ID;
2. run cleanup under `if: always()` with an explicit step ID and no `|| true`;
3. upload diagnostics under `if: always()`;
4. add a final verdict step under `if: always()` that fails if either gate or cleanup failed.

Example intent:

```yaml
- id: gate
  name: Exercise lifecycle
  run: scripts/run-systemd-release-gate.sh

- id: cleanup
  if: always()
  name: Cleanup protected host
  run: scripts/cleanup-protected-host.sh

- if: always()
  name: Enforce protected-host verdict
  run: |
    test "${{ steps.gate.outcome }}" = success
    test "${{ steps.cleanup.outcome }}" = success
```

Adapt this to GitHub Actions expression semantics and test it statically.

### G3. Retain dual-failure diagnostics

When both gate and cleanup fail, preserve:

- original gate exit status and transcript;
- cleanup exit status and transcript;
- service status;
- remaining process/port state;
- marker directory state;
- relevant journal or launchd diagnostics.

Do not let cleanup failure erase the original failure context.

### G4. Apply to every protected job

Apply fail-closed cleanup to:

- systemd lifecycle;
- launchd lifecycle;
- Linux operational/resource/soak;
- macOS operational/resource/soak;
- any sustained self-hosted mixed-fleet job;
- finalizer temporary artifact cleanup where failure could affect rerun integrity.

### G acceptance criteria

1. No qualifying cleanup command is followed by `|| true`.
2. Cleanup always executes.
3. Cleanup failure causes the job to fail.
4. Primary gate failure remains visible when cleanup also fails.
5. Failure artifacts upload after either failure.
6. A mocked workflow test covers gate-success/cleanup-failure and gate-failure/cleanup-failure cases.

## Workstream H: pin and record finalizer tooling identity

### H1. Choose an immutable tooling model

Use one of two explicit models:

#### Model 1: candidate-contained finalizer

- checkout the candidate SHA before running finalizer scripts;
- require all finalizer scripts and schemas to exist in the candidate;
- record `tooling_sha == candidate_sha`.

#### Model 2: separate trusted finalizer tooling commit

- accept a full tooling SHA as an input;
- checkout that SHA detached;
- require it to be an ancestor of or explicitly approved successor to the candidate;
- record both candidate SHA and tooling SHA;
- prohibit mutable branch checkout;
- document why a post-candidate tooling correction is trusted.

For this release, Model 1 is preferred after Phase 18 corrections are included in the final candidate.

### H2. Validate checkout identity

The finalizer must:

- use `ref: <full SHA>`;
- use `fetch-depth: 0` where tag verification is required;
- detach checkout;
- verify `git rev-parse HEAD` exactly;
- record tooling SHA in retrieval and final manifests.

### H3. Reject mutable finalizer execution

Static validation must fail if `release-finalize.yml` uses a default checkout without a full immutable ref.

### H acceptance criteria

1. Finalizer tooling comes from an immutable SHA.
2. Tooling SHA is recorded in the final manifest.
3. Mutable default-branch checkout cannot qualify.
4. Candidate and tooling identity policy is documented.
5. Tag verification runs in a checkout that contains the fetched annotated tag object.
