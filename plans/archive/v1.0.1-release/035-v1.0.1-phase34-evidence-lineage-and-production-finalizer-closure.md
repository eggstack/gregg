# Phase 35: `v1.0.1` Phase-34 evidence-lineage and production-finalizer closure

## Objective

Close the remaining release-control defects found after Phase 34 and prove that the final synthetic and production finalization paths consume the **same selected evidence objects** that were actually produced and validated at each preceding release boundary.

Phase 34 successfully added checksum-bearing Boundary-2 registry resolution, real command-evidence indices, local candidate file validation, complete production stage enumeration, a checked-in qualification contract, and exact-SHA hosted qualification. The remaining defect is not absence of evidence. It is absence of authoritative **cross-binding** between evidence producers, selected GitHub artifacts, retrieved files, package provenance, role materialization, and final aggregation.

The baseline for this plan is current `main` at:

```text
f8069fcb9f74284f13aa749e218f91c31e91cf17
```

The Phase 34 hosted run and artifact remain useful partial evidence:

```text
qualified implementation SHA: a30f0811ccad953b54f5a17cc23c5017e6789db7
workflow run: 30364594098
artifact: 8690276022
```

They do not close this phase because direct source and artifact inspection found that:

- the final synthetic chain creates generic replacement candidates for `registry-reverify-greggd` and `registry-reverify-gregg` instead of selecting the candidates generated by the real Boundary-2 executions;
- `boundary2_summaries` and `candidate_manifest_path` are passed into final-chain construction but are not used to enforce lineage;
- the final synthetic package provenance is generated from new stub archives rather than the exact archives verified at Boundary 2;
- the synthetic postpublish ZIP does not actually contain the registry summary or `1.0.0` disposition later attributed to that artifact;
- singleton role records are assembled from manually copied artifact metadata rather than derived from the retrieved artifact contents;
- the production finalizer retrieves selected evidence but then independently creates registry summary and disposition files locally;
- the production finalizer indexes direct local files without materializing them and passes those direct paths to aggregation;
- the qualification validator checks stage membership and individual evidence validity but does not prove cross-binding among the final selection, retrieved manifest, actual Boundary-2 candidates, package archives, postpublish ZIP, role index, and final manifest;
- the checked-in negative-case contract omits several Phase-34 rejection cases that would have detected these substitutions.

Phase 35 supersedes Phase 34 only for these evidence-lineage and production-finalizer defects. Preserve all correct Phase 31 through Phase 34 behavior.

## Governing invariants

1. **One produced object has one identity.** A later phase may reference an earlier archive, candidate, artifact, or file only by carrying forward its exact immutable identity.
2. **Stage-name equivalence is not evidence equivalence.** A generic candidate named `registry-reverify-greggd` cannot substitute for the actual candidate emitted by the `greggd` Boundary-2 execution.
3. **The final selection is authoritative.** Every final manifest stage must derive from the exact run, attempt, artifact ID, artifact name, ZIP digest, ZIP size, and candidate file selected by the final run-selection document.
4. **Boundary-1 archives remain byte-identical.** The protocol, daemon, and client archives selected before publication must be the same bytes referenced at protocol-index verification, Boundary 2, final package provenance, and publication authorization.
5. **Boundary-2 candidates carry their proof.** The selected Boundary-2 artifact must contain its real summary, command index, command transcripts, registry record, generated lockfile identity, normalized manifest, package archive identity, and candidate metadata.
6. **Postpublish evidence is an artifact, not a local reconstruction.** Registry summary and `1.0.0` disposition must exist inside the selected postpublish artifact and be retrieved from it.
7. **Role identity comes from retrieval.** The role index must be derived from validated candidate declarations and files extracted from the exact selected artifact.
8. **Materialization precedes aggregation.** Final aggregation receives only materialized singleton paths produced from the validated role index.
9. **The production finalizer and qualification harness share the same input-preparation primitive.** Workflow shell and synthetic tests must not implement materially different lineage rules.
10. **Independent validation follows references.** A validator must open and compare all referenced candidates, manifests, indices, archives, and role records rather than checking only that fields are present.
11. **Synthetic evidence may emulate behavior, not identity.** Synthetic platform results are acceptable for orchestration qualification, but their artifact identity and lineage rules must be production-equivalent.
12. **No source-of-record duplication.** Registry summary, disposition, package provenance, and selected candidates each have one authoritative producer.
13. **Validation fails closed.** Replacement candidates, changed archives, files absent from claimed ZIPs, manual role metadata, direct-path final inputs, incomplete cross-links, and stale hosted evidence all exit nonzero.
14. **Exact-SHA qualification remains mandatory.** Any executable, workflow, schema, fixture, contract, or test change invalidates previous hosted qualification.
15. **No publication occurs in Phase 35.** No release tag or crates.io mutation is allowed.

## Workstream A: define and enforce exact evidence lineage

### A1. Extend the retrieved-manifest lineage contract

The retrieved manifest must expose one canonical record for each selected logical stage. A minimal stage binding is:

```json
{
  "stage": "registry-reverify-greggd",
  "workflow_run_id": "123456",
  "workflow_run_attempt": "1",
  "artifact": {
    "id": 987654,
    "name": "registry-reverify-greggd-abc123-1",
    "zip_sha256": "<64 lowercase hex>",
    "zip_size_bytes": 12345,
    "extraction_root": "runs/123456/attempt-1/artifacts/987654"
  },
  "candidate": {
    "path": ".../candidate.json",
    "sha256": "<64 lowercase hex>",
    "size_bytes": 1234
  }
}
```

Requirements:

- exactly one binding per required stage;
- no stage appears in multiple selected artifacts;
- no selected artifact contains multiple candidate files for the same stage;
- candidate `workflow_run_id` and attempt equal the selected run and attempt;
- candidate stage, candidate SHA, and release version match the selection;
- candidate file identity is retained;
- artifact extraction root is normalized and contained;
- the selected ZIP identity is immutable;
- artifact IDs are positive integers;
- conflicting reuse of one artifact ID fails.

Do not add a parallel, independently populated lineage document when the retrieved manifest can be extended without ambiguity.

### A2. Add package/archive lineage records

The provenance index or retrieved manifest must expose exact archive lineage for all three packages:

```json
{
  "package": "greggd",
  "boundary_1_stage": "binary-prepublish-greggd",
  "boundary_1_artifact_id": 111,
  "archive_path": ".../greggd-1.0.1.crate",
  "archive_sha256": "...",
  "archive_size_bytes": 123,
  "boundary_2_stage": "registry-reverify-greggd",
  "boundary_2_artifact_id": 222,
  "boundary_2_archive_sha256": "same value",
  "final_provenance_sha256": "same value"
}
```

For `gregg-protocol`, bind:

```text
protocol-prepublish archive
-> local sparse-registry archive
-> protocol-index checksum
-> final package provenance
```

For `greggd` and `gregg`, bind:

```text
binary-prepublish archive
-> Boundary-2 input archive
-> Boundary-2 archive-before identity
-> Boundary-2 archive-after identity
-> final package provenance
```

Any mismatch fails.

### A3. Add singleton-file lineage records

Every required singleton role record must retain:

- stage;
- workflow run ID and attempt;
- artifact ID and exact artifact name;
- ZIP digest and size;
- extraction root;
- candidate path and identity;
- declared candidate artifact path, role, digest, and size;
- extracted file path, digest, and size;
- materialized path, digest, and size.

The candidate declaration, extracted file, and materialized file must have identical digest and size.

### Workstream A acceptance criteria

- [ ] The retrieved manifest contains exactly one canonical binding for every selected stage.
- [ ] Each binding includes complete run, artifact, ZIP, candidate, and extraction identity.
- [ ] Stage bindings are derived by retrieval, not synthesized after retrieval.
- [ ] Package archive lineage exists for all three crates.
- [ ] Singleton lineage binds candidate declaration, extracted file, and materialized copy.
- [ ] Duplicate, missing, ambiguous, or conflicting stage bindings fail.
- [ ] Conflicting artifact-ID reuse fails.
- [ ] Candidate/run/attempt mismatch fails.
- [ ] Candidate file identity mismatch fails.
- [ ] Archive or singleton lineage mismatch fails.

## Workstream C: preserve exact package archives across all boundaries

### C1. Build Boundary-1 archives once

The qualification harness must create exactly one archive per package before the candidate/pre-tag chain:

```text
gregg-protocol-1.0.1.crate
greggd-1.0.1.crate
gregg-1.0.1.crate
```

These archives must be packaged from valid crate trees. Do not use arbitrary text files with a `.crate` suffix.

The candidate/pre-tag package artifacts must include these exact bytes and package provenance records.

### C2. Use the protocol archive as the local registry payload

The local sparse registry must serve the exact `gregg-protocol-1.0.1.crate` selected in the protocol-prepublish stage. Its index checksum must equal that archive digest.

The protocol-index stage must bind the same archive digest and the sparse registry record.

### C3. Use dependent archives as Boundary-2 inputs

Boundary 2 must consume the exact selected `greggd` and `gregg` archive paths from the candidate/pre-tag artifact/provenance bindings.

Do not generate new archives inside `_run_boundary2_chain()`.

The expected archive SHA and size must come from Boundary-1 package provenance, not be recomputed and treated as a new source of truth.

### C4. Reuse the same archives in final package provenance

Final package provenance must be merged from the original package-provenance records selected in the candidate/pre-tag artifacts. Do not create final stub archives, binaries, lockfiles, or replacement provenance records.

If a final merged provenance document is generated, it must merge the selected original records and verify:

- candidate SHA and version;
- exact archive path/identity;
- exact package-specific lockfile identity;
- exact built executable identity where applicable;
- exact source artifact binding.

### C5. Add an explicit archive-lineage validator

Add a production validation function or subcommand that proves:

- protocol archive digest equals sparse index checksum and protocol-index archive checksum;
- dependent Boundary-1 archive digest equals Boundary-2 candidate archive digest;
- command index archive-before and archive-after identities equal Boundary-1 identity;
- final package provenance archive identity equals Boundary-1 identity;
- one package cannot reference another package’s archive;
- no replacement archive appears after the initial package stage.

### Workstream C acceptance criteria

- [ ] Exactly one packaged archive is created per crate in qualification.
- [ ] Candidate/pre-tag artifacts contain those exact archives and provenance.
- [ ] The local sparse registry serves the selected protocol archive bytes.
- [ ] Boundary 2 consumes the selected dependent archive bytes.
- [ ] Final package provenance reuses the original selected provenance records.
- [ ] No `final-*.crate` stub or replacement archive creation remains.
- [ ] Archive SHA-256 and size are identical across all applicable boundaries.
- [ ] A one-byte archive mutation at any boundary fails.
- [ ] A repacked byte-different but semantically equivalent archive fails.
- [ ] Swapped package archives fail.
- [ ] Missing package-specific lockfile or executable lineage fails.

2. create decision and identity files inside that root;
3. write installed-verification synthetic evidence;

5. run production `write-candidate --artifact-root`;

7. register that ZIP with the mock API;
8. add its exact run and artifact identity to final selection;

### D3. Derive role records from retrieved candidate declarations

- verify the candidate-declared digest and size;

### D4. Preserve operator decision identity

Document the chosen model in `architecture/release-evidence.md` and protect it in workflow validation.
