# Phase 14: version 1.0.1 final release execution

## Objective

Close the final two source-level defects, repair the release-candidate workflow so it can produce authoritative evidence, execute every remaining native and operational gate, and publish a traceable `1.0.1` release of all three crates.

The implementation baseline for this plan is:

```text
ea58735bcc870ace88634c3c7b708b789b144222
```

Phase 13 successfully implemented the major remaining source corrections:

- correct launchd domain/service-target separation and production plist discovery;
- transactional, cross-process-locked `gregg edit`;
- common daemon failure cleanup with bounded task joining;
- bounded macOS native collector retries;
- an initial release-candidate workflow;
- replacement of the stale evidence document with an explicit blocker ledger.

Preserve those changes. Phase 14 is not a new architecture phase and must not reopen completed client, daemon, protocol, collector, TUI, or packaging design work. Its purpose is to make the last source details correct, make the release machinery truthful and executable, run the remaining gates, and complete publication.

## Current release disposition

At the baseline commit:

- workspace source is versioned `1.0.1`;
- crates.io contains only unyanked `1.0.0` releases of `gregg-protocol`, `greggd`, and `gregg`;
- no `v1.0.1` tag resolves;
- launchd `stop()` is not idempotent from an already-unloaded state;
- client atomic writes do not explicitly preserve or establish user-only permissions;
- the release-candidate workflow accepts a ref but compares the literal input to `HEAD`, so tag inputs fail;
- package verification runs all three crates concurrently even though the binary crates require indexed `gregg-protocol 1.0.1`;
- the daemon loopback smoke is absent and masked by `|| true`;
- Linux ARM64, systemd lifecycle, launchd lifecycle, resource, and soak evidence remain unavailable;
- workflow artifacts are not uploaded as durable evidence;
- the final evidence document contains inconsistent test counts and candidate terminology;
- several registry rows overstate evidence-dependent completion.

`1.0.1` remains an unfrozen source candidate.

## Workstream A: final source correctness

### A1. Make launchd stop idempotent

The current launchd implementation calls `bootout()` unconditionally. Define state-aware behavior:

| State | `stop()` behavior |
| --- | --- |
| `NotLoaded` | return success without invoking `bootout` |
| `Loaded` | invoke `bootout` and require success |
| `Running` | invoke `bootout` and require success |
| state-query execution/permission failure | return the original actionable error |

Implementation requirements:

- call `state()` before `bootout()`;
- do not translate permission, malformed-target, or launchd-unavailable failures into idempotent success;
- retain the existing distinction between domain targets and service targets;
- retain exact argument-array construction;
- document that stop means unload, matching the installer and CLI documentation;
- ensure repeated `stop` calls succeed after the first successful unload.

Add deterministic command-runner or argument/state tests proving:

1. `NotLoaded` returns success and never calls `bootout`;
2. `Loaded` calls `bootout` exactly once;
3. `Running` calls `bootout` exactly once;
4. state query failure propagates;
5. bootout failure propagates;
6. two consecutive stops are idempotent in a stateful fake runner.

Native macOS evidence remains required later; unit tests are not a substitute.

### A2. Preserve secure client config permissions

`Config::write_atomic()` creates a replacement temporary file and renames it over the live file. Explicitly define permission semantics.

Required Unix policy:

- if the destination exists, preserve its permission mode unless it is broader than the accepted client security policy;
- if the destination does not exist, create the replacement with mode `0600`;
- never allow an edit transaction to replace a `0600` file with a mode derived only from a permissive process umask;
- do not change ownership deliberately; the rename must remain within the same user-owned configuration directory;
- the parent directory durability sync must remain intact.

A simpler acceptable policy is to force the final client config to `0600` on every write. If selected, document it and test it consistently.

Implementation order:

1. determine the target mode before creating the atomic replacement;
2. create the temporary file with explicit `OpenOptions` rather than `fs::write` where needed;
3. set permissions before writing sensitive content or immediately after creation;
4. write all bytes;
5. flush and `sync_all`;
6. rename atomically;
7. sync the parent directory;
8. verify final mode in tests.

Add Unix tests for:

- new config is `0600` under a permissive umask;
- existing `0600` remains `0600` after `add`, `remove`, `refresh`, and `edit`;
- invalid edit leaves original bytes and permissions unchanged;
- editor failure leaves original bytes and permissions unchanged;
- atomic replacement does not expose a broad-permission intermediate file;
- lock and temp files do not become active configuration files.

Non-Unix behavior may retain existing semantics but must compile and remain documented.

### A3. Correct lock-file semantics and documentation

The lock-acquisition comment says the lock file is opened without truncation, but the implementation currently uses `.truncate(true)`.

Preferred correction:

- remove `.truncate(true)`;
- retain the existing lock inode across acquisitions;
- acquire `flock` on the opened descriptor;
- never delete the lock file during normal release;
- leave stale-inode behavior documented as harmless because lock ownership is descriptor-based.

If truncation is intentionally retained, update the comment and prove it cannot interfere with a process already holding a lock on the same inode. Removing truncation is simpler and less surprising.

Add or retain tests demonstrating:

- concurrent processes serialize mutations;
- closing the descriptor releases the lock;
- a persistent empty lock file does not imply a stale lock;
- repeated acquisitions do not replace the lock inode unexpectedly where the platform exposes inode identity.

### A acceptance criteria

1. `stop()` succeeds when the service is already not loaded.
2. `stop()` propagates real state and bootout failures.
3. Repeated native launchd stops are idempotent.
4. New client configuration files are user-only on Unix.
5. Atomic rewrites and edit transactions preserve the selected secure mode.
6. Invalid edits preserve original content and mode.
7. Lock-file implementation and documentation agree.
8. Existing cross-process mutation tests remain green.

## Workstream B: make candidate identity exact

### B1. Resolve refs instead of comparing strings

The workflow currently compares `git rev-parse HEAD` to the literal `candidate_ref` input. Replace this with explicit resolution.

Acceptable designs:

#### Design 1: SHA-only input

- rename the input to `candidate_sha`;
- require a full 40-character lowercase or uppercase hexadecimal commit SHA;
- reject branches, abbreviated SHAs, and tags;
- checkout the SHA;
- compare `git rev-parse HEAD` to the normalized full SHA.

#### Design 2: ref plus resolved SHA

- retain `candidate_ref`;
- after fetch, resolve it with `git rev-parse "${candidate_ref}^{commit}"`;
- compare `HEAD` to the resolved commit SHA;
- print both the input ref and resolved SHA;
- reject ambiguous or missing refs.

Design 2 is preferred because it can verify both a frozen commit and the final annotated tag.

### B2. Make candidate mutation impossible during a run

Every job must:

- check out the resolved commit, not a moving branch tip;
- record the exact SHA in job output;
- fail if the requested ref resolves differently from the workflow's frozen candidate output;
- use the same SHA across all jobs;
- include the SHA in artifact names and manifests.

Add a small `resolve-candidate` job whose outputs are consumed by all other jobs:

```yaml
outputs:
  candidate_sha: ${{ steps.resolve.outputs.candidate_sha }}
  candidate_version: ${{ steps.resolve.outputs.candidate_version }}
```

All later jobs should use `needs.resolve-candidate.outputs.candidate_sha`.

### B3. Verify release metadata at the candidate

The resolve job must fail unless:

- workspace version is exactly `1.0.1`;
- all inter-crate dependency requirements are exactly compatible with `1.0.1`;
- the worktree is clean after checkout;
- `Cargo.lock` is present and consistent;
- changelog contains the intended `1.0.1` section;
- the candidate is reachable from the expected protected/default branch unless an explicit exception is documented.

### B acceptance criteria

1. Full commit SHAs verify successfully.
2. Annotated tag inputs resolve and verify successfully.
3. Invalid or ambiguous refs fail before package work starts.
4. All jobs consume one immutable resolved SHA.
5. Artifact names identify the exact candidate SHA.

## Workstream C: implement dependency-aware package stages

The existing matrix cannot verify binary packages before `gregg-protocol 1.0.1` exists in the crates.io index. Split release verification into explicit stages.

### C1. Define workflow stages

Use an explicit `stage` workflow input with these values:

- `protocol-prepublish`
- `binary-prepublish`
- `native-evidence`
- `operational-evidence`
- `postpublish-verify`
- `full-available`

`full-available` may run all stages that are valid given current registry state, but must fail clearly rather than silently skipping an unmet dependency.

Alternatively, separate workflows are acceptable if they share scripts and evidence formats. Do not duplicate complex shell logic across files without tests.

### C2. Protocol prepublication job

For `gregg-protocol 1.0.1`:

1. run `cargo package -p gregg-protocol --list`;
2. run verified `cargo package -p gregg-protocol` without dirty/no-verify bypasses;
3. locate `target/package/gregg-protocol-1.0.1.crate` exactly;
4. compute SHA-256;
5. unpack to a fresh directory;
6. record the normalized manifest;
7. build and test unpacked source under stable;
8. build and test or at least build unpacked source under Rust 1.75;
9. build a clean external consumer against the unpacked package or local registry representation;
10. upload all evidence artifacts.

This stage must not attempt binary package verification unless the indexed protocol version is available.

### C3. Protocol index prerequisite

Before binary prepublication jobs run:

- query crates.io/index metadata for `gregg-protocol 1.0.1`;
- require it to be present and not yanked;
- record its published checksum and timestamp;
- build a clean consumer that resolves the registry copy, not the workspace path;
- fail with an explicit `protocol 1.0.1 is not indexed` message if unavailable.

Do not treat a cached local workspace package as indexed proof.

### C4. Binary prepublication jobs

After the protocol index prerequisite succeeds, verify `greggd` and `gregg` in parallel or sequentially:

1. run `cargo package --list`;
2. run verified `cargo package` without `--allow-dirty` or `--no-verify`;
3. locate exact archives under `target/package/`;
4. compute SHA-256;
5. unpack into separate fresh directories;
6. inspect normalized manifests and included files;
7. build and test unpacked sources under stable;
8. build unpacked sources under Rust 1.75;
9. install each package under an empty `--root`;
10. run strict installed-binary smokes;
11. upload archive metadata, logs, and checksums.

### C5. Avoid false `--locked` assumptions

A normalized `.crate` archive may not contain the workspace lockfile in a form usable by `cargo install --path --locked`. Test the actual archive behavior.

- use `--locked` only when a valid included lockfile exists;
- otherwise generate or vendor a deterministic lockfile during verification and record it;
- do not weaken MSRV checks by silently resolving a different dependency graph without recording it.

### C acceptance criteria

1. Protocol verification runs independently before publication.
2. Binary verification cannot run until indexed protocol `1.0.1` is proven.
3. No matrix race attempts all three packages concurrently before indexing.
4. Every archive is located from `target/package` and checksummed.
5. Every unpacked package builds from a clean directory.
6. Both binaries install into empty roots and execute.
7. Stable and Rust 1.75 package-source builds are recorded.
8. All package outputs are uploaded as immutable artifacts.

## Workstream D: make runtime smoke tests authoritative

### D1. Add a repository-owned loopback script

Create an executable script such as:

```text
scripts/verify-installed-daemon.sh
```

It must accept the installed `greggd` path and an optional port/config root.

Required behavior:

1. create an isolated temporary directory;
2. select a free loopback port deterministically or through a safe helper;
3. create a valid daemon config bound to `127.0.0.1`;
4. start the installed binary in foreground mode as a child process;
5. capture stdout/stderr and PID;
6. poll `/healthz` with a bounded startup deadline;
7. require transition to a valid ready response;
8. query `/v1/status`;
9. parse JSON and validate key schema fields and schema version;
10. send the documented termination signal;
11. require bounded clean process exit;
12. print logs on failure;
13. clean all child processes and temporary files through a trap.

The script must return nonzero on every failed condition.

### D2. Remove all failure masking

Delete `|| true` from release-evidence commands unless the command is explicitly probing an expected failure and the exit code is asserted afterward.

Specifically:

- missing loopback scripts must fail;
- daemon startup failure must fail;
- health timeout must fail;
- malformed JSON must fail;
- process cleanup timeout must fail;
- binary `--help` and `--version` failures must fail.

### D3. Verify the installed client

For the clean-installed `gregg` binary:

- run `--help` and version output if supported;
- use an isolated config path;
- run `add` with a custom default port case;
- run `list --json` and parse it;
- run `refresh`;
- run `remove` exact and host-wide cases;
- use a deterministic noninteractive fake editor to exercise a valid edit transaction;
- verify final config permissions on Unix;
- avoid launching the TUI in noninteractive CI.

### D4. Test scripts themselves

- run shellcheck;
- add a short CI test that invokes expected-failure paths;
- ensure traps clean child processes when a check fails;
- avoid dependencies not preinstalled on every selected runner, or install and record them explicitly.

### D acceptance criteria

1. The daemon loopback script exists in the repository.
2. The workflow invokes the installed package binary, not the workspace target by accident.
3. No authoritative smoke command is masked by `|| true`.
4. Health and status JSON are validated.
5. Child processes are always cleaned up.
6. Client noninteractive configuration behavior is verified from the installed package.

## Handoff rule

An implementing agent may complete source and workflow corrections without publication credentials or every native host. It must not mark Phase 14 complete in that state.

When blocked, the agent must leave:

- source and workflow changes committed separately;
- the exact candidate or pre-candidate SHA;
- the exact unexecuted command or workflow stage;
- the required host, privilege, runner label, duration, or credential;
- partial artifacts already generated;
- the next safe action;
- affected acceptance-criterion numbers.

The following are not closure evidence:

- green source-only CI;
- fixture-based ARM64 tests;
- macOS mock collector tests;
- source inspection of systemd or launchd commands;
- version bumps without indexed packages;
- console-only checksums with no preserved artifact;
- an unbounded, skipped, or failure-masked smoke test;
- cross-compilation without native collector execution;
- short runs labeled as 24-hour soaks;
- source reasoning substituted for measured values.

Phase 14 closes only after the exact tagged and published source has complete package, native, lifecycle, resource, soak, dependency, registry-install, and publication evidence.
