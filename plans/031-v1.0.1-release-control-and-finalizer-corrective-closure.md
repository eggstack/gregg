# Phase 31: `v1.0.1` release-control and finalizer corrective closure

## Objective

Close the remaining release-control defects that survived Phases 18, 19, 21, and 22 so that Phase 30 can freeze one candidate and execute a coherent, fail-closed release sequence.

This phase is deliberately narrow. It does not implement the product and platform corrections already owned by Phases 23 through 29. It corrects the machinery that selects workflow runs, validates sustained evidence, resolves package provenance, sequences the multi-crate publication, retrieves immutable artifacts, materializes final inputs, and produces independently valid pre-tag and final manifests.

The implementation baseline for this phase is:

```text
5109768d02c91c850c4e93b1a18cc9081e1e357a
```

At this baseline, `v1.0.1` remains a no-go.

## Current disposition

The following improvements have already landed and must be preserved:

- authenticated GitHub artifact retrieval through `GITHUB_TOKEN`;
- ZIP download, hashing, bounded extraction, and candidate validation;
- graph-aware workflow dependency validation;
- a production-path sustained workload using `PollScheduler`, `HttpClient`, and `AppState`;
- live `/proc` sampling of the workload process;
- bounded child cleanup;
- separate package provenance and lockfiles for `greggd` and `gregg`;
- immutable candidate checkout in finalization;
- pre-tag and final aggregation modes.

The following blockers remain:

1. `mixed-fleet-client` current-run aggregation requires a sustained stage that can only be produced by a separate dispatch.
2. The workflow validator does not validate the per-dispatch aggregate-stage contract.
3. The sustained runner does not fail immediately on a nonzero workload exit.
4. Sustained summary fields are checked for presence but not for qualifying values.
5. `max_concurrent_polls` currently records batch cardinality rather than observed active polls.
6. Scheduler cancellation is requested but clean shutdown is not positively observed.
7. The checked-in run-selection example uses grouped binary stage names that do not exist in candidate metadata.
8. Retrieval associates every artifact in a selected run with every logical stage instead of selecting the exact containing artifact.
9. Package provenance ownership is inferred from stage strings; `protocol-prepublish` therefore cannot populate `gregg-protocol` provenance reliably.
10. Registry summary and `1.0.0` disposition files are not deterministically materialized for final mode.
11. Numeric GitHub artifact identity remains optional in aggregated manifests.
12. The current release order requires `gregg-protocol 1.0.1` to be indexed before the pre-tag gate that is supposed to authorize publishing it.
13. The finalizer lacks a full synthetic test covering all required stage classes and successful final-mode aggregation.
14. Plan and evidence status can drift from the implementation state.

## Governing invariants

1. **One logical stage, one selected artifact.** Every required logical stage resolves to exactly one GitHub artifact containing its matching `candidate.json`.
2. **Run identity and artifact identity are distinct.** Workflow run ID, run attempt, numeric artifact ID, artifact name, ZIP SHA-256, and ZIP size are separate required fields.
3. **Current-run aggregation describes only the current dispatch.** A dispatch must never require evidence that only another dispatch can produce.
4. **Cross-run aggregation owns release completeness.** The finalizer combines independently selected dispatch artifacts into the complete release manifest.
5. **Sustained evidence is semantic.** File existence and field presence are insufficient; the observed values must satisfy the workload contract.
6. **Package ownership comes from provenance content.** Stage names and filesystem ordering are not authoritative package identifiers.
7. **Final inputs are declared.** Registry and disposition evidence must be selected and indexed, not discovered by broad `find` commands or assumed root paths.
8. **Publication ordering must be satisfiable.** A gate cannot require a registry record that the same gate sequence has not yet authorized publishing.
9. **Pre-tag and final manifests have different contracts.** Pre-tag mode must not require postpublication evidence; final mode must require it.
10. **Validation fails closed.** Missing, duplicate, ambiguous, malformed, nonqualifying, or unbound evidence exits nonzero.
11. **Examples are executable fixtures.** Checked-in example selection files must pass schema validation and synthetic retrieval tests.
12. **No release status by assertion.** A plan is complete only when local tests and a nonpublishing workflow run demonstrate the acceptance criteria.

## Workstream B: close sustained-evidence semantics

### Exit handling

After the child exits, the runner must reject any nonzero exit code before accepting its summary as qualifying evidence.

Required behavior:

```text
exit_code == 0
summary exists
summary parses
summary satisfies all semantic checks
resource samples satisfy all semantic checks
```

A stale summary left from an earlier run must not allow a failed child to pass. The runner already removes previous evidence files; preserve that behavior and add a regression test.

### Required summary checks

The runner must require:

- `requested_duration_secs` equals the configured duration;
- `observed_duration_secs >= requested_duration_secs` within documented clock precision;
- externally measured monotonic duration is also at least requested duration;
- `endpoint_count >= 3` and equals the configured workload endpoint count;
- `completed_generations >= 2`;
- `first_generation > 0`;
- `last_generation >= first_generation`;
- generation accounting is internally consistent;
- `online_results > 0`;
- `offline_results > 0`;
- `observed_transitions` is a nonempty array of nonempty strings;
- `clean_shutdown is true`;
- `panic_or_join_failure` is null;
- observed active poll concurrency is positive and does not exceed the configured limit.

The workflow must copy actual validated values into candidate notes. It must not use unvalidated values merely because they exist in JSON.

### Correct concurrency measurement

Do not calculate active concurrency from `batch.results.len()`. That is endpoint cardinality.

Implement test-only instrumentation around the production `HttpClient::poll` path. Preferred shape:

```rust
#[cfg(test)]
#[derive(Clone)]
pub struct PollActivityObserver {
    active: Arc<AtomicUsize>,
    peak: Arc<AtomicUsize>,
}
```

A guard should increment immediately before the production request future begins and decrement on every return path, including error and cancellation. `HttpClient` may accept an optional observer only under `cfg(test)` or through a test-only constructor. Normal production behavior and public package API must remain unchanged.

The sustained summary should record:

```json
{
  "configured_max_concurrent_polls": 4,
  "observed_max_concurrent_polls": 4
}
```

If a differently named field is used, it must distinguish configured from observed values.

### Positive shutdown observation

The workload must not record clean shutdown immediately after `cancel.cancel()`.

Provide a completion signal or joinable scheduler handle in the test path. Acceptable approaches:

1. a test-only `run_with_handle()` method returning the batch receiver and join handle;
2. a scheduler completion oneshot used only by tests;
3. another narrow mechanism that proves the scheduler loop exited after cancellation.

The summary may set `clean_shutdown: true` only after the scheduler task has completed within a bounded deadline. Timeout, panic, or join failure must produce a nonzero workload result and a non-null diagnostic.

### Required negative tests

The actual runner validation path must reject:

- nonzero child exit with a syntactically valid summary;
- requested-duration mismatch;
- insufficient observed duration;
- zero or one completed generation;
- inconsistent generation range;
- zero online results;
- zero offline results;
- empty transitions;
- `clean_shutdown: false`;
- non-null panic/join failure;
- observed concurrency of zero;
- observed concurrency above the configured limit;
- missing or stale summary;
- insufficient resource samples;
- wrong PID;
- zero RSS;
- nonmonotonic sample timestamps;
- last sample before the required runtime fraction.

Tests that only duplicate boolean expressions in the test body do not qualify. Extract validation into callable functions and invoke those functions from both the runner and tests.

## Workstream C: normalize the run-selection schema

### One selection entry per logical stage

The selection file must use the exact logical stage emitted by `candidate.json`.

Replace grouped entries such as:

```text
binary-prepublish
binary-msrv
```

with:

```text
binary-prepublish-greggd
binary-prepublish-gregg
binary-msrv-greggd
binary-msrv-gregg
```

Multiple logical stages may select the same workflow run, but each stage entry must identify only the artifact expected to contain that stage.

Example:

```json
{
  "binary-prepublish-greggd": {
    "run_id": 1004,
    "attempt": 1,
    "workflow_name": "release-candidate",
    "artifacts": [{"name": "binary-greggd-abcdef01-1"}]
  },
  "binary-prepublish-gregg": {
    "run_id": 1004,
    "attempt": 1,
    "workflow_name": "release-candidate",
    "artifacts": [{"name": "binary-gregg-abcdef01-1"}]
  }
}
```

### Selection validation

Reject:

- a selected stage absent from all selected artifact candidate metadata;
- one stage selecting more than one containing artifact;
- one artifact name resolving to more than one numeric artifact ID in the selected run;
- a selected artifact containing multiple `candidate.json` records for the same stage;
- a run attempt that does not equal the API-reported selected attempt;
- duplicate logical stage keys;
- grouped aliases not present in `release-requirements.json`;
- stage names not declared by the requirements contract.

The checked-in example must be used by tests, not treated as documentation-only JSON.

## Workstream D: bind each stage to its exact GitHub artifact

### Retrieval record

For each logical stage, write exactly one artifact object:

```json
{
  "stage": "binary-prepublish-greggd",
  "run": {
    "run_id": 1004,
    "run_attempt": 1,
    "workflow_name": "release-candidate",
    "head_sha": "<40-char-sha>",
    "conclusion": "success"
  },
  "artifact": {
    "github_artifact_id": 123456789,
    "github_artifact_name": "binary-greggd-abcdef01-1",
    "downloaded_zip_sha256": "<64-char-sha256>",
    "downloaded_zip_size_bytes": 12345,
    "github_reported_size_bytes": 12345,
    "extraction_path": "...",
    "candidate_metadata_path": ".../candidate.json",
    "candidate_metadata_sha256": "<64-char-sha256>"
  }
}
```

An array containing unrelated artifacts from the same run is not an acceptable stage binding.

### Artifact filtering

When a run contains multiple artifacts, compute `found_in` and persist only the single matching artifact for the logical stage. Do not attach all `artifact_specs` from the run to every stage.

### Mandatory aggregated identity

When `--retrieved-manifest` is supplied, every required stage must contain a complete `github_artifact` record. Validation must require:

- integer ID greater than zero;
- exact nonempty name;
- lowercase 64-character ZIP SHA-256;
- positive ZIP size;
- run ID and attempt matching the candidate metadata;
- candidate metadata path and digest;
- candidate SHA matching the manifest candidate.

The semantic `artifact_ids` list may remain as content metadata for backward compatibility, but it must not satisfy immutable artifact identity requirements.

### Ambiguity policy

A stage with zero or more than one containing artifact fails. Do not choose `artifacts[0]`, traversal order, lexical order, or the first successful match.

## Workstream E: index package provenance by document content

### Required behavior

For every extracted `package-provenance.json`:

1. parse the document;
2. validate its candidate SHA and release version;
3. read the exact package keys from its `packages` object;
4. require one package key for a per-package provenance file unless the schema explicitly permits a merged record;
5. map the package key to the provenance path, digest, lockfile, archive, logical stage, and artifact identity;
6. reject conflicting records for the same package and stage.

Do not infer package identity from:

- stage names;
- parent directory names;
- artifact names;
- `.crate` filename alone;
- filesystem discovery order.

### Required provenance-index shape

The exact schema may vary, but it must provide deterministic package selection:

```json
{
  "packages": {
    "gregg-protocol": {
      "stage": "protocol-prepublish",
      "provenance_path": "...",
      "provenance_sha256": "...",
      "archive_path": "...",
      "archive_sha256": "...",
      "artifact_id": 123
    },
    "greggd": {},
    "gregg": {}
  }
}
```

Use an object rather than an arbitrary list when exactly one selected record is required.

### Lockfile association

Associate lockfiles by package-specific evidence metadata or provenance declaration. Do not select the first `Cargo.lock` under an artifact if more than one exists.

A missing, duplicate, or mismatched package record must prevent merged provenance generation.

## Workstream F: deterministically materialize final-mode inputs

### Registry summary

The postpublication workflow must emit `registry-summary.json` as an artifact entry with a `role` field, not an undocumented `artifact_id` substitute.

Retrieval must index declared evidence files by role and bind them to the artifact that contains the matching candidate stage.

For final mode, materialize or pass the exact indexed path for:

```text
registry-summary
```

Do not assume it exists at `evidence/registry-summary.json` unless the retrieval tool explicitly copied and verified it there.

### `1.0.0` disposition

The postpublication workflow must query the current crates.io records for all three `1.0.0` crates and write a structured disposition file containing at least:

```json
{
  "gregg-protocol": {
    "version": "1.0.0",
    "yanked": false,
    "checksum": "...",
    "observed_at": "..."
  },
  "greggd": {},
  "gregg": {}
}
```

Name the artifact role:

```text
version-1.0.0-disposition
```

Retrieval must index and materialize this file exactly as it does the registry summary. Do not rely on a manually created untracked file.

### Role validation

Candidate artifact entries must use one schema consistently:

```json
{"name":"registry-summary.json","role":"registry-summary"}
```

Reject missing role, duplicate singleton role, path escape, missing declared file, or digest mismatch.

### Finalizer interface

Preferred behavior:

- the retrieval manifest contains a top-level `evidence_files` index;
- the aggregation wrapper receives the retrieved manifest and resolves singleton evidence roles itself;
- finalizer shell does not hard-code extracted filesystem locations.

A materialization helper is acceptable if it copies only a uniquely indexed, digest-verified source and records the source path and digest in the final manifest.

## Workstream G: repair the multi-crate release sequence

### Baseline deadlock

At baseline:

- binary package gates depend on `protocol-index-check`;
- `protocol-index-check` requires `gregg-protocol 1.0.1` on crates.io;
- pre-tag requirements include `protocol-index-check` and binary package evidence;
- Phase 30 says pre-tag aggregation authorizes tag creation and publication.

This requires the protocol crate to be published before the gate that authorizes publishing it.

### Required release model

Use a satisfiable three-boundary model.

#### Boundary 1: candidate qualification before tag or publication

Require:

- source CI;
- protocol archive and local package verification;
- binary archive creation;
- binary archive verification against the exact candidate protocol package through a temporary Cargo patch/config;
- source-native evidence;
- package-native evidence using the exact candidate archives and exact candidate protocol package;
- mixed-fleet functional and sustained evidence;
- lifecycle/resource/soak evidence;
- complete package provenance;
- immutable GitHub artifact identity.

Do **not** require crates.io `gregg-protocol 1.0.1` at this boundary.

#### Boundary 2: protocol publication and dependent-package registry qualification

After Boundary 1 passes and the annotated tag is created according to Phase 30:

1. publish `gregg-protocol 1.0.1`;
2. wait for crates.io API and index availability;
3. run `protocol-index-check`;
4. re-verify the already selected `greggd` and `gregg` archives against the actual registry protocol dependency;
5. compare the reverified archive checksums with the Boundary 1 provenance;
6. authorize publication of `greggd` and `gregg` only if all checks pass.

No source rebuild or archive replacement is permitted between boundaries.

#### Boundary 3: postpublication and final aggregation

After all three crates are indexed:

- install registry binaries into clean roots;
- execute postpublication verification;
- produce registry summary and `1.0.0` disposition;
- run final aggregation.

### Binary archive creation before protocol publication

If `cargo package` verification cannot resolve unpublished `gregg-protocol = 1.0.1`, use:

```text
cargo package --no-verify
```

only when followed immediately by stricter independent verification:

- unpack the exact `.crate` archive;
- verify normalized manifest and file list;
- configure a temporary `[patch.crates-io]` or command-line Cargo patch pointing to the exact unpacked `gregg-protocol-1.0.1` candidate archive/source;
- run build and tests from the unpacked binary archive;
- install from the unpacked archive with `--locked` and the exact package-specific lockfile;
- record the patch source digest and package provenance;
- fail if any dependency resolves from an unintended local workspace path.

`--no-verify` by itself is forbidden.

### Requirements contract changes

Split stage requirements by boundary. Recommended fields:

```json
{
  "candidate_required_stages": [],
  "protocol_publication_required_stages": ["protocol-index-check"],
  "final_required_stages": []
}
```

Do not retain `protocol-index-check` in the pre-publication candidate boundary if it requires crates.io availability.

The final manifest must include evidence from all boundaries.

## Stop conditions

Stop implementation and report the blocker when:

- the selected artifact contract cannot uniquely bind a stage;
- candidate and artifact metadata disagree on SHA, version, run, or attempt;
- the pre-publication package verification requires an undocumented network or workspace dependency;
- a binary archive changes after its provenance is recorded;
- sustained concurrency cannot be measured on the production request path;
- scheduler completion cannot be observed without expanding public production API scope;
- final evidence roles are ambiguous;
- candidate and final boundary requirements remain cyclic;
- a test is made green by weakening a release requirement;
- implementation requires changes owned by Phases 23 through 29.

Do not work around a stop condition with traversal order, hard-coded temporary paths, `|| true`, optional identity fields, reduced duration, source-only evidence, or prose justification.
