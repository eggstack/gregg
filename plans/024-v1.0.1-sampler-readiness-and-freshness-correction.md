# Phase 24: `v1.0.1` sampler readiness and freshness correction

## Objective

Separate collector readiness, last valid snapshot retention, and snapshot freshness so a warming or reset collector cannot be reported as ready merely because an older snapshot still exists.

## Recommended dependency

Complete Phase 23 first so macOS high-bit counter corruption is not confused with readiness behavior. The readiness fix must still handle genuine counter resets on every platform.

## Baseline defect

At baseline `eab5fe2e1d8f4635bb09aaf4ba69e18375ff5671`:

- `crates/greggd/src/sampler.rs::sample_once()` returns early for a sample with no CPU percentage;
- `CollectErrorKind::Warming` and `CounterReset` log a message but do not change `self.readiness`;
- after a previous successful sample, `self.readiness` therefore remains `Ready` and `self.snapshot` remains the old snapshot;
- `Sampler::run()` invokes the callback with `Ready` and the old snapshot;
- `crates/greggd/src/run.rs::sync_sampler_state()` calls `ServerState::update_snapshot()` for that old snapshot;
- `update_snapshot()` resets server failure counters and marks the server ready;
- age-based staleness may eventually make HTTP handlers return `503`, while the stored health body can still describe a prior ready state.

The last valid snapshot is useful and should normally be retained, but its existence must not overwrite the current collector state.

## Scope

### In scope

- `crates/greggd/src/sampler.rs`;
- `crates/greggd/src/run.rs`;
- `crates/greggd/src/server/mod.rs` and its tests;
- protocol use only as needed to represent existing `Ready`, `Warming`, and `Failed` states correctly;
- documentation of `/v1/status` and `/healthz` semantics.

### Out of scope

- changing JSON schema version 1;
- adding a new public stale-snapshot protocol variant;
- changing sampling intervals;
- changing collector implementations beyond reset signaling;
- adding authentication or TLS;
- removing cached snapshot serving.

## Required state model

Represent these concepts independently:

1. **Collector state:** `Warming`, `Ready`, or `Failed`.
2. **Last valid snapshot:** optional immutable snapshot from the most recent successful sample.
3. **Freshness:** whether the last valid snapshot is still within the configured staleness policy.
4. **Failure count:** consecutive hard collection failures, separate from normal warming/reset events.

Do not use “snapshot exists” as a synonym for “collector ready.”

## Required transition table

Implement and test behavior equivalent to:

| Previous collector state | Sample outcome | New collector state | Snapshot action | Health status |
| --- | --- | --- | --- | --- |
| Warming | valid fresh sample | Ready | replace snapshot | 200 |
| Ready | valid fresh sample | Ready | replace snapshot | 200 |
| Failed | valid fresh sample | Ready | replace snapshot and reset failures | 200 |
| Warming | warming/no delta | Warming | preserve optional prior snapshot | 503 |
| Ready | warming/no delta | Warming | preserve prior snapshot | 503 |
| Ready | counter reset | Warming | preserve prior snapshot, discard collector baseline | 503 |
| Failed | warming after recovery attempt | Warming | preserve prior snapshot | 503 |
| any | hard collection failure | Failed | preserve prior snapshot | 503 |

A preserved snapshot may remain available from `/v1/status` while it is within the configured stale window. That does not make `/healthz` ready.

## Suggested internal API

Prefer an explicit update value rather than passing a readiness enum plus an ambiguous optional snapshot.

Example shape:

```rust
pub enum SamplerUpdate {
    Fresh(Arc<StatusSnapshot>),
    Warming {
        reason: WarmingReason,
        last_valid: Option<Arc<StatusSnapshot>>,
    },
    Failed {
        category: HealthCategory,
        message: String,
        last_valid: Option<Arc<StatusSnapshot>>,
        consecutive_failures: u32,
    },
}
```

A smaller struct with fields is also acceptable. The important property is that a callback can distinguish:

- a newly produced snapshot;
- an old retained snapshot;
- current collector state.

Do not call `update_snapshot()` unless a new valid snapshot was produced in that collection cycle.

## Sampler changes

### Fresh sample

On a valid sample with CPU percentage:

- create a new snapshot;
- set collector state to `Ready`;
- reset hard failure count;
- replace `last_valid_snapshot`;
- emit `Fresh(new_snapshot)`.

### Warming or no CPU delta

On `cpu_usage_pct.is_none()` or `CollectErrorKind::Warming`:

- set collector state to `Warming` even if previously `Ready`;
- preserve `last_valid_snapshot`;
- do not increment hard failure count;
- emit a warming update;
- do not re-emit the old snapshot as a fresh sample.

### Counter reset

On `CollectErrorKind::CounterReset`:

- set collector state to `Warming`;
- preserve the last valid snapshot;
- do not report ready;
- ensure the collector has discarded or replaced the invalid counter baseline;
- emit a distinct reason in logs and tests.

### Hard failure

On other collection errors:

- set collector state to `Failed`;
- increment consecutive hard failures;
- preserve the last valid snapshot;
- emit a failed update with the actual error category/message where practical.

Do not replace all diagnostics with the fixed string `collector failure` when a structured error is available.

## ServerState changes

`ServerState` must expose operations with unambiguous semantics:

```text
publish_fresh_snapshot(snapshot)
set_warming_preserve_snapshot(reason)
set_failed_preserve_snapshot(category, message)
```

Names may differ, but behavior must not.

### Health behavior

`/healthz`:

- returns `200` only when collector state is `Ready` and the snapshot is fresh;
- returns `503` for `Warming`;
- returns `503` for `Failed`;
- returns `503` when a ready snapshot has aged past the stale threshold;
- serializes a body consistent with the current collector state.

A stale ready snapshot must not return a body that still claims healthy readiness.

### Status behavior

`/v1/status` and `/`:

- return `503` when no valid snapshot has ever been produced;
- may return the retained last valid snapshot with its original `observed_at_unix_ms` while it is within the configured stale window, even when the collector is warming or failed;
- return `503` after that snapshot becomes stale;
- never rewrite the old snapshot timestamp to make it appear fresh;
- never reset failure counters merely because the old snapshot is served.

This preserves the existing useful cached-data behavior while making health truthful.

## Freshness computation

Use the snapshot’s original `observed_at_unix_ms` and the configured `stale_after_ms`.

Do not maintain a second contradictory freshness timestamp unless required for monotonic testing. If wall-clock rollback behavior is tested, retain the existing saturating age behavior and document it.

Prefer deriving response health at request time from:

- current collector state;
- last valid snapshot;
- current freshness;
- failure diagnostic.

This is safer than storing a ready `HealthResponse` object that can outlive its freshness.

## Required tests

### Sampler transition tests

1. initial warming -> valid -> ready;
2. ready -> valid -> ready with a newer timestamp;
3. ready -> warming -> collector state warming, old snapshot retained;
4. ready -> counter reset -> warming, old snapshot retained;
5. ready -> hard failure -> failed, old snapshot retained;
6. failed -> valid -> ready and failure count reset;
7. ready -> reset -> valid baseline sequence -> ready recovery;
8. warming/reset does not increment hard failure count;
9. old snapshot is never emitted as `Fresh`;
10. callback observes every transition in order.

### Server state tests

1. initial `/healthz` is `503` warming;
2. fresh snapshot makes `/healthz` `200`;
3. warming after ready makes `/healthz` `503` immediately;
4. failed after ready makes `/healthz` `503` immediately;
5. retained fresh-enough snapshot can still be returned by `/v1/status` with original timestamp;
6. retained snapshot becomes unavailable after stale threshold;
7. stale `/healthz` body does not claim ready;
8. publishing a fresh snapshot restores `200` and resets failure count;
9. warming transition does not clear the snapshot;
10. hard failure increments count exactly once per failed cycle.

### Integration test

Add one deterministic end-to-end test using a scripted collector:

```text
valid -> counter reset -> warming -> valid
```

Assert the HTTP sequence:

```text
health 200 -> health 503 -> health 503 -> health 200
```

During the middle states, `/v1/status` may return the retained snapshot until stale, but its timestamp must remain unchanged.

## Guardrails

- Do not clear the last valid snapshot on a normal counter reset.
- Do not report ready when the current cycle is warming.
- Do not call `update_snapshot()` with an old snapshot.
- Do not refresh `observed_at_unix_ms` without a new collection.
- Do not treat warming as a hard failure count increment.
- Do not change protocol schema version 1.
- Do not broaden `/v1/status` into a historical-data endpoint.
- Do not mask test timing with arbitrary sleeps; use synthetic clocks where possible.

## Acceptance criteria

Phase 24 is complete only when all criteria are demonstrated:

1. Collector state, retained snapshot, freshness, and failure count are represented independently.
2. Warming after ready changes health to `503` immediately.
3. Counter reset after ready changes health to `503` immediately.
4. The old snapshot is retained but is not published as a fresh sample.
5. `/v1/status` preserves the old snapshot timestamp.
6. `/v1/status` stops serving the snapshot after the stale threshold.
7. `/healthz` never returns a body that claims ready when the response status is stale/warming/failed `503`.
8. Hard failures preserve the last valid snapshot and increment the count exactly once.
9. Warming/reset events do not increment hard failure count.
10. A subsequent valid sample restores ready state and resets failures.
11. The valid -> reset -> warming -> valid integration sequence passes.
12. No public protocol schema change is introduced.
13. All targeted sampler, server, and run tests pass.
14. The complete workspace gate passes.
