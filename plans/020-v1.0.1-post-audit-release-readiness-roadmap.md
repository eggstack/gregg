# Phase 20: post-audit `v1.0.1` release-readiness roadmap

## Objective

Close the release-blocking correctness, orchestration, platform, security, and evidence defects found after the Phase 19 implementation pass, then produce one immutable and fully evidenced `v1.0.1` release candidate.

The implementation baseline for this roadmap is:

```text
eab5fe2e1d8f4635bb09aaf4ba69e18375ff5671
```

At that baseline, the repository is **not release ready**. The source tree has substantial test and release machinery, but the remaining defects can prevent a required workflow stage from running, produce invalid macOS CPU samples, report stale readiness incorrectly, accept endpoint configurations that cannot be polled, run the macOS service with excessive privilege, and claim sustained evidence without a sustained live workload.

This roadmap supersedes Phase 19 as the active source of truth for release closure. Phase 19 remains historical evidence of the preceding implementation attempt.

## Release disposition

`v1.0.1` is a **no-go** until phases 21 through 28 are complete.

Do not:

- freeze a candidate SHA;
- create or move the `v1.0.1` tag;
- publish any crate;
- mark the release ledger complete;
- accept source inspection or nominal workflow definitions as evidence.

## Product and architecture contract

Gregg must work correctly on the four advertised native targets:

1. Linux x86-64;
2. Linux ARM64;
3. macOS Intel x86-64;
4. macOS Apple Silicon ARM64.

The protocol and product scope remain narrow:

- `greggd` collects native host metrics and serves a small read-only HTTP/1 API;
- `gregg` polls configured daemons and renders the fleet state;
- no TLS, authentication, remote control, HTTP/2, application serving, Windows support, or generalized release framework is added in this line of work.

## Governing invariants

1. **Correctness before evidence:** do not generate release evidence for code known to be defective.
2. **One concern per phase:** smaller-model agents must not combine unrelated phases in one implementation pass.
3. **One immutable candidate:** every qualifying run and artifact must identify the same full 40-character candidate SHA.
4. **Reachability is executable:** a workflow job is not considered present unless a dispatch input can cause it to run with all dependencies satisfied.
5. **Sustained means live:** compilation time and sequential unit-test duration do not qualify as a sustained workload.
6. **Native means native:** cross-compilation and source inspection do not replace execution on the advertised architecture.
7. **Freshness is explicit:** collector state, last valid snapshot, and snapshot freshness must not be collapsed into one boolean.
8. **Mach counters preserve bit patterns:** unsigned kernel counters must never be sign-extended through signed Rust values.
9. **Persisted configuration is authoritative:** manually edited TOML must receive the same semantic validation as CLI-created entries.
10. **Least privilege by default:** installed services must not run as root unless a documented, tested capability requires it.
11. **Optimization is measurement gated:** no hot-path rewrite may land without preserving semantics and providing before/after evidence.
12. **Evidence is immutable:** run IDs, attempts, artifact IDs, ZIP digests, tag-object SHA, peeled commit SHA, and registry results are recorded separately and accurately.

## Current blocking findings

### P0 release orchestration

- `.github/workflows/release-candidate.yml` allows `mixed-fleet-sustained` as a dispatch stage.
- The mandatory `mixed-fleet-sustained` job depends on `source-ci` succeeding.
- `source-ci` is skipped for the `mixed-fleet-sustained` dispatch value.
- The static workflow validator does not prove input-to-job reachability.

Result: the mandatory sustained stage is structurally unreachable.

### P0 sustained evidence

The current job:

- measures the duration of several sequential `cargo test` invocations;
- includes compilation time in the measured interval;
- samples processes only after tests have exited;
- permits empty resource output;
- fails fast workloads rather than maintaining a workload for the qualifying duration.

Result: the artifact may be named “sustained” without proving a sustained live fleet workload.

### P0 macOS CPU correctness

The Mach FFI reads unsigned `natural_t` CPU counters through `[i32; 4]` and casts each lane directly to `u64`. Once the high bit is set, the cast sign-extends the value. Saturating sums can then pin totals at `u64::MAX`, causing counter-reset or zero-delta behavior.

Result: both Intel and Apple Silicon can stop producing fresh CPU samples on sufficiently long-running hosts.

### P0 readiness and freshness semantics

A warming or counter-reset sample after a previously ready sample can leave the sampler marked ready while re-emitting the old snapshot. The server state can therefore be reset to ready even though the collector requires a new baseline. Age-based staleness eventually produces a `503`, but the stored health body can still describe the wrong state.

Result: `/healthz` and `/v1/status` can disagree with collector reality.

### P1 endpoint and config correctness

- bracketed scoped IPv6 is accepted by the parser but later rendered as an invalid URL;
- persisted endpoint IDs are not required to be nonempty UUIDs;
- persisted hosts do not receive the same canonical validation as CLI input.

Result: valid-looking configuration can be unpollable or internally ambiguous.

### P1 macOS service privilege posture

The system LaunchDaemon has no `UserName` or `GroupName`, so it runs as root. The default daemon bind is `0.0.0.0`, while the service intentionally has no authentication or TLS.

Result: the macOS package has materially weaker least-privilege behavior than the systemd package.

### P1 architecture and hot-path coverage

- ordinary CI has Linux x86-64, macOS ARM64, and macOS x86-64, but no Linux ARM64 lane;
- MSRV is checked only on Linux x86-64;
- the scheduler creates one Tokio task per endpoint and lets most wait on a semaphore;
- the current-thread daemon runtime performs synchronous collection inline;
- status JSON is serialized for every request even though a snapshot is immutable between samples.

Result: one advertised architecture is under-tested and several scaling costs are avoidable, but optimizations must remain subordinate to correctness.

## Smaller-model execution protocol

Every phase plan is written for an agent with limited context. The implementing agent must:

1. read this roadmap and only its assigned phase plan;
2. inspect the named files before editing;
3. add a failing regression test before or with the fix;
4. avoid opportunistic refactors outside the phase scope;
5. run the phase-specific commands;
6. run the complete local gate when feasible;
7. record exact files changed, commands run, and remaining external evidence;
8. stop rather than weaken an acceptance criterion to obtain a green result.

A phase implementation commit should use a subject such as:

```text
fix(<area>): complete phase NN <short description>
```

Do not mark a phase `implemented` merely because code was committed. The phase status changes only after its acceptance criteria are demonstrated.

## Complete local gate

Unless a phase plan states a narrower pre-check, the final implementation pass must run:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-targets --all-features
cargo doc --workspace --no-deps
python3 -m unittest discover -s scripts -p 'test*.py'
for script in scripts/*.sh packaging/*.sh; do bash -n "$script"; done
```

Also run any existing release workflow validator and `shellcheck` commands documented by CI.

Native-only checks must be executed on their native runners. An agent working on Linux must not claim the macOS criteria passed locally.

## Cross-phase acceptance criteria

The line of work is complete only when all of the following are true:

1. Every `workflow_dispatch.stage` value has a tested, satisfiable job path.
2. Every mandatory release stage is emitted by exactly one qualifying artifact.
3. The sustained stage runs a live production-path workload for the configured duration.
4. The sustained stage records multiple nonempty resource samples while the target process is alive.
5. Compilation and setup occur before the sustained timer starts.
6. macOS CPU lanes preserve their unsigned 32-bit bit patterns.
7. wrap, reset, high-bit, and zero-delta CPU cases are deterministic and tested.
8. warming or counter-reset state cannot be reported as ready.
9. the last valid snapshot may be retained, but its age and collector state are represented honestly.
10. scoped IPv6 behavior is either correctly encoded end to end or rejected with a clear diagnostic.
11. persisted endpoint IDs and hosts are validated canonically.
12. the macOS installed service does not combine root execution with an unauthenticated wildcard bind.
13. ordinary CI runs on all four advertised architectures.
14. hot-path changes preserve ordering, cancellation, generation completeness, response schema, and stale-snapshot behavior.
15. one frozen SHA passes source, native, package-native, mixed-fleet, lifecycle, resource, soak, pre-tag, publication, postpublication, and final aggregation gates.
16. the final ledger contains immutable GitHub and crates.io evidence rather than commit abbreviations or prose claims.

## Release-ready definition

Gregg is release ready only when:

- phases 21 through 27 are complete with evidence;
- the complete local gate is green;
- ordinary CI is green on all four native architectures;
- the release workflow is dispatched against one full candidate SHA;
- all required artifacts are downloaded, validated, and aggregated;
- the annotated `v1.0.1` tag identifies the same candidate;
- publication follows the required crate order;
- registry-installed binaries pass verification;
- final aggregation succeeds using actual run IDs, attempts, numeric artifact IDs, and ZIP digests;
- `plans/v1.0.1-final-evidence.md` is reconciled against immutable records.

## Non-goals

Do not use this roadmap to:

- add Windows support;
- add authentication or TLS;
- redesign the protocol schema;
- expand the TUI;
- add remote-control endpoints;
- replace Tokio, axum, reqwest, ratatui, or clap;
- create a generalized benchmark framework;
- rewrite the collectors wholesale;
- reduce required soak or protected-host gates;
- publish a new major or minor version.

Any newly discovered issue belongs in this line of work only when it is required for correctness, safety, advertised architecture support, publishability, release integrity, or the explicit product contract.
