# Phase 13: version 1.0.1 release-gate closure

## Objective

Close the small set of correctness defects and the substantial release-evidence gaps that remain after the Phase 12 implementation, then publish a verifiable `1.0.1` release without broadening Gregg's version-1 scope.

The implementation baseline for this plan is:

```text
19d76c10686fa7d2151be9bd255afed48bb6d6fe
```

Phase 12 materially improved macOS collection, client endpoint handling, configuration mutation locking, polling, response limits, daemon supervision, installers, systemd identity, and dual-architecture macOS CI. Preserve those changes. This phase must not repeat completed work or use unrelated refactoring as a substitute for closing the remaining gates.

## Current release disposition

At the baseline commit:

- the workspace source version is `1.0.1`;
- crates.io still contains only `1.0.0` for `gregg-protocol`, `greggd`, and `gregg`;
- no verified `v1.0.1` annotated tag exists;
- package/archive/install gates were removed from ordinary CI after their first implementation failed;
- the evidence document still describes removed CI steps and explicitly lacks Linux ARM64, native systemd lifecycle, and soak evidence;
- the plan registry incorrectly marks Phase 12 and dependent phases implemented.

`1.0.1` remains a release candidate, not a completed release.

## Scope

### P0 correctness blockers

- Correct launchd bootstrap domain syntax.
- Ensure the production launchd manager always knows the installed plist path.
- Make `stop` followed by `start` work from the normal CLI.
- Make `gregg edit` transactional, locked, validated, and rollback-safe.
- Join the surviving daemon task on every unexpected task-exit path.
- Bound the macOS native collector retry loop.

### P0 release blockers

- Restore meaningful package/archive/install verification using a staged dependency-aware release process.
- Prove native behavior on Linux ARM64, Linux x86-64, macOS Intel, and macOS Apple Silicon.
- Exercise real systemd and launchd service lifecycles.
- Record actual resource, latency, descriptor, thread, and soak measurements.
- Replace stale evidence with immutable release-candidate evidence.
- Correct registry statuses before claiming completion.
- Tag, publish, and verify the exact release candidate.

### Non-goals

Do not add:

- TLS, authentication, or public-internet hardening;
- new metrics or protocol fields;
- history, alerting, discovery, remote execution, or plugins;
- Windows support;
- a new HTTP, terminal, service-management, or configuration framework;
- release automation broader than needed to verify and publish the three existing crates;
- cosmetic refactors unrelated to an acceptance criterion below.

## Workstream A: finish launchd lifecycle correctness

### A1. Correct `launchctl bootstrap` syntax

`launchctl bootstrap` accepts a domain target and a service path. The current adapter passes the full service target as the domain.

Use:

```text
launchctl bootstrap system /Library/LaunchDaemons/com.eggstack.greggd.plist
```

Do not use:

```text
launchctl bootstrap system/com.eggstack.greggd <plist>
```

Required construction rules:

- `bootstrap`: `launchctl bootstrap <domain-target> <plist-path>`;
- `bootout`: `launchctl bootout <service-target>` or the explicitly chosen documented plist/domain form;
- `kickstart`: `launchctl kickstart -k <service-target>`;
- `print`: `launchctl print <service-target>`;
- domain target and service target must remain separate types or helper methods so they cannot be accidentally interchanged.

Add exact argument-array tests for every operation.

### A2. Configure the production plist path

`platform_service_manager()` currently constructs `LaunchdManager::new()` without a plist path. The normal CLI must instead construct the manager with the installed system plist path:

```text
/Library/LaunchDaemons/com.eggstack.greggd.plist
```

Preferred implementation:

- define one platform constant for the installed plist path;
- make `LaunchdManager::new()` production-ready by assigning that path, or have the platform factory call a dedicated production constructor;
- retain custom constructors for tests;
- avoid requiring the current working directory or repository checkout at runtime.

### A3. Define explicit service-state transitions

Required behavior:

| Initial state | `start` | `stop` | `restart` | `croncheck` |
| --- | --- | --- | --- | --- |
| Not loaded, plist present | bootstrap | idempotent success | bootstrap | bootstrap and verify running |
| Loaded, not running | kickstart | bootout or documented stop policy | clean restart | kickstart and verify running |
| Running | idempotent success | bootout | bootout then bootstrap, or documented kickstart restart | success/no restart |
| Plist missing | actionable failure | idempotent or actionable failure | actionable failure | actionable failure |

Do not infer that every failed `launchctl print` means merely `NotLoaded`. Distinguish command-execution failure from a normal not-found exit where practical.

### A4. Native launchd validation

On a real supported macOS host:

1. install the binary and plist;
2. bootstrap/start;
3. verify the process and HTTP endpoint;
4. run `greggd stop`;
5. verify it is unloaded;
6. run `greggd start`;
7. verify bootstrap and HTTP recovery;
8. run restart;
9. exercise croncheck while running and while unloaded;
10. remove the service and clean up.

Record exact commands, exit codes, architecture, macOS version, and relevant `launchctl print` output.

### A acceptance criteria

1. Bootstrap uses a domain target rather than a service target.
2. The production manager has the installed plist path without test-only construction.
3. `greggd stop && greggd start` succeeds on native macOS.
4. Start, stop, restart, and croncheck have tested behavior for all three service states.
5. Missing-plist and command-execution failures produce actionable nonzero results.
6. Native launchd transcripts are present in final evidence.

## Workstream B: make `gregg edit` transactional

### B1. Reuse the cross-process lock

Expose a narrowly scoped `ConfigStore` editing transaction rather than bypassing the store from the CLI.

The lock must cover the complete read-edit-validate-commit transaction. A second `gregg add`, `remove`, `refresh`, or `edit` process must block with the same bounded timeout instead of racing with the editor.

Do not make the raw lock guard a general public API unless necessary. Prefer a method such as:

```rust
pub fn edit_transaction(
    &self,
    edit: impl FnOnce(&Path) -> Result<(), ConfigError>,
) -> Result<(), ConfigError>;
```

### B2. Edit a temporary copy

Required sequence:

1. acquire the in-process mutex and OS file lock;
2. load the current valid configuration or create a default in memory;
3. serialize it to a temporary file in the destination directory;
4. invoke the editor on the temporary file;
5. if the editor exits nonzero, delete the temporary file and leave the live config unchanged;
6. parse the complete edited file;
7. reject unknown fields and validation violations;
8. atomically replace the live config using the existing durable write path;
9. clean up the temporary file on all paths.

Never open the live file directly in the editor.

### B3. Preserve permissions and durability

- Preserve or deliberately set appropriate user-only permissions for client configuration.
- Ensure the final rename and parent-directory sync retain the existing atomic-write guarantees.
- Do not leave editor backup files or transaction files interpreted as active config.

### B4. Tests

Add tests for:

- valid edit commits atomically;
- invalid TOML leaves original bytes unchanged;
- semantic validation failure leaves original bytes unchanged;
- nonzero editor exit leaves original bytes unchanged;
- editor launch failure leaves original bytes unchanged;
- concurrent mutation times out or waits without lost updates;
- missing config starts from a default temporary copy and commits only after validation;
- temporary files are removed on success and failure.

Use a deterministic fake editor executable or shell script; do not require an interactive terminal in CI.

### B acceptance criteria

1. `gregg edit` acquires the same cross-process lock as other mutations.
2. The live config is never exposed to partial editor writes.
3. Invalid edits and editor failures leave the original file byte-for-byte intact.
4. Valid edits commit through the atomic durable write path.
5. Concurrent CLI mutation cannot be lost during an edit session.

## Workstream C: complete daemon failure-path supervision

### C1. Do not return from inside supervision branches

The current unexpected-exit branches send shutdown and immediately return, bypassing common task joining.

Refactor supervision to produce an outcome value:

```rust
let outcome = tokio::select! {
    signal = wait_for_shutdown_signal() => RunOutcome::Signal(signal),
    result = &mut server_handle => RunOutcome::Server(result),
    result = &mut sampler_handle => RunOutcome::Sampler(result),
};

let _ = shutdown_tx.send(());
join_remaining_tasks(...).await;
return outcome.into_result();
```

Use pinned or directly borrowed join handles so the selected handle is not joined twice.

### C2. Join or abort within a global bound

- Join every still-running critical task after both normal and abnormal outcomes.
- Use one bounded shutdown deadline rather than allowing sequential per-task timeouts to multiply unexpectedly.
- If the deadline expires, abort the remaining task and await its cancellation.
- Return the original critical failure while logging cleanup failures separately.
- Ensure the daemon does not report success when cleanup timed out after an abnormal exit.

### C3. Tests

Create injectable or test-only critical-task futures to demonstrate:

- server error shuts down and joins sampler;
- server panic shuts down and joins sampler;
- unexpected clean server exit is a nonzero failure and joins sampler;
- sampler panic shuts down and joins server;
- unexpected clean sampler exit is a nonzero failure and joins server;
- signal shutdown joins both tasks and returns success;
- a non-cooperative task is aborted after the deadline;
- the original error is preserved after cleanup.

### C acceptance criteria

1. No critical-task branch returns before common cleanup.
2. Surviving tasks are joined or explicitly aborted on every exit path.
3. Unexpected clean exits and panics remain nonzero daemon failures.
4. Cleanup duration is globally bounded.
5. Tests prove failure-path joining rather than only signal-path joining.

## Workstream D: bound native macOS retry behavior

The production collector smoke test currently retries `CounterReset` indefinitely.

### D1. Add a bounded retry policy

Use both:

- a maximum attempt count; and
- an elapsed-time deadline.

For example:

```text
maximum attempts: 20
maximum elapsed time: 10 seconds
sleep between attempts: 200-500 milliseconds
```

The test must fail with diagnostics containing:

- observed architecture;
- attempt count;
- elapsed duration;
- last error kind;
- relevant counter values where available.

### D2. Keep the test meaningful

Do not convert persistent counter failure into a skipped or successful test. A virtualized runner may receive more time, but inability to produce a valid second sample remains a failure of the advertised platform class.

### D acceptance criteria

1. The native test cannot run indefinitely.
2. Transient counter resets remain tolerated.
3. Persistent failure produces a bounded, diagnostic test failure.
4. Intel and Apple Silicon jobs both execute the complete production collector path.

## Workstream E: restore dependency-aware package and install gates

Ordinary source CI should remain fast and deterministic. Add a separate release-candidate workflow rather than pretending package verification is complete in the normal CI workflow.

### E1. Create a release-candidate workflow

Create a manually dispatchable workflow, for example:

```text
.github/workflows/release-candidate.yml
```

It must accept or derive the exact candidate ref and must print and archive:

- commit SHA;
- Rust/Cargo versions;
- OS and architecture;
- Cargo metadata;
- package checksums;
- command logs.

The workflow must fail if the checked-out commit differs from the requested candidate.

### E2. Stage 1: protocol package verification

Before publishing anything:

1. run `cargo package -p gregg-protocol --list`;
2. run `cargo package -p gregg-protocol`;
3. locate the archive under `target/package/`;
4. calculate SHA-256;
5. unpack it into a clean directory;
6. build and test the unpacked crate under stable and Rust 1.75;
7. inspect normalized `Cargo.toml` and included files;
8. archive logs and checksum.

If the protocol source is unchanged from `1.0.0` but workspace inheritance requires `1.0.1`, document the metadata-only patch disposition.

### E3. Publish and index protocol `1.0.1`

Publication is an explicit human-authorized step. After publication:

- wait until the crates.io index resolves exactly `gregg-protocol 1.0.1`;
- record publication timestamp and checksum;
- install or build a clean consumer against the indexed crate;
- do not proceed using only the workspace path dependency.

### E4. Stage 2: binary package verification

After protocol indexing:

For both `greggd` and `gregg`:

1. run `cargo package --list`;
2. run verified `cargo package` without `--allow-dirty` or `--no-verify`;
3. locate `target/package/<crate>-1.0.1.crate` explicitly;
4. calculate SHA-256;
5. unpack into separate clean directories;
6. build and test the unpacked source;
7. install with `cargo install --path <unpacked-root> --locked --root <temp-root>`;
8. run binary help and noninteractive smoke commands;
9. for `greggd`, run a loopback daemon/status request test from the installed binary;
10. archive logs and checksums.

### E5. MSRV package gates

The declared Rust 1.75 compatibility must include package source, not only workspace source:

- build the unpacked protocol package under Rust 1.75;
- build the unpacked binary packages under Rust 1.75 after protocol indexing;
- verify the lockfile or generated dependency resolution does not select dependencies requiring a newer compiler;
- record any platform-specific MSRV exception explicitly rather than silently dropping the gate.

### E6. Publish and verify binaries

After all source, native, lifecycle, package, advisory, and resource gates pass:

1. publish `greggd 1.0.1`;
2. wait for index availability;
3. publish `gregg 1.0.1`;
4. install both from crates.io into empty roots;
5. run the same smoke and loopback checks against registry-installed binaries;
6. compare registry checksums and source contents to the candidate archives.

### E acceptance criteria

1. Package verification exists in an immutable release-candidate run, even if omitted from ordinary CI.
2. Every archive is located from `target/package`, checksummed, unpacked, built, and inspected.
3. Binary archives install and execute from clean roots.
4. Package builds pass Rust 1.75 where claimed.
5. Protocol publication and indexing precede verified binary packaging.
6. Registry-installed binaries pass post-publication smoke tests.

### F3. Native systemd lifecycle

On a real systemd Linux host:

1. run the installer from a working directory outside the repository;
2. confirm dedicated user/group creation;
3. confirm config preservation and ownership;
4. enable and start the unit;
5. verify process UID is nonzero;
6. verify `/v1/status` and `/healthz`;

8. confirm hardening directives do not block `/proc` or `/sys` collection;
9. test missing config and missing binary failure behavior;
10. uninstall or clean up.

### F4. Resource measurements

Run the existing measurement script or an improved equivalent against release binaries.

Record at minimum:

- release binary sizes;
- idle daemon CPU;
- daemon RSS;
- thread count;
- file-descriptor count;
- payload size;
- cached loopback p50, p95, and p99 latency;
- client CPU and RSS for 10, 50, and 100 endpoints where practical;
- environment and sampling methodology.

Report measured values even when they miss an original budget. Each miss requires a fix or an explicit reviewed deviation.

### F5. Soak evidence

Required:

- 24-hour daemon soak on Linux;
- 24-hour daemon soak on macOS;
- multi-hour client soak polling mixed Linux/macOS systems with at least one unreachable endpoint;
- periodic RSS, CPU, thread, FD, response, and error samples;
- before/after Mach-port count or equivalent native-resource evidence during repeated macOS sampling;
- final leak/growth assessment.

A script existing in the repository is not soak evidence. Attach the generated CSV/log outputs or preserve immutable external artifacts.

### F6. Dependency policy

Run `cargo deny check` on the frozen candidate and document every advisory or policy exception with:

- dependency path;
- affected functionality;
- reachability from Gregg;
- fixed-version availability;
- chosen disposition;
- follow-up owner or issue where remediation is deferred.

### F acceptance criteria

1. All four supported native architecture classes have executable evidence.
2. Real systemd and launchd lifecycle transcripts exist.
3. Resource sections contain actual measurements rather than deferred targets.
4. Linux and macOS daemon soaks complete for the required duration.
5. Mixed-fleet client soak completes with bounded resource growth.
6. Mach-port growth is measured and dispositioned.
7. Dependency advisories have explicit reviewed outcomes.

## Handoff rule

An implementing agent must leave a criterion open when it lacks required native hardware, service-manager privileges, soak duration, crates.io credentials, or publication authorization. It must record the exact blocker, attempted command, observed output, and environment needed to finish the criterion.

Do not mark this phase complete based on source presence, unit tests, compensating reasoning, green reduced CI, or a version bump. Native runs, package archives, measurements, tag identity, and registry publication are mandatory parts of the deliverable.
