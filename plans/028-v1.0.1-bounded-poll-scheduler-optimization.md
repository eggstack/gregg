# Phase 28: `v1.0.1` bounded poll-scheduler optimization

## Objective

Eliminate the scheduler’s one-Tokio-task-per-endpoint fan-out while preserving bounded concurrency, endpoint ordering, generation completeness, panic isolation, and existing cancellation semantics.

## Dependency

Phase 25 must be complete so every scheduled endpoint is canonical and pollable. Phase 27 should be in place before final evidence so the optimized scheduler is tested on all native architectures.

## Baseline behavior and cost

At baseline `eab5fe2e1d8f4635bb09aaf4ba69e18375ff5671`, `crates/gregg/src/scheduler.rs::poll_generation()`:

1. allocates a `Vec` sized to the full endpoint count;
2. calls `tokio::spawn` once for every endpoint;
3. has every task wait on a shared semaphore;
4. stores every `JoinHandle`;
5. awaits handles in endpoint order;
6. emits a synthetic `Cancelled` result when a task panics.

Concurrency at the network layer is bounded, but task creation is not. A fleet of 10,000 endpoints creates 10,000 tasks even when `max_concurrent_requests` is 16 or 64.

## Required semantic invariants

The optimized implementation must preserve:

1. first generation begins immediately;
2. generations never overlap;
3. manual refresh does not reset the periodic interval;
4. missed ticks use the existing skip policy;
5. every configured endpoint produces exactly one `PollResult`;
6. result order matches configured endpoint order;
7. generation numbers are strictly increasing;
8. maximum active polls never exceeds `max_concurrent`;
9. one poll panic produces one synthetic `Cancelled` result rather than terminating the generation;
10. dropping the output receiver stops future generations according to existing behavior;
11. cancellation behavior is not made less responsive;
12. batch start/completion timestamps retain their current meaning.

## Preferred implementation

Use a bounded in-task future stream rather than spawning all endpoints.

Conceptual shape:

```rust
let mut slots: Vec<Option<PollResult>> =
    std::iter::repeat_with(|| None).take(endpoints.len()).collect();

let stream = futures_util::stream::iter(endpoints.iter().cloned().enumerate())
    .map(|(index, endpoint)| {
        let client = self.client.clone();
        let clock = self.clock.clone();
        async move {
            let outcome = std::panic::AssertUnwindSafe(client.poll(&endpoint, &clock))
                .catch_unwind()
                .await;
            (index, endpoint, outcome)
        }
    })
    .buffer_unordered(self.max_concurrent);
```

As each item completes:

- place the result in `slots[index]`;
- convert a caught panic into a synthetic `Cancelled` result for that endpoint;
- reject duplicate or missing slot completion as an internal invariant failure.

Finally convert slots to the ordered result vector.

Equivalent bounded `JoinSet` or manually replenished window designs are acceptable when no more than `max_concurrent` tasks exist at once.

## Panic isolation

Removing `tokio::spawn` removes automatic panic isolation. Restore it deliberately.

Acceptable approaches:

- `FutureExt::catch_unwind` around each poll future;
- at most `max_concurrent` spawned tasks in a replenished `JoinSet`, with a reliable mapping from task completion to endpoint index.

Do not allow one endpoint poll panic to unwind the scheduler task or omit the endpoint from the generation.

## Result storage

O(N) result storage is expected because the complete ordered batch is required. The optimization target is task/future scheduling overhead, not eliminating the result vector.

Use one indexed result vector. Do not retain both a full handle vector and a full result vector.

The final conversion must fail loudly in tests if any slot is empty. Production code may synthesize `Cancelled` only for a known endpoint failure; it must not silently invent results for an internal indexing bug.

## Test seam

If `HttpClient` prevents deterministic concurrency tests, introduce a private trait such as:

```rust
trait EndpointPoller: Clone + Send + Sync + 'static {
    fn poll<'a>(
        &'a self,
        endpoint: &'a Endpoint,
        clock: &'a impl Clock,
    ) -> Pin<Box<dyn Future<Output = PollResult> + Send + 'a>>;
}
```

Keep it private to the crate. Implement it for `HttpClient` and for a scripted test poller.

A generic internal async function is also acceptable. Do not expose a new public API solely for testing.

## Required tests

### Concurrency bound

Use a scripted poller with atomic counters:

- increment active count on entry;
- update maximum active count;
- wait on a controlled barrier or delay;
- decrement on exit.

For endpoint counts `1`, `16`, `64`, `1_000`, and `10_000`, assert:

```text
maximum_active <= max_concurrent
```

For counts greater than the limit, assert the maximum reaches the limit when enough work is available.

### Ordered output

Complete polls deliberately out of order and assert the final batch result order exactly matches the input endpoint order.

### Completeness

For 10,000 endpoints:

- result count equals endpoint count;
- every endpoint ID appears exactly once;
- no slot is missing;
- no duplicate ID is introduced.

### Panic isolation

Make one scripted endpoint panic. Assert:

- the batch completes;
- that endpoint receives `PollOutcome::Cancelled`;
- all other endpoints retain their expected outcomes;
- result order remains correct.

### Timing/cadence regression

Retain or extend existing tests for:

- immediate first generation;
- periodic fixed cadence;
- manual refresh;
- closed refresh channel;
- no generation overlap;
- output receiver dropped;
- cancellation during or between generations according to current documented semantics.

## Measurement gate

Record a deterministic before/after comparison for a large scripted fleet. At minimum record:

- endpoint count;
- max concurrency;
- number of spawned Tokio tasks attributable to one generation, when measurable;
- maximum active polls;
- generation wall time under the same scripted delay;
- peak or approximate memory when available.

Required structural improvement:

```text
baseline spawned tasks: O(endpoint_count)
corrected spawned tasks/futures actively scheduled: O(max_concurrent)
```

The optimized implementation must not regress scripted generation wall time by more than 10% under the same runtime and test workload. If timing is noisy, use several runs and report the median.

## Guardrails

- Do not return completion order instead of config order.
- Do not spawn one task per endpoint behind another semaphore.
- Do not remove panic isolation.
- Do not overlap generations to improve throughput.
- Do not change refresh semantics.
- Do not add retries or backoff.
- Do not increase `MAX_CONCURRENT_REQUESTS`.
- Do not expose a new public scheduler abstraction solely for tests.
- Do not accept a throughput improvement that loses endpoints or changes outcomes.

## Acceptance criteria

Phase 28 is complete only when all criteria are demonstrated:

1. One generation no longer spawns one Tokio task per endpoint.
2. Active poll work is bounded by `max_concurrent`.
3. A 10,000-endpoint generation completes with exactly 10,000 results.
4. Result order matches endpoint configuration order.
5. Every endpoint ID appears exactly once.
6. One poll panic yields one `Cancelled` result without aborting the batch.
7. Existing generation, cadence, manual refresh, and no-overlap semantics pass unchanged.
8. Cancellation behavior is not less responsive than baseline.
9. No full handle vector is retained in addition to the result vector.
10. Structural work scheduling changes from O(N) spawned tasks to O(max concurrency) active work.
11. Median scripted generation time does not regress by more than 10%.
12. Scheduler tests pass on all four native architecture lanes.
13. The complete workspace gate passes.
