# Phase 16: version 1.0.1 release-integrity and evidence closure

## Objective

Close the remaining release-control defects after the Phase 15 source corrections, prove that every package, native, lifecycle, resource, soak, tag, publication, and registry-install gate evaluates one immutable candidate, and complete an auditable `1.0.1` release of:

- `gregg-protocol`;
- `greggd`;
- `gregg`.

The implementation baseline for this plan is:

```text
5b3bc4bb0cc220f3ee09c462299766d68c02cfa3
```

The substantive Phase 15 application corrections are considered landed and must be preserved:

- the installed-daemon verifier uses the real flat `greggd` configuration schema;
- startup and shutdown are bounded;
- child exit status is reaped and validated;
- config and editor temporary files are created with mode `0600` before content is written;
- required permission failures propagate;
- launchd state transitions execute through an injectable runner and deterministic tests;
- protocol publication is separated from binary package verification;
- Linux ARM64, protected systemd, protected launchd, artifact upload, and postpublication workflow foundations exist;
- the evidence ledger explicitly avoids claiming release completion.

This phase must not reopen daemon, client, protocol, collector, scheduler, or TUI architecture. It is a narrowly scoped release-integrity pass.

## Current disposition

At the baseline commit:

- workspace source is versioned `1.0.1`;
- no source SHA is frozen for publication;
- no annotated `v1.0.1` tag exists;
- crates.io contains only unyanked `1.0.0` releases;
- no final release workflow run IDs or artifact IDs are recorded;
- native Linux x86-64, native macOS Apple Silicon, native macOS Intel, systemd, launchd, resource, 24-hour soak, and mixed-fleet evidence remain incomplete;
- `postpublish-verify` invokes a repository script without checking out the repository;
- operational evidence can emit `candidate_sha = "unknown"` and omits required metadata fields;
- protected jobs accept externally supplied executables without proving that they derive from the frozen candidate;
- release soaks can be shortened below the required 24 hours;
- package jobs upload checksums and metadata but not the actual `.crate` archives;
- the aggregate job validates only artifacts from one workflow dispatch and does not prove completeness across all release stages;
- `candidate_ref` can resolve from mutable branches or lightweight tags despite being described as immutable;
- binary package installation is not consistently locked to the graph that was built and tested;
- binary dev-dependency protocol requirements remain at `1.0.0` while release dependencies require `1.0.1`.

Phase 16 is complete only when these defects are corrected and all release gates are executed against one immutable candidate.

## Governing invariants

The implementation and release operator must preserve these invariants:

1. **One source identity:** every artifact and transcript names the same full 40-character source SHA.
2. **One package identity:** every executable used for qualifying package, lifecycle, resource, or soak evidence is traceable to a verified `.crate` archive from that SHA.
3. **No mutable release references:** branch names and lightweight tags cannot satisfy immutable candidate validation.
4. **No evidence substitution:** workflow definitions, source inspection, local smoke tests, cross-compilation, and shortened soaks do not satisfy native or release-duration gates.
5. **No hidden dependency drift:** package build, test, install, and runtime checks use recorded lockfiles or otherwise prove the exact resolved graph.
6. **No partial aggregate:** a final release manifest cannot pass unless every mandatory stage and platform is present exactly once or with an explicitly documented approved rerun.
7. **No publication ambiguity:** protocol, daemon, and client publication records, checksums, timestamps, and yank states are preserved.
8. **No post-tag source mutation:** source, manifests, workflows, scripts, and packaging do not change after the annotated release tag is created.

## Scope

### P0 workflow correctness

- Check out the exact candidate before invoking repository-owned postpublication tools.
- Define and enforce one canonical evidence metadata schema.
- Tie protected-host executables to candidate package artifacts by checksum and provenance.
- Enforce release-duration soaks and deterministic mixed-fleet fixtures.
- Upload complete package and execution artifacts.
- Add cross-run final aggregation with a mandatory-stage manifest.
- Validate full commit SHAs and annotated tags explicitly.
- Align package dependency versions and locked installation behavior.

### P0 release execution

- Produce one clean final candidate commit.
- Run prepublication, native, lifecycle, resource, and soak gates.
- decide the `1.0.0` disposition;
- create and verify the annotated `v1.0.1` tag;
- publish in dependency order;
- run postpublication registry installs and runtime checks;
- reconcile immutable evidence and plan status.

### Non-goals

Do not add:

- new metrics, endpoints, wire fields, commands, or TUI behavior;
- TLS, authentication, discovery, history, alerting, or internet-facing deployment;
- Windows support;
- a new CI platform or general release framework unrelated to Gregg;
- unrelated dependency upgrades;
- bypass flags such as `--allow-dirty`, `--no-verify`, or failure-masking `|| true` in release gates;
- a claim that local ARM64 testing substitutes for the full platform matrix.

## Workstream A: make postpublication verification self-contained

### A1. Check out the frozen candidate

The `postpublish-verify` job must check out the exact candidate SHA before invoking:

- `scripts/verify-installed-daemon.sh`;
- any client configuration smoke helper;
- evidence-schema validation;
- release-manifest validation.

Required order:

1. resolve candidate identity;
2. check out `needs.resolve.outputs.candidate_sha` with detached SHA semantics;
3. verify `git rev-parse HEAD` equals the resolved candidate SHA;
4. install Rust;
5. install registry crates into clean roots;
6. execute repository-owned verification tools from the checked-out source;
7. upload complete evidence.

The postpublication job must not use scripts from `main` if the release tag points elsewhere.

### A2. Verify all three registry records

Before installing binaries, fetch crates.io records for:

- `gregg-protocol = 1.0.1`;
- `greggd = 1.0.1`;
- `gregg = 1.0.1`.

Require for each record:

- exact version `1.0.1`;
- `yanked == false`, unless an explicitly approved emergency disposition says otherwise;
- nonempty registry checksum;
- published timestamp;
- crate identity matching the requested package.

Store the raw registry JSON and a normalized summary.

### A3. Prove registry resolution

Create clean external consumers that use exact requirements:

```toml
[dependencies]
gregg-protocol = "=1.0.1"
```

For the binaries, use:

```bash
cargo install greggd --version '=1.0.1' --locked --root <clean-root>
cargo install gregg  --version '=1.0.1' --locked --root <clean-root>
```

Record:

- generated lockfiles;
- `cargo tree` output where applicable;
- installed binary SHA-256 and size;
- `--version` and `--help` output;
- installed-daemon verifier transcript;
- installed-client config mode and functional smoke transcript.

### A4. Postpublication acceptance criteria

1. Repository scripts exist because the exact candidate is checked out.
2. All three crates.io records are captured and validated.
3. Both binaries install from the registry with exact version requirements.
4. Registry-installed `greggd` passes health, status, and clean-shutdown verification.
5. Registry-installed `gregg` creates and mutates a mode-`0600` config.
6. Binary checksums, lockfiles, command output, and registry JSON are uploaded.

- `resource-summary.json`;

## Workstream C: prove candidate package and executable provenance

### C1. Treat verified `.crate` archives as release artifacts

The protocol and binary prepublication stages must upload the actual archives:

- `gregg-protocol-1.0.1.crate`;
- `greggd-1.0.1.crate`;
- `gregg-1.0.1.crate`.

For each archive preserve:

- normalized `Cargo.toml`;
- package `Cargo.lock` if present or generated verification lockfile;
- unpacked-source build and test transcript;
- MSRV transcript;
- install transcript for binaries.

### C2. Generate a package provenance manifest

Create a manifest similar to:

```json
{
  "candidate_sha": "...",
  "release_version": "1.0.1",
  "packages": {
    "gregg-protocol": {
      "archive": "gregg-protocol-1.0.1.crate",
      "sha256": "...",
      "size_bytes": 12345
    },
    "greggd": {
      "archive": "greggd-1.0.1.crate",
      "sha256": "...",
      "installed_binary_sha256": "..."
    },
    "gregg": {
      "archive": "gregg-1.0.1.crate",
      "sha256": "...",
      "installed_binary_sha256": "..."
    }
  }
}
```

The manifest must be generated from files, not manually typed values.

### C3. Eliminate unproven external binary inputs

Protected systemd, launchd, resource, and soak jobs must not accept an arbitrary executable solely because it is executable.

Use one of these approved patterns:

#### Preferred: artifact transfer

1. Download the verified binary package artifact for the frozen candidate.
2. Verify the archive checksum against the package provenance manifest.
3. Unpack and install on the protected host into a clean release-specific root.
4. Verify installed binary checksum.
5. Run lifecycle/resource/soak gates against that binary.

#### Alternate: pre-provisioned binary with proof

Only where artifact transfer is operationally impossible:

1. require the expected candidate binary checksum as an input derived from the package provenance manifest;
2. checksum the host binary;
3. fail unless checksums match exactly;
4. record the provisioning mechanism and path;
5. preserve both expected and observed checksums.

The preferred artifact-transfer path should be used for final closure.

### C4. Verify version and embedded package identity

For every qualifying binary:

- require `--version` to report `1.0.1`;
- record the binary checksum and size;
- record the archive checksum from which it was installed;
- record installation root;
- ensure no fallback to a workspace `target/release` binary.

### C acceptance criteria

1. All three `.crate` files are retained as immutable workflow artifacts.
2. Protected jobs consume package-derived binaries tied to the candidate SHA.
3. Every qualifying binary checksum is recorded and matched to package provenance.
4. No environment-variable path can silently introduce a stale binary.
5. Package, installed-binary, lifecycle, resource, and soak evidence form one traceable chain.

## Workstream D: enforce qualifying soak duration and deterministic fleet behavior

### D1. Add explicit smoke and release modes

`soak-test.sh` must distinguish:

- `--mode smoke`: short validation of harness correctness; never qualifies for release closure;
- `--mode release`: enforces the mandatory duration and evidence requirements.

For `--mode release`:

- require at least 1,440 minutes of configured duration;
- reject a shorter environment or CLI override;
- record monotonic and wall-clock start/end times;
- require observed duration to meet the configured minimum within a documented tolerance;
- require a minimum sample count derived from interval and duration;
- fail on early exit, skipped sampling, malformed output, or clock inconsistency.

### D2. Make resource measurement qualification explicit

Resource measurement should similarly distinguish smoke and qualifying modes.

A qualifying run must record:

- candidate and binary provenance;
- OS and architecture;
- duration and sample interval;
- RSS, CPU, thread, descriptor, payload-size, and latency distributions;
- configured acceptance thresholds;
- pass/fail calculation;
- raw CSV and normalized JSON summary.

Thresholds must come from the Phase 15/earlier release contract, not be invented after observing results.

### D3. Provision deterministic mixed-fleet fixtures

A mixed-fleet qualifying gate must create controlled endpoints representing:

- healthy/online;
- offline/refused connection;
- slow but eventually successful;
- timeout;
- malformed JSON;
- HTTP error;
- stale data;
- recovery from failure to healthy;
- healthy to failure transition.

Do not rely solely on arbitrary URLs supplied by the operator.

Use repository-owned fixture processes or containers with deterministic modes. Record every expected transition and observed state.

### D4. Exercise the actual client state engine

The mixed-fleet gate must exercise `gregg` or a supported nonvisual state-engine harness rather than only issuing independent `curl` requests.

Evidence must prove:

- each endpoint remains independently tracked;
- one slow endpoint does not block the fleet beyond configured concurrency behavior;
- malformed and failed endpoints do not crash the process;
- state transitions are reflected correctly;
- recovery is observed;
- refresh generations remain bounded;
- memory and task counts do not grow without bound during the run.

### D5. Platform-qualified soaks

Required qualifying soaks:

- Linux package-installed daemon: 24 hours;
- macOS Apple Silicon package-installed daemon: 24 hours with Mach-port/resource observations;
- mixed-fleet client/state engine: duration defined by the release plan, using deterministic fixtures;
- any Intel-specific long run explicitly required by the prior plan, or a documented rationale if Intel native functional evidence is sufficient and the approved contract does not require a second 24-hour soak.

### D acceptance criteria

1. A release soak cannot pass with a one-minute override.
2. Actual observed duration and sample count are validated.
3. Fleet fixtures cover healthy, slow, failed, malformed, stale, and recovery behavior.
4. The real client/state engine is exercised.
5. Raw and summarized outputs are retained.
6. Every soak uses a package-derived binary tied to the frozen candidate.

## Workstream G: enforce immutable commit and annotated-tag identity

### G1. Candidate input modes

Support two explicit modes:

#### Pre-tag candidate mode

- input must be a full 40-character lowercase hexadecimal commit SHA;
- reject branch names, abbreviated SHAs, and tags;
- check out detached at that SHA;
- record the exact input and resolved HEAD.

#### Final-tag verification mode

- input must be exactly `v1.0.1`;
- `git cat-file -t v1.0.1` must return `tag`;
- record tag-object SHA with `git rev-parse v1.0.1^{tag}` or equivalent;
- record peeled commit SHA with `git rev-parse v1.0.1^{commit}`;
- require the peeled commit to equal the frozen candidate SHA;
- reject lightweight tags.

### G2. Freeze procedure

Before tagging:

1. complete all source and prepublication corrections;
2. ensure the worktree is clean;
3. record final candidate commit SHA;
4. run all pre-tag gates against the full SHA;
5. prohibit source changes after the final qualifying gate set begins;
6. decide `1.0.0` disposition;
7. create annotated `v1.0.1` tag with release summary;
8. push the tag;
9. run tag verification mode;
10. publish only from the peeled tagged commit.

### G3. Evidence identity

Record in the final manifest and evidence ledger:

- candidate commit SHA;
- tag name;
- tag-object SHA;
- peeled commit SHA;
- tagger and timestamp;
- tag message digest or full release message;
- confirmation that source tree at the tag matches the verified candidate.

### G acceptance criteria

1. Mutable branches cannot satisfy candidate validation.
2. Abbreviated SHAs cannot satisfy candidate validation.
3. Lightweight tags cannot satisfy final tag verification.
4. Annotated tag object and peeled commit are both recorded.
5. Publication source equals the verified tagged commit.

### H acceptance criteria
