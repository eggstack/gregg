# Phase 23: `v1.0.1` macOS Mach counter correctness

## Objective

Correct the macOS Mach FFI so unsigned kernel counters preserve their bit patterns on both Intel and Apple Silicon, then prove high-bit, wrap/reset, and recovery behavior with deterministic and native tests.

## Baseline defect

At baseline `eab5fe2e1d8f4635bb09aaf4ba69e18375ff5671`:

- `crates/greggd/src/collector/macos/ffi.rs` allocates `[0i32; 4]` for `HOST_CPU_LOAD_INFO`;
- it converts each field with `buf[index] as u64`;
- Mach `natural_t` counters are unsigned 32-bit values;
- a value with bit 31 set is interpreted as a negative `i32` and sign-extended to a very large `u64`;
- `RawCpuTicks::busy()` and `total()` use saturating sums, allowing malformed values to pin sums at `u64::MAX`;
- the same direct signed-to-unsigned conversion exists for the leading VM page-count fields.

This can create repeated `CounterReset` or zero-delta behavior after a macOS host has accumulated sufficiently large CPU tick values.

## Scope

### In scope

- `crates/greggd/src/collector/macos/ffi.rs`;
- `crates/greggd/src/collector/macos/cpu.rs`;
- `crates/greggd/src/collector/macos/mod.rs` if baseline/reset handling needs a narrow correction;
- macOS unit and native smoke tests;
- macOS collector documentation if it describes counter behavior.

### Out of scope

- replacing the Mach APIs;
- adding a third-party system metrics crate;
- changing the public JSON schema;
- changing Linux collector math;
- changing sampling cadence;
- broad collector refactoring.

## Required representation

Define the relevant C/Mach scalar types explicitly:

```rust
type integer_t = i32;
type natural_t = u32;
type mach_msg_type_number_t = u32;
```

The exact Rust naming may follow project style.

The FFI call’s ABI-compatible output pointer may still use `integer_t`, but the returned payload must be interpreted as `natural_t` bit patterns. Two acceptable implementations are:

### Option A: unsigned buffer with explicit pointer cast

```rust
let mut buf = [0 as natural_t; 4];
let kr = unsafe {
    host_statistics(
        host.raw(),
        HOST_CPU_LOAD_INFO,
        buf.as_mut_ptr().cast::<integer_t>(),
        &mut count,
    )
};
```

The safety comment must explain that `integer_t` and `natural_t` are both 32-bit Mach words and the flavor defines unsigned CPU tick payloads.

### Option B: signed ABI buffer with bit-preserving conversion

```rust
fn mach_natural(word: integer_t) -> u64 {
    u64::from(word as natural_t)
}
```

Then every unsigned field uses `mach_natural(buf[index])` rather than `buf[index] as u64`.

Do not use transmute.

## CPU raw value constraints

After conversion, every individual CPU lane must be within:

```text
0..=u32::MAX
```

`RawCpuTicks::busy()` and `total()` must not rely on saturation to hide malformed values. Since four `u32` lanes fit safely in `u64`, use ordinary `u64` addition after widening each lane, or checked addition with an impossible-state assertion.

Preferred representation:

```rust
pub struct RawCpuTicks {
    pub user: u32,
    pub system: u32,
    pub idle: u32,
    pub nice: u32,
}
```

Keeping `u64` fields is acceptable only when constructors and FFI conversion guarantee `<= u32::MAX` and tests enforce that invariant.

## Counter decrease and wrap policy

The minimum release-safe policy is:

1. high-bit values such as `0x8000_0000` are treated as ordinary increasing counters;
2. a true lane decrease is classified as `CounterReset`;
3. the collector discards the old baseline;
4. the next valid pair produces a fresh CPU percentage;
5. a decrease cannot leave the collector in a permanent reset loop.

Optional bounded wrap handling may be added only when it is conservative and well tested. If implemented:

- calculate wrapping deltas per lane, not from an already summed total;
- accept wrap only when the previous value is near `u32::MAX`, the new value is near zero, and the wrapped delta is within a documented plausibility bound;
- otherwise return `CounterReset` and re-baseline.

Do not treat every decrease as a wrap; that would turn reboot/reset events into huge false CPU activity.

## VM page-count correction

The leading `HOST_VM_INFO64` fields currently read through signed Mach words. Apply the same bit-preserving conversion for:

- `free_count`;
- `active_count`;
- `inactive_count`;
- `wire_count`.

The resulting values must equal the zero-extended 32-bit payload. Do not sign-extend negative `i32` values.

Do not alter the ABI field ordering or page-size calculation in this phase.

## Required unit tests

Add tests for the conversion helper or unsigned buffer behavior:

1. `0x0000_0000` converts to `0`;
2. `0x7fff_ffff` converts to `2_147_483_647`;
3. `0x8000_0000` converts to `2_147_483_648`;
4. `0xffff_ffff` converts to `4_294_967_295`;
5. no converted CPU or VM lane exceeds `u32::MAX`;
6. no high-bit input becomes a value near `u64::MAX`.

Add CPU delta tests:

1. normal values below the signed boundary;
2. increasing values across `0x7fff_ffff -> 0x8000_0000`;
3. increasing values near `0xffff_ffff` without wrap;
4. true decrease returns `CounterReset` under the minimum policy;
5. after a reset/re-baseline, the next pair returns a valid `0..=100` percentage;
6. zero total delta remains a controlled warming/reset condition;
7. busy delta never exceeds total delta without being rejected or clamped according to existing policy.

If bounded wrap handling is implemented, also test:

- accepted small wrap;
- rejected implausibly large wrap;
- independent lane wrap;
- mixed wrap and reset conditions.

## Native tests

Run the existing native FFI smoke tests on:

- `macos-15` ARM64;
- `macos-15-intel` x86-64.

Add a native assertion that two samples can be obtained or cleanly re-warmed without producing values outside the protocol bounds. Virtualized runners may legitimately report a zero delta; that may be classified as warming/reset, but the FFI values must still remain within unsigned 32-bit bounds.

## Smaller-model implementation sequence

1. Read `ffi.rs`, `cpu.rs`, and `macos/mod.rs` completely.
2. Add conversion boundary tests before changing production conversion.
3. Introduce explicit Mach scalar aliases or one bit-preserving helper.
4. Replace every direct `i32 as u64` conversion for unsigned Mach counters.
5. Remove or justify saturating CPU sums.
6. Add high-bit delta tests.
7. Confirm reset causes re-baselining rather than permanent failure.
8. Run macOS-specific unit tests where available.
9. Run the complete workspace gate.
10. Use native CI for both macOS architectures.

## Guardrails

- Do not silence Clippy with a blanket `cast_sign_loss` allowance around the defective conversion.
- Do not change the FFI structure count or field order without checking the XNU ABI.
- Do not convert through `usize`; the kernel word is 32-bit here.
- Do not use saturating arithmetic as a substitute for correct input representation.
- Do not claim native correctness from Linux tests.
- Do not make Linux collector changes in the same commit.
- Do not add a dependency solely for four integer conversions.

## Acceptance criteria

Phase 23 is complete only when all criteria are demonstrated:

1. No unsigned Mach CPU or VM payload is converted with direct signed `i32 as u64` sign extension.
2. `0x8000_0000` becomes `2_147_483_648`, not a near-`u64::MAX` value.
3. `0xffff_ffff` becomes `4_294_967_295`.
4. CPU lane values preserve all 32 bits on Intel and ARM64.
5. CPU busy and total calculations cannot saturate because of sign-extended inputs.
6. Increasing counters across the signed boundary produce a normal percentage.
7. A genuine decrease produces a controlled reset or a conservatively validated wrap.
8. A reset is followed by successful re-baselining and recovery.
9. VM page counts use the same bit-preserving unsigned conversion.
10. The public protocol schema is unchanged.
11. Linux collector behavior and tests are unchanged.
12. Unit tests cover all four conversion boundary values.
13. Native macOS collector tests pass on Intel x86-64.
14. Native macOS collector tests pass on Apple Silicon ARM64.
15. The complete workspace gate passes.
