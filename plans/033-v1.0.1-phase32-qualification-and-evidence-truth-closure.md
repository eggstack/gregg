# Phase 33: `v1.0.1` Phase-32 qualification and evidence-truth closure

## Objective

Close the remaining release-control defects left after the Phase 32 implementation and produce immutable GitHub-hosted evidence that the complete nonpublishing orchestration path is executable before Phase 30 freezes a release candidate.

This phase is deliberately narrow. It does not reopen Gregg product behavior or the platform work owned by Phases 23 through 29. It corrects the remaining Boundary-2 verification, external-selection provenance, historical-disposition authorization, synthetic finalizer qualification, fail-closed artifact publication, and evidence-ledger consistency defects found after commit:

```text
2dae2302198aac111c4ebff8214e151e10a94554
```

At this baseline, the sustained workload and joined scheduler shutdown paths are materially corrected, cross-run manifests require GitHub artifact identity, exact package provenance association is substantially implemented, and one hosted qualification run exists. Phase 32 is nevertheless incomplete because the hosted run exercised only local gates and a short sustained smoke; Boundary-2 does not compare the generated lockfile checksum with the observed registry checksum; verification transcripts are not retained; the finalizer misstates and incompletely uploads external selection provenance; the `1.0.0` decision is hard-coded; qualification artifacts are allowed to be absent; and the evidence ledger is internally inconsistent.

Phase 33 supersedes Phase 32 only for these remaining defects. Preserve every correct Phase 31 and Phase 32 behavior.

## Current defects to close

1. `scripts/registry-reverify.py` validates that the generated lockfile contains `gregg-protocol 1.0.1` and a registry source, but it does not compare the lockfile package checksum with the checksum observed from the registry API.
2. Boundary-2 build, test, install, `--help`, `--version`, Cargo, and Rust command output is not retained as immutable evidence.
3. `release-finalize.yml` decodes a workflow-dispatch base64 selection but does not pass the decoded selection to aggregation, so the final manifest can label the source as `selection-file` instead of `workflow-dispatch-base64`.
4. The exact decoded selection, selection identity, role index, and other finalizer inputs are omitted from the uploaded finalizer artifact.
5. `1.0.0-disposition.json` hard-codes `decision: retain`; the decision is not supplied by an operator or bound to an immutable checked-in Phase-30 decision.
6. `.github/workflows/phase32-qualification.yml` executes local gates and a short sustained smoke only. It does not execute candidate/pre-tag cross-run finalization, Boundary-2 re-verification, or final cross-run finalization.
7. The qualification workflow uses `if-no-files-found: warn`, allowing a nominally successful run with missing qualification evidence.
8. The recorded hosted qualification targets `54a3a39...`, while later test changes exist at the current implementation head. No immutable run qualifies the complete current implementation.
9. `plans/v1.0.1-final-evidence.md` simultaneously records hosted qualification and states that no qualifying workflow evidence exists; its implementation SHA and blocker text are stale.
10. The Phase 32 hosted artifact contains sustained-smoke files only, not the candidate manifest, Boundary-2 candidates, retrieved manifest, provenance index, final synthetic manifest, selections, checksums, and logs required by the Phase 32 completion contract.

## Governing invariants

1. **Registry compatibility includes checksum identity.** A lockfile source and version match is insufficient unless the lockfile checksum equals the registry-observed checksum.
2. **Verification evidence is replayable.** Required commands, versions, exit statuses, stdout/stderr, and output digests must be retained as files, not merely printed to the Actions log.
3. **Selection provenance is truthful end to end.** Workflow-dispatch base64 input must remain identified as workflow-dispatch base64 through decoding, retrieval, aggregation, validation, and artifact upload.
4. **Future run data remains data only.** External selection and disposition decision inputs may not supply executable scripts, commands, paths to executables, workflow fragments, or arbitrary environment variables.
5. **Historical disposition is authorized, not inferred.** `retain` or `yank` must come from an explicit immutable operator decision; the finalizer may merge it with observed registry state but may not invent it.
6. **Synthetic qualification exercises production code paths.** Tests must invoke the same decoder, retrieval, provenance, materialization, Boundary-2, aggregation, and validation entry points used by the workflows.
7. **Synthetic topology resembles production.** Shared and package-specific artifacts, numeric GitHub artifact IDs, separate run attempts, exact candidates, and postpublication evidence must be represented realistically.
8. **Qualification artifacts are mandatory.** Missing files, empty files, wrong checksums, or incomplete output sets fail the workflow.
9. **Qualification is SHA-specific.** Any executable, workflow, script, test, schema, or fixture change after a qualifying run invalidates that run and requires a new qualification.
10. **Evidence-only reconciliation is distinguishable.** A documentation-only commit may record a prior exact implementation SHA, but it must not pretend that its own tree was qualified if it changed executable inputs.
11. **No publication occurs in Phase 33.** The qualification path must create no tag, publish no crate, and mutate no crates.io state.
12. **Validation fails closed.** Ambiguity, missing identity, source mismatch, checksum mismatch, malformed input, unauthorized decision, partial transcript, or stale evidence exits nonzero.

## Workstream A: complete Boundary-2 registry verification

### A1. Parse the exact lockfile package record

Replace substring checks in `scripts/registry-reverify.py` with semantic parsing of the generated `Cargo.lock`.

The implementation must locate exactly one package record satisfying:

```text
name == "gregg-protocol"
version == "1.0.1"
source is the expected registry source
checksum is lowercase 64-character SHA-256
```

Use Python's standard-library TOML parser where available. If compatibility with the repository's supported Python version requires a small dedicated parser, constrain it to Cargo lockfile package tables and test it extensively. Do not parse the checksum with unrestricted regular-expression search across the whole file.

Reject:

- no matching package record;
- more than one matching record;
- a path/git source;
- a missing checksum;
- a malformed checksum;
- a checksum different from `--protocol-checksum`;
- a package record with version other than `1.0.1`;
- an accepted registry URL that is not the configured production registry in production mode.

Production mode must accept the canonical crates.io sparse or git-index source forms already supported by Cargo. Test-fixture mode may accept only an explicitly supplied fixture registry source and must never activate implicitly in the release workflow.

### A2. Validate the registry API record before use

The Boundary-2 workflow must validate the crates.io response before invoking the helper:

- HTTP request succeeds;
- `.version.num == "1.0.1"`;
- `.version.yanked == false`;
- `.version.cksum` is lowercase 64-character SHA-256;
- `.version.created_at` is valid RFC3339;
- crate identity is `gregg-protocol`.

Write the complete response to an evidence file and include it in the candidate artifact with a canonical role such as `protocol-registry-record`.

### A3. Retain complete command evidence

For each package-specific Boundary-2 stage, retain files for:

```text
archive identity validation
normalized packaged Cargo.toml
fresh generated Cargo.lock
Cargo.lock SHA-256 and size
cargo metadata or cargo tree resolution proof
cargo build transcript
cargo test transcript
cargo install transcript
binary --help transcript
binary --version transcript
cargo --version
rustc --version --verbose
host/runner identity
registry API response
Boundary-2 summary JSON
```

Every required command must run through a helper that captures:

- exact argv as JSON;
- start and completion timestamps;
- exit status;
- stdout path and SHA-256;
- stderr path and SHA-256.

A nonzero command must fail immediately after its transcript is flushed. Do not rely on `tee` pipelines without `pipefail`. Do not discard stderr.

The Boundary-2 summary must bind:

- candidate SHA and release version;
- package name;
- source package workflow run ID and attempt;
- exact selected artifact name;
- exact archive relative path;
- archive SHA-256 and size from Boundary 1;
- independently recomputed archive SHA-256 and size at Boundary 2;
- registry protocol checksum;
- lockfile protocol checksum;
- lockfile source;
- lockfile SHA-256 and size;
- installed binary SHA-256 and size;
- command evidence index SHA-256 and size;
- verification verdict.

### A4. Preserve exact Boundary-1 bytes

The helper must operate on the downloaded `.crate` file directly. It may unpack the archive into a clean temporary directory but must not:

- run `cargo package` again;
- re-tar or recompress the archive;
- substitute a workspace build;
- copy a differently named archive into the expected path;
- mutate the original archive bytes.

Verify archive digest and size before unpacking. Recompute them again after all checks and fail if they changed.

### A5. Update candidate artifact roles

The `registry-reverify-greggd` and `registry-reverify-gregg` candidates must enumerate every required evidence file with a nonempty canonical role. At minimum include:

```text
registry-reverify-summary
protocol-registry-record
package-archive
normalized-manifest
verification-lockfile
resolution-proof
command-evidence-index
build-transcript
command-versions
```

Package-specific roles may be prefixed when necessary, but the role schema must be deterministic and validated.

### A6. Boundary-2 tests

Add production-code tests for:

Positive:

- exact archive and provenance match;
- lockfile resolves `gregg-protocol 1.0.1` from the expected registry;
- lockfile checksum equals the registry checksum;
- complete build/test/install/help/version evidence is materialized;
- exact archive bytes remain unchanged;
- both `greggd` and `gregg` candidates validate.

Negative:

- lockfile checksum differs from registry checksum;
- registry response checksum is malformed;
- registry response describes the wrong version;
- lockfile omits checksum;
- lockfile contains a path source;
- lockfile contains a git source;
- two matching protocol records exist;
- archive digest or size differs from Boundary 1;
- packaged manifest contains `[patch.crates-io]`;
- packaged manifest contains a path dependency;
- build, test, install, help, or version command exits nonzero;
- a required transcript is absent or empty;
- transcript index digest does not match files;
- archive bytes change during verification;
- test-registry mode is requested by the production workflow.

## Workstream B: make external selection provenance truthful and complete

### B1. Define one canonical selection identity

The finalizer must create one immutable identity document immediately after strict base64 decoding, for example:

```json
{
  "schema_version": 1,
  "source": "workflow-dispatch-base64",
  "sha256": "<decoded JSON SHA-256>",
  "size_bytes": 1234,
  "workflow_run_id": "...",
  "workflow_run_attempt": "...",
  "actor": "...",
  "candidate_sha": "<40 lowercase hex>",
  "release_version": "1.0.1"
}
```

Write it to a deterministic path such as:

```text
evidence/selection-identity.json
```

The decoder must continue to reject malformed base64, invalid UTF-8, NUL bytes, oversized input, wrong candidate SHA, wrong release version, empty selections, grouped aliases, and unsupported fields.

### B2. Pass the decoded selection explicitly through aggregation

`release-finalize.yml` must invoke aggregation with the actual decoded file:

```text
--selection evidence/release-run-selection.json
--selection-source workflow-dispatch-base64
--selection-workflow-run-id <finalizer run ID>
--selection-workflow-run-attempt <finalizer attempt>
```

Do not let the retrieved manifest's default `selection-file` label override the workflow input's true source.

Choose one of these narrow implementations and document it:

1. retrieval accepts `--selection-identity` and copies the canonical identity into its manifest; or
2. aggregation validates the retrieval selection digest/size against the canonical identity and writes the canonical identity into the final manifest.

Do not maintain two independently computed authoritative selection identities.

### B3. Validate identity agreement

Before manifest generation, require exact equality among:

- decoder-computed SHA-256 and size;
- retrieval manifest selection SHA-256 and size;
- aggregation input selection SHA-256 and size;
- final manifest selection SHA-256 and size;
- candidate SHA and release version in the decoded selection;
- finalizer workflow run ID and attempt in the canonical identity.

A source label of `selection-file` must fail when the finalizer input mode was base64.

### B4. Upload all selection evidence

The finalizer artifact must include:

```text

evidence/v1.0.1-package-provenance.json, when present

```

Also include the registry summary, disposition, and their decision identity in final mode. The exact decoded selection must be available for independent checksum verification.

### B5. Selection tests

Positive:

- final selection adds postpublication and Boundary-2 runs without changing tooling;
- final manifest says `workflow-dispatch-base64`;
- decoder, retrieval, and manifest digests match;
- exact decoded selection is present in uploaded-output fixture.

Negative:

- retrieval manifest reports a different digest or size;
- aggregation omits `--selection`;
- source is mislabeled `selection-file`;
- selection identity has the wrong run ID or attempt;
- decoded selection is not included in the final output set;
- actor is empty;
- final selection changes candidate SHA or version;
- selection contains an executable path, command, environment assignment, or workflow fragment.

## Workstream C: require an explicit `1.0.0` disposition decision

### C1. Remove hard-coded decisions

Delete unconditional workflow construction of:

```json
"decision": "retain"
```

The finalizer must receive an immutable decision input from the release operator. Use one narrow interface:

```text
disposition_decision_base64
```

The decoded JSON should contain only decision data, for example:

```json
{
  "schema_version": 1,
  "historical_version": "1.0.0",
  "candidate_sha": "<40 lowercase hex>",
  "decisions": {
    "gregg-protocol": {"decision": "retain", "rationale": "..."},
    "greggd": {"decision": "retain", "rationale": "..."},
    "gregg": {"decision": "retain", "rationale": "..."}
  }
}
```

A checked-in Phase-30 decision file is acceptable only if the finalizer takes its exact path from immutable tooling, hashes it, and the file already exists before candidate freeze. Do not support both interfaces unless one is an explicit, tested fallback with identical identity semantics.

### C2. Validate decision input before registry mutation or aggregation

Require:

- strict base64 and UTF-8 decoding;
- documented maximum size;
- schema version 1;
- `historical_version == "1.0.0"`;
- candidate SHA matches the workflow candidate;
- exactly the three crate keys;
- decision is `retain` or `yank`;
- nonempty rationale for every decision;
- no commands, paths, executable content, or arbitrary extra fields;
- SHA-256, byte size, workflow run ID, attempt, and actor identity are recorded.

Write the exact decoded decision and identity to deterministic evidence paths.

### C3. Merge decision with observed registry state

Query the three actual crates.io `1.0.0` records as already intended. Construct `1.0.0-disposition.json` by combining:

- observed version, yank state, checksum, and publication timestamp from crates.io;
- actual observation timestamp;
- explicit decision and rationale from the operator input;
- decision input digest and actor identity.

Rules:

- `yank` may be reported as completed only when observed `yanked == true`;
- `retain` with observed `yanked == true` requires an explicit ledger note explaining the already-yanked state;
- no decision may be inferred from `yanked`;
- registry observation fields may not be supplied by the operator input;
- operator decision fields may not be overwritten by registry observation.

Phase 33 must not perform a yank. It validates and records the decision contract only. Actual mutation, if ever selected, belongs to the controlled Phase-30 publication procedure.

### C4. Decision tests

Positive:

- three explicit retain decisions merge with three unyanked observations;
- a valid already-yanked observation with retain and required note validates;
- a yank decision validates only with an observation fixture showing it executed;
- decision identity appears in the final manifest evidence.

Negative:

- no decision input;
- workflow hard-codes retain;
- wrong historical version;
- wrong candidate SHA;
- missing or extra crate;
- missing rationale;
- invalid decision value;
- operator input attempts to supply checksum, yanked state, or publication time;
- observed registry record has wrong version or malformed checksum;
- yank decision with `yanked == false`;
- retain with `yanked == true` and no note;
- decision file is absent from final output.

### Workstream C acceptance criteria

- [ ] The workflow contains no inferred or hard-coded retain/yank decision.
- [ ] An explicit immutable operator decision is required in final mode.
- [ ] Decision identity includes digest, size, actor, workflow run ID, and attempt.
- [ ] Registry observations and operator decisions are merged without crossing ownership boundaries.
- [ ] The final disposition contains actual `1.0.0` records and explicit rationales.
- [ ] Invalid or missing authorization fails before final aggregation.
- [ ] Phase 33 performs no crates.io mutation.
