# Phase 26: `v1.0.1` macOS service least privilege

## Objective

Make the packaged macOS LaunchDaemon run under a dedicated unprivileged service account, preserve required metrics and networking behavior, secure its configuration and logs, and prevent a root-owned unauthenticated wildcard listener from being the installed default execution model.

## Baseline defect

At baseline `eab5fe2e1d8f4635bb09aaf4ba69e18375ff5671`:

- `packaging/launchd/com.eggstack.greggd.plist` is installed in `/Library/LaunchDaemons`;
- the plist does not specify `UserName` or `GroupName`;
- the service therefore runs as root;
- the installed default config binds `0.0.0.0:11310`;
- the API intentionally has no authentication, TLS, or rate limiting;
- the Linux systemd service already uses a dedicated `greggd` user and group.

The installer requiring root privileges is normal for system installation. The installed daemon continuing to run as root is not required by Gregg’s metric collection contract.

## Recommended dependency

Complete Phase 24 first so lifecycle tests exercise the corrected readiness semantics.

## Scope

### In scope

- `packaging/launchd/com.eggstack.greggd.plist`;
- `packaging/install-macos.sh`;
- launchd service-manager and lifecycle tests;
- package-native macOS lifecycle evidence;
- install and security documentation;
- a narrow bind-exposure warning or explicit installer policy.

### Out of scope

- sandbox profiles or Endpoint Security integration;
- code signing/notarization infrastructure;
- TLS or authentication;
- a GUI installer;
- converting the system LaunchDaemon into a per-user LaunchAgent;
- changing Linux service behavior except shared documentation/tests.

## Required service identity

Create a dedicated hidden system account and group. Recommended names:

```text
UserName: _greggd
GroupName: _greggd
```

A non-underscore `greggd` account is acceptable if the implementation follows established macOS system-account conventions consistently.

The account must:

- have no interactive login shell;
- have no usable password;
- have no home directory requiring write access;
- not be an administrator;
- not belong to privileged supplemental groups;
- be created idempotently;
- be reused safely on reinstall;
- fail installation if an existing conflicting account/group has incompatible identity.

Do not use `nobody` as the permanent service identity. A shared anonymous account weakens file ownership and auditability.

## Installer account creation

Implement explicit helper functions in `packaging/install-macos.sh`, for example:

```text
ensure_service_group
ensure_service_user
validate_service_identity
```

The implementation may use `dscl`, `dseditgroup`, and `dscacheutil` or another standard macOS system administration interface available on supported versions.

### Unique ID policy

Do not hard-code an ID that may collide silently.

The installer must either:

1. reuse the existing `_greggd` account after validating its properties; or
2. choose an unused system-range UID/GID deterministically and verify the result.

Record the chosen UID/GID in installer output. On a conflicting preexisting principal, exit nonzero with a clear diagnostic rather than modifying an unrelated account.

### Idempotence

Running the installer twice must:

- preserve the same UID/GID;
- preserve an existing valid config;
- reapply secure ownership/mode;
- replace the binary and plist safely;
- not create duplicate directory-service entries;
- leave the service start instructions correct.

## LaunchDaemon plist changes

Add:

```xml
<key>UserName</key>
<string>_greggd</string>
<key>GroupName</key>
<string>_greggd</string>
```

Use the actual chosen account name consistently.

Retain:

- `RunAtLoad`;
- bounded restart throttling;
- file-descriptor limits;
- explicit program and config paths.

Do not add privileged Mach services, sockets, or capabilities.

Validate the plist with:

```bash
plutil -lint packaging/launchd/com.eggstack.greggd.plist
```

## File ownership and modes

Use an application-specific log directory rather than a world-readable root-owned flat file. Recommended layout:

```text
/var/log/gregg/
/var/log/gregg/greggd.log
```

Recommended ownership/modes:

| Path | Owner | Group | Mode | Reason |
| --- | --- | --- | --- | --- |
| `/usr/local/bin/greggd` | root | wheel | `0755` | immutable executable for service user |
| `/Library/LaunchDaemons/com.eggstack.greggd.plist` | root | wheel | `0644` | launchd requirement |
| `/Library/Application Support/gregg` | root | `_greggd` | `0750` | service-readable config directory |
| `greggd.toml` | root | `_greggd` | `0640` | not world-readable or service-writable by default |
| `/var/log/gregg` | `_greggd` | `_greggd` | `0750` | writable service log directory |
| `greggd.log` | `_greggd` | `_greggd` | `0640` | service-writable, not world-readable |

If the daemon must edit its own config for a documented command, use the narrowest writable path and document why. The current service can read config without owning it.

The installer must correct insecure modes on an existing installation rather than preserving them silently.

## Bind exposure policy

The product is intended for trusted private-network monitoring, so wildcard binding may remain supported. The release must prevent accidental exposure through one of these approaches:

### Preferred approach

Keep the installed config’s explicit `0.0.0.0` bind only when the installer prints a prominent warning stating:

- the endpoint is unauthenticated plain HTTP;
- it must be restricted to a trusted private network/firewall;
- loopback can be selected by changing `host = "127.0.0.1"`;
- internet exposure is unsupported.

Require an explicit installer flag such as `--listen-all` before creating a new wildcard config. Without the flag, create a loopback config.

### Acceptable narrower approach

Always install loopback by default and document the manual opt-in for private-LAN binding.

Do not silently preserve the current combination of root execution and wildcard bind. Once least privilege is implemented, preserving an existing user-selected wildcard bind is acceptable with a warning.

## Metrics-access verification

Prove that the unprivileged account can execute all required macOS collector calls:

- Mach CPU load information;
- Mach VM information;
- page size;
- swap usage sysctl;
- load averages;
- hostname, kernel, architecture, and memory identity queries.

The package-native lifecycle test must run the installed binary as `_greggd`, not merely inspect the plist.

No test may use `sudo greggd run` as the qualifying service process.

## Lifecycle evidence

On both macOS architectures:

1. install the verified package artifact;
2. create/validate the service account;
3. validate plist syntax and ownership;
4. bootstrap the LaunchDaemon;
5. confirm the process effective UID/GID match the dedicated account;
6. confirm the listening socket uses the configured address/port;
7. request `/healthz` until ready or a bounded diagnostic timeout;
8. request `/v1/status` and validate schema;
9. restart with `launchctl kickstart -k`;
10. confirm a new PID still uses the dedicated account;
11. boot out the service;
12. confirm no process or listener remains;
13. preserve logs and cleanup evidence;
14. fail closed if cleanup is incomplete.

## Required tests

### Static tests

1. plist includes `UserName` and `GroupName`;
2. account names match installer constants;
3. `plutil -lint` passes;
4. plist paths match installer paths;
5. log path is writable by the service identity;
6. config is not world-readable;
7. binary and plist remain root-owned and nonwritable by the service user.

### Installer tests

Use mocks or a disposable macOS host to cover:

1. clean install creates account/group;
2. reinstall reuses account/group;
3. conflicting user fails clearly;
4. conflicting group fails clearly;
5. insecure existing modes are corrected;
6. existing config content is preserved;
7. new install defaults to loopback unless explicit private-LAN opt-in is supplied, if using the preferred policy;
8. wildcard opt-in prints the security warning;
9. missing account-creation tool fails before partial installation;
10. failure cleans temporary files and does not bootstrap a partial service.

### Runtime tests

1. service process is not UID 0;
2. service can read config;
3. service can write logs;
4. service cannot modify root-owned binary or plist;
5. all native collector queries succeed or return documented nonpermission errors;
6. `/healthz` and `/v1/status` work;
7. restart and stop are bounded;
8. no root-owned greggd process remains after test.

## Smaller-model implementation sequence

1. Add constants for service user/group and paths in the installer.
2. Add failing static tests for missing plist identity.
3. Implement idempotent group creation and validation.
4. Implement idempotent user creation and validation.
5. Add `UserName` and `GroupName` to the plist.
6. Move log ownership to a dedicated directory.
7. secure config ownership and modes.
8. implement loopback/private-LAN installation policy and warning.
9. update lifecycle scripts to assert effective UID/GID.
10. run static shell tests.
11. run native package lifecycle tests on ARM64 and Intel.
12. update documentation and evidence contract.

## Guardrails

- Do not run the installed daemon as root.
- Do not use `nobody`.
- Do not make the config world-writable or service-writable without a documented requirement.
- Do not assign arbitrary fixed UID/GID without collision validation.
- Do not mask account-creation or ownership failures with `|| true`.
- Do not bootstrap the service after a partial install.
- Do not claim success from plist inspection alone.
- Do not remove private-LAN binding support from the product.
- Do not add authentication/TLS in this phase.

## Acceptance criteria

Phase 26 is complete only when all criteria are demonstrated:

1. The LaunchDaemon specifies a dedicated nonroot `UserName` and `GroupName`.
2. The installer creates or validates that identity idempotently.
3. UID/GID collision and conflicting-principal cases fail closed.
4. The installed process effective UID is not 0.
5. The service account can execute every required collector query.
6. Config is readable by the service and not world-readable.
7. Binary and plist remain root-owned and nonwritable by the service account.
8. Logs are writable by the service without granting broad filesystem access.
9. A new install requires explicit private-LAN wildcard opt-in or defaults to loopback.
10. Existing wildcard configs are preserved only with an explicit warning.
11. Plist syntax and ownership pass validation.
12. Install, reinstall, start, readiness, status, restart, stop, and cleanup all pass.
13. Lifecycle evidence records effective UID/GID and listening address.
14. Native package lifecycle passes on macOS ARM64.
15. Native package lifecycle passes on macOS Intel x86-64.
16. No root-owned greggd process or listener remains after cleanup.
17. Shell, workspace, and release-tooling tests pass.
